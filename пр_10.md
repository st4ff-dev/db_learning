# Практична робота №10: Реалізація цілісності даних — ключі та обмеження

## Мета

Опанувати механізми забезпечення **цілісності даних** у PostgreSQL: сутнісної (`PRIMARY KEY`), доменної (`NOT NULL`, `CHECK`, `DEFAULT`, типи даних) та посилальної (`FOREIGN KEY` з каскадними діями). Продемонструвати поведінку при порушенні кожного обмеження.

> Робота продовжує пр_7–пр_9: використовуємо базу `college`, схему `college`.

---

## 1. Три рівні цілісності даних

| Рівень | Що гарантує | Механізми PostgreSQL |
|---|---|---|
| **Сутнісна** (entity integrity) | Кожен рядок унікально ідентифікується | `PRIMARY KEY`, `GENERATED ... IDENTITY` |
| **Доменна** (domain integrity) | Значення колонки відповідають дозволеному домену | `NOT NULL`, `CHECK`, `DEFAULT`, `UNIQUE`, типи даних |
| **Посилальна** (referential integrity) | Зв'язки між таблицями коректні | `FOREIGN KEY` з правилами `ON DELETE / ON UPDATE` |

## 4. Демонстрація ON DELETE RESTRICT

### 4.1. Що маємо перед експериментом

```sql
SELECT d.department_id, d.code, COUNT(c.course_id) AS courses_count
FROM college.departments d
LEFT JOIN college.courses c ON c.department_id = d.department_id
GROUP BY d.department_id, d.code
ORDER BY d.department_id;
```

```
 department_id | code | courses_count
---------------+------+---------------
             1 | IT   |             3
             2 | FIZ  |             1
             3 | MAT  |             1
```

### 4.2. Спроба видалити кафедру IT

```sql
DELETE FROM college.departments WHERE department_id = 1;
```

**Результат — помилка:**

```
ERROR:  update or delete on table "departments" violates foreign key
        constraint "fk_courses_department" on table "courses"
DETAIL: Key (department_id)=(1) is still referenced from table "courses".
```

### 4.3. Що говорить повідомлення

- **`violates foreign key constraint fk_courses_department`** — назване обмеження, яке ми заблокували.
- **`on table courses`** — у якій таблиці стоїть FK.
- **`Key (department_id)=(1) is still referenced`** — конкретне значення, що має живі посилання.

PostgreSQL **не дозволяє зламати цілісність** — батьківський запис не можна прибрати, доки є дочірні.

### 4.4. Як «обійти» RESTRICT (3 варіанти)

```sql
-- Варіант 1: спочатку перенести курси на іншу кафедру
UPDATE college.courses SET department_id = 2 WHERE department_id = 1;
DELETE FROM college.departments WHERE department_id = 1;

-- Варіант 2: видалити курси, потім кафедру
DELETE FROM college.courses WHERE department_id = 1;
DELETE FROM college.departments WHERE department_id = 1;

-- Варіант 3: тимчасово змінити FK на CASCADE (небезпечно для живої бази)
ALTER TABLE college.courses DROP CONSTRAINT fk_courses_department;
ALTER TABLE college.courses ADD CONSTRAINT fk_courses_department
    FOREIGN KEY (department_id) REFERENCES college.departments (department_id)
    ON DELETE CASCADE;
```

## 5. Демонстрація ON DELETE CASCADE

### 5.1. Що маємо перед експериментом

```sql
SELECT b.book_id, b.title,
       (SELECT COUNT(*) FROM college.demo_pages p WHERE p.book_id = b.book_id) AS pages
FROM college.demo_books b;
```

```
 book_id |       title       | pages
---------+-------------------+-------
       1 | Linux основи       |     3
       2 | SQL за 21 день     |     2
```

### 5.2. Видаляємо книгу

```sql
DELETE FROM college.demo_books WHERE book_id = 1
RETURNING book_id, title;
```

**Результат:**

```
 book_id |     title
---------+---------------
       1 | Linux основи
```

### 5.3. Перевірка — сторінки зникли автоматично

```sql
SELECT COUNT(*) FROM college.demo_pages WHERE book_id = 1;
-- 0

SELECT COUNT(*) FROM college.demo_pages WHERE book_id = 2;
-- 2 (книга 2 й сторінки не зачеплені)
```

**Висновок:** CASCADE автоматично «зачистив» усі сторінки книги разом з нею. Жодна залишкова сторінка з неіснуючим `book_id` не лишилася — цілісність збережена.

## 6. Таблиця «обмеження → команда → помилка»

Повний перелік порушень і реакцій PostgreSQL на них:

| Обмеження | Команда, що порушує | Повідомлення PostgreSQL |
|---|---|---|
| **NOT NULL** | `INSERT INTO demo_employees (full_name, age) VALUES (NULL, 30);` | `ERROR: null value in column "full_name" of relation "demo_employees" violates not-null constraint` |
| **PRIMARY KEY** (дублікат PK) | `INSERT INTO demo_books (book_id, title, author) VALUES (1, 'Дубль', 'Автор');` ⚠️ з BY DEFAULT | `ERROR: duplicate key value violates unique constraint "pk_demo_books"` |
| **IDENTITY ALWAYS** (ручна вставка) | `INSERT INTO demo_employees (employee_id, ...) VALUES (1, ...);` | `ERROR: cannot insert a non-DEFAULT value into column "employee_id"` |
| **UNIQUE** (дублікат значення) | `INSERT INTO demo_employees (full_name, email, age) VALUES ('Інший', 'ivan@test.ua', 28);` коли такий email уже є | `ERROR: duplicate key value violates unique constraint "uq_demo_employees_email"` DETAIL: Key (email)=(ivan@test.ua) already exists. |
| **CHECK (age 18..100)** | `INSERT INTO demo_employees (full_name, age) VALUES ('Молодий', 15);` | `ERROR: new row for relation "demo_employees" violates check constraint "ck_demo_employees_age"` |
| **CHECK (salary >= 0)** | `INSERT INTO demo_employees (full_name, age, salary) VALUES ('Боржник', 30, -1000);` | `ERROR: ... violates check constraint "ck_demo_employees_salary"` |
| **FOREIGN KEY** (неіснуючий parent) | `INSERT INTO demo_pages (book_id, page_number) VALUES (9999, 1);` | `ERROR: insert or update on table "demo_pages" violates foreign key constraint "fk_demo_pages_book"` DETAIL: Key (book_id)=(9999) is not present in table "demo_books". |
| **FOREIGN KEY RESTRICT** (видалити parent з дітьми) | `DELETE FROM departments WHERE department_id = 1;` | `ERROR: update or delete on table "departments" violates foreign key constraint "fk_courses_department" on table "courses"` |
| **NOT NULL + явний NULL** | `INSERT INTO demo_employees (full_name, age, salary) VALUES ('Невдалий', 40, NULL);` | `ERROR: null value in column "salary" violates not-null constraint` (DEFAULT не спрацьовує при явному NULL) |

### 6.1. Загальне правило повідомлень

Кожне повідомлення PostgreSQL містить:

1. **Рівень** — `ERROR`.
2. **Що порушено** — `violates <тип>_constraint`.
3. **Назва обмеження** — ту, яку ви задали через `CONSTRAINT name`.
4. **DETAIL** — конкретне значення, що викликало проблему.

Саме тому в пр_7 рекомендували **задавати іменовані обмеження** — у помилці видно, яке саме правило порушено.

## 7. UNIQUE і NULL — скільки NULL дозволено?

### 7.1. Експеримент

```sql
INSERT INTO college.demo_employees (full_name, email, age) VALUES
    ('Анна',   NULL, 25),
    ('Богдан', NULL, 27),
    ('Віктор', NULL, 29);
```

**Результат:** усі три INSERT проходять **без помилок**. У колонці `email` з обмеженням `UNIQUE` тепер три значення `NULL`.

```sql
SELECT employee_id, full_name, email
FROM college.demo_employees
WHERE email IS NULL;
```

```
 employee_id | full_name | email
-------------+-----------+-------
           2 | Анна      | NULL
           3 | Богдан    | NULL
           4 | Віктор    | NULL
```

### 7.2. Чому так?

У стандарті SQL `NULL ≠ NULL` — це **невизначене значення, яке не дорівнює жодному іншому**, навіть іншому NULL. Для UNIQUE це означає: два NULL не вважаються дублікатами.

Логіка: NULL — це «я не знаю», а два «я не знаю» — не те саме, що два однакових значення.

### 7.3. Нова можливість PostgreSQL 15+ — `NULLS NOT DISTINCT`

У PostgreSQL 15 з'явилася опція, що міняє цю поведінку:

```sql
CONSTRAINT uq_... UNIQUE NULLS NOT DISTINCT (email)
```

З цим прапорцем **два NULL трактуються як рівні**, і друга вставка з NULL видасть помилку унікальності. Корисно, коли ви хочете дозволити рівно один NULL (наприклад, «тільки один співробітник без email»).

### 7.4. Практичне рішення

Якщо ви хочете, щоб **кожен** співробітник мав унікальний email і не було жодного без email — додавайте ще й `NOT NULL`:

```sql
email VARCHAR(100) NOT NULL,
CONSTRAINT uq_email UNIQUE (email)
```

Разом це гарантує і наявність значення, і його унікальність.

## 8. CHECK і DEFAULT — коли спрацьовують

### 8.1. CHECK: при INSERT і UPDATE, але не при DELETE

```sql
-- Не пройде — порушує ck_demo_employees_age
INSERT INTO demo_employees (full_name, age) VALUES ('Дідо', 150);

-- Також не пройде
UPDATE demo_employees SET age = 150 WHERE employee_id = 1;
```

**CHECK не перевіряє існуючі рядки при додаванні обмеження ALTER TABLE**, якщо не вказано `NOT VALID`. За замовчуванням ALTER перевірить і закине помилку, якщо є рядки, що порушують нове правило.

Щоб додати CHECK без перевірки старих даних:

```sql
ALTER TABLE demo_employees
    ADD CONSTRAINT ck_salary_max CHECK (salary <= 1000000) NOT VALID;
```

Потім можна перевірити окремо:

```sql
ALTER TABLE demo_employees VALIDATE CONSTRAINT ck_salary_max;
```

### 8.2. DEFAULT: тільки при INSERT без значення

```sql
-- DEFAULT спрацює
INSERT INTO demo_employees (full_name, age) VALUES ('Марія', 35);
-- salary = 20000.00 (з DEFAULT), hire_date = сьогодні

-- DEFAULT НЕ спрацює (явний NULL пройде повз DEFAULT і впаде на NOT NULL):
INSERT INTO demo_employees (full_name, age, salary)
VALUES ('Невдалий', 40, NULL);
-- ERROR: null value in column "salary" violates not-null constraint
```

### 8.3. DEFAULT при UPDATE — через ключове слово

```sql
UPDATE demo_employees SET salary = DEFAULT WHERE full_name = 'Анна';
```

Тут `DEFAULT` використовується явно — це єдиний спосіб застосувати його при UPDATE.

### 8.4. Зведена таблиця

| Обмеження | Коли спрацьовує | Що робить |
|---|---|---|
| **NOT NULL** | INSERT, UPDATE | Блокує NULL |
| **CHECK** | INSERT, UPDATE | Блокує рядки, що не відповідають умові |
| **DEFAULT** | INSERT без значення, UPDATE із `= DEFAULT` | Підставляє значення за замовчуванням |
| **UNIQUE** | INSERT, UPDATE | Блокує дублікати (NULL не враховує за замовчуванням) |
| **PRIMARY KEY** | INSERT, UPDATE | NOT NULL + UNIQUE одночасно |
| **FOREIGN KEY** | INSERT, UPDATE дочірнього; DELETE/UPDATE батьківського | Блокує «висячі» посилання, виконує каскадні дії |

## 9. Відповіді на питання для захисту

### 9.1. Як CHECK взаємодіє з NULL?

**CHECK пропускає рядок, якщо умова повертає NULL або TRUE.** Блокує тільки коли умова явно FALSE.

Приклад:

```sql
age SMALLINT CHECK (age BETWEEN 18 AND 100)
```

| Значення | Результат умови | CHECK |
|---|---|---|
| 25 | `25 BETWEEN 18 AND 100` → TRUE | ✅ пропускає |
| 10 | FALSE | ❌ блокує |
| 150 | FALSE | ❌ блокує |
| NULL | `NULL BETWEEN 18 AND 100` → NULL | ✅ пропускає! |

**Це називається "three-valued logic"** — у SQL є TRUE, FALSE і UNKNOWN (NULL). CHECK блокує тільки FALSE.

**Практичний наслідок:** якщо ви хочете, щоб NULL **не допускалося**, треба додатково оголосити `NOT NULL`:

```sql
age SMALLINT NOT NULL CHECK (age BETWEEN 18 AND 100)
```

Інакше `INSERT INTO t (name) VALUES ('Безвіковий')` пройде, а `age` буде NULL — хоча CHECK ніби встановлений.

**Виняток:** можна явно заборонити NULL у CHECK:

```sql
CHECK (age IS NOT NULL AND age BETWEEN 18 AND 100)
```

Але це некрасиво — `NOT NULL` чіткіший.

### 9.2. Коли доцільний CASCADE, а коли RESTRICT?

**Правило:** вибір залежить від того, **чи має сенс дочірній запис існувати без батьківського**.

**CASCADE — для «залежних» дочірніх даних**, які не мають сенсу самі по собі:

| Приклад | Чому CASCADE |
|---|---|
| Замовлення → позиції замовлення | Позиції без замовлення — безглузді. |
| Книга → сторінки | Сторінка без книги — абсурд. |
| Клієнт → адреси клієнта | Якщо клієнт знищено, його адреси не потрібні. |
| Публікація → коментарі | Коментарі до неіснуючого поста непотрібні. |
| Теми форуму → повідомлення в темі | Повідомлення в неіснуючій темі безглузді. |

**RESTRICT — для довідкових або історично важливих даних:**

| Приклад | Чому RESTRICT |
|---|---|
| Клієнт → замовлення | Втрата історії — незаконно (аудит, фінзвіти). |
| Кафедра → курси | Випадкове видалення кафедри зруйнує навчальний план. |
| Товар → продажі | Товар, який продавали, не можна забути — звітність. |
| Користувач → створений ним контент | Авторство має лишитися (анонімізувати, не видаляти). |

**Інші опції:**

- **SET NULL** — коли зв'язок бажаний, але не критичний (категорія → підкатегорія: при видаленні категорії її підкатегорії стають кореневими).
- **SET DEFAULT** — коли є «базова» категорія-fallback (при видаленні автора статті переходять на «невідомого автора»).

**Коротке правило:** якщо не впевнені — почніть з **RESTRICT**. Його простіше послабити до CASCADE, ніж наслідки CASCADE відновити з бекапу.

### 9.3. Чому UNIQUE допускає кілька NULL?

Корінь у **тризначній логіці SQL**: NULL — це «невідоме значення», і будь-яке порівняння з NULL дає NULL, а не TRUE/FALSE.

- `5 = 5` → TRUE
- `5 = 7` → FALSE
- `5 = NULL` → NULL
- `NULL = NULL` → NULL (!), не TRUE

Обмеження UNIQUE забороняє рядки, у яких значення **рівні вже існуючим**. Але «рівність» NULL з NULL не визначена, тому СКБД не вважає два NULL дублікатами.

**Логічне обґрунтування:** NULL означає «ми не знаємо значення». Два «ми не знаємо» не можуть бути «однаковими», бо ми не знаємо, чи вони взагалі однакові. Можливо, обидва значення різні, просто ми їх не маємо.

**Приклад з життя:** у таблиці співробітників email як UNIQUE, але не всі мають email. Двоє без email — не дублікати, бо їхні email просто невідомі, а не однакові.

**Коли така поведінка не підходить:** у PostgreSQL 15+ додана опція `UNIQUE NULLS NOT DISTINCT`, що трактує NULL як звичайне рівне значення. З нею — тільки один NULL в колонці.

### 9.4. Що захищає FOREIGN KEY?

FOREIGN KEY захищає **посилальну цілісність** — властивість, яка гарантує, що:

1. **Усі посилання ведуть на існуючі записи.** Не можна вставити в `enrollments` рядок з `student_id = 999`, якщо такого студента немає.
2. **Батьківський запис не можна видалити, залишивши «висячі» посилання** (якщо правило RESTRICT).
3. **Зміни в батьківській таблиці правильно відображаються** в дочірніх (ON UPDATE CASCADE автоматично оновлює FK).

**Що станеться без FOREIGN KEY:**

- У `enrollments` з'являться записи з `student_id`, яких немає в `students` — «осиротілі».
- `JOIN students ON student_id` втрачатиме ці рядки без попередження.
- Застосунок падатиме при спробі показати студента, якого немає.
- Статистика (сума балів студента) рахуватиметься по неіснуючих даних.
- Міграції й бекапи втрачатимуть сенс — не зрозуміло, що чому належить.

**FOREIGN KEY — це контракт**: «цей стовпець завжди вказує на справжній рядок іншої таблиці». СКБД виконує контракт автоматично при кожному INSERT/UPDATE/DELETE, не покладаючись на дисципліну розробника.

**Додаткові переваги:**

- **Оптимізація запитів** — PostgreSQL може використати FK для видалення зайвих JOIN (join elimination).
- **Автоматична документація** — схема сама показує зв'язки між таблицями.
- **Підтримка CASE-засобів** — ER-діаграми, dbdiagram.io, DBeaver будують зв'язки автоматично з FK.

## 10. Підсумкова таблиця видів цілісності

| Тип цілісності | Приклади порушення | Механізм захисту | Повідомлення |
|---|---|---|---|
| **Сутнісна** | Дублікат PK; NULL у PK | `PRIMARY KEY` | `duplicate key value violates unique constraint "pk_..."` |
| **Доменна** | Негативна зарплата; вік 200 | `CHECK`, типи даних, `NOT NULL` | `violates check constraint "ck_..."` |
| **Унікальності** | Два співробітники з однаковим email | `UNIQUE` | `duplicate key value violates unique constraint "uq_..."` |
| **Посилальна** | Запис з FK на неіснуючий parent; видалення parent з дітьми | `FOREIGN KEY` + правила ON DELETE | `violates foreign key constraint "fk_..."` |
| **Прикладна** (бізнес-правила) | Складна логіка типу «баланс = сума приходів − сума видатків» | Тригери, збережені процедури, застосунок | Довільне повідомлення |

## Висновок

У межах роботи створено демо-таблиці з повним набором обмежень цілісності й продемонстровано їхню дію на практиці:

- **6 типів обмежень** — PK, FK, UNIQUE, NOT NULL, CHECK, DEFAULT — у таблиці `demo_employees`.
- **ON DELETE RESTRICT** — захищено кафедру `IT` від випадкового видалення, доки в ній є курси.
- **ON DELETE CASCADE** — видалення книги автоматично прибрало всі її сторінки.
- **9 демонстрацій порушень** із повним текстом повідомлень PostgreSQL.
- **UNIQUE і NULL** — показано, що три NULL в колонці UNIQUE проходять.
- **CHECK і DEFAULT** — з'ясовано, коли спрацьовують (CHECK пропускає NULL, DEFAULT не спрацьовує при явному NULL).

Обмеження цілісності — основний захист даних на рівні СКБД. Вони не залежать від застосунку й спрацьовують однаково для всіх клієнтів (psql, pgAdmin, бекенд, скрипти). Правильна комбінація NOT NULL + CHECK + FOREIGN KEY перекриває переважну більшість сценаріїв пошкодження даних на вхідному рівні.
