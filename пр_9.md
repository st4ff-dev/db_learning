# Практична робота №9: Маніпулювання даними у SQL / DML

## Мета

Опанувати мову **DML** (Data Manipulation Language) PostgreSQL: оператори `INSERT`, `UPDATE`, `DELETE`, `SELECT`, їх безпечне використання з умовою `WHERE`, конструкцію `RETURNING`, а також типові патерни запитів з псевдонімами, обчислюваними стовпцями та сортуванням.

> Робота продовжує пр_7 і пр_8: використовуємо схему `college.*` у базі `college`.

## 3. Частина 1 — INSERT

### 3.1. Прості INSERT з кількома рядками

```sql
INSERT INTO college.departments (code, name) VALUES
    ('IT',  'Інформаційні технології'),
    ('FIZ', 'Фізика'),
    ('MAT', 'Математика');
```

**Особливості:**

- Одним оператором вставлено 3 рядки — економніше за три окремі INSERT, бо одна транзакція й одна робота з індексами.
- Колонка `department_id` не вказана, бо вона `GENERATED ALWAYS AS IDENTITY` — значення призначить СКБД (1, 2, 3).

### 3.2. INSERT з RETURNING

```sql
INSERT INTO college.students
    (student_number, full_name, email, birth_date, enrollment_year)
VALUES
    ('ST-2024-001', 'Петренко Олег Іванович',  'petrenko@college.ua', '2005-03-12', 2024),
    ('ST-2024-002', 'Іваненко Марія Сергіївна', 'ivanenko@college.ua', '2005-07-08', 2024),
    ('ST-2024-003', 'Коваль Назар Петрович',    'koval@college.ua',    '2005-11-22', 2024)
RETURNING student_id, student_number, full_name;
```

**Що робить `RETURNING`:**

- Повертає значення колонок **одразу після вставки**.
- Корисно, коли потрібно отримати згенеровані ID для подальшого використання у транзакції — без окремого `SELECT`.
- Можна повертати будь-які колонки, у тому числі обчислені: `RETURNING student_id, full_name, UPPER(full_name) AS upper_name`.
- Форма `RETURNING *` повертає всі колонки.

**Очікуваний результат:**

```
 student_id | student_number |         full_name
------------+----------------+---------------------------
          1 | ST-2024-001    | Петренко Олег Іванович
          2 | ST-2024-002    | Іваненко Марія Сергіївна
          3 | ST-2024-003    | Коваль Назар Петрович
```

### 3.3. Перевірка кількості рядків

```sql
SELECT 'departments' AS tab, COUNT(*) FROM college.departments
UNION ALL
SELECT 'students',    COUNT(*) FROM college.students
UNION ALL
SELECT 'courses',     COUNT(*) FROM college.courses
UNION ALL
SELECT 'enrollments', COUNT(*) FROM college.enrollments;
```

**Очікуваний результат:**

```
     tab     | count
-------------+-------
 departments |     3
 students    |     4
 courses     |     5
 enrollments |     6
```

## 4. Частина 2 — UPDATE

### 4.1. Чому `WHERE` — обов'язкова

**Без WHERE `UPDATE` оновить ВСІ рядки таблиці** — класична помилка, що веде до втрати даних. Тому:

- Завжди починайте із `SELECT` з тим самим WHERE, щоб побачити, скільки рядків зачепить операція.
- Використовуйте транзакцію: `BEGIN; UPDATE … ; -- перевірка; COMMIT;` або `ROLLBACK;`.
- Додавайте `RETURNING`, щоб побачити, які рядки реально змінились.

### 4.2. Безпечний UPDATE з умовою

**Крок 1 — перевіряємо стан ДО:**

```sql
SELECT student_id, course_id, grade, status
FROM college.enrollments
WHERE student_id = 2 AND course_id = 1;
```

```
 student_id | course_id | grade | status
------------+-----------+-------+--------
          2 |         1 |  NULL | active
```

**Крок 2 — виконуємо UPDATE:**

```sql
UPDATE college.enrollments
SET grade  = 90.0,
    status = 'completed'
WHERE student_id = 2 AND course_id = 1
RETURNING student_id, course_id, grade, status;
```

**Крок 3 — стан ПІСЛЯ:**

```
 student_id | course_id | grade |   status
------------+-----------+-------+------------
          2 |         1 |  90.00 | completed
```

### 4.3. Масовий UPDATE з умовою

```sql
UPDATE college.enrollments
SET status = 'completed'
WHERE status = 'active' AND grade IS NOT NULL;
```

Переводить у статус «completed» усі записи, де є виставлена оцінка. Умова фільтрує, щоб студенти без оцінок залишилися в статусі «active».

### 4.4. UPDATE з обчисленням на основі поточного значення

```sql
UPDATE college.enrollments
SET grade = grade + 2
WHERE grade IS NOT NULL AND grade < 80;
```

Додає 2 коригувальні бали всім з оцінкою нижче 80. Важливо не забути `grade IS NOT NULL` — інакше операція `NULL + 2 = NULL` даремно пройде по рядках без оцінки.

## 5. Частина 3 — DELETE

### 5.1. Видалення з умовою WHERE

**Перед DELETE:**

```sql
SELECT * FROM college.enrollments WHERE student_id = 1 AND course_id = 2;
```

```
 student_id | course_id | enrolled_at | grade | status
------------+-----------+-------------+-------+--------
          1 |         2 | 2026-11-26  |  85.00 | active
```

**Виконуємо DELETE:**

```sql
DELETE FROM college.enrollments
WHERE student_id = 1 AND course_id = 2
RETURNING student_id, course_id, grade, status;
```

Повертає видалений рядок перед знищенням — зручно для журналу операцій.

**Після DELETE:**

```sql
SELECT * FROM college.enrollments WHERE student_id = 1 AND course_id = 2;
-- (0 rows)
```

### 5.2. Що станеться з пов'язаними даними

Ми видалили **запис зв'язку** `enrollments`, але:

- **Студент №1 (Петренко)** залишається в `students`.
- **Курс №2 (Вебтехнології)** залишається в `courses`.
- Видалено тільки **сам зв'язок** між ними.

### 5.3. А якщо спробувати видалити самого студента?

Поведінка залежить від правила `ON DELETE` у зовнішньому ключі `fk_enrollments_student`:

| Правило | Що станеться при `DELETE FROM students WHERE student_id = 1` |
|---|---|
| **CASCADE** (наш випадок) | Автоматично видалить **усі** записи в `enrollments`, де `student_id = 1`. |
| **RESTRICT** | Заблокує видалення студента, доки є залежні записи в `enrollments`. |
| **SET NULL** | У `enrollments.student_id` поставить NULL (вимагає, щоб колонка допускала NULL). |
| **SET DEFAULT** | Виставить значення за замовчуванням (яке теж має посилатися на існуючий запис). |

**Демонстрація у транзакції:**

```sql
BEGIN;
    SELECT COUNT(*) FROM college.enrollments WHERE student_id = 1;
    -- 2 рядки

    DELETE FROM college.students WHERE student_id = 1;

    SELECT COUNT(*) FROM college.enrollments WHERE student_id = 1;
    -- 0 рядків — CASCADE каскадно видалив
ROLLBACK;
```

Для `courses.department_id → departments` у нас стоїть `ON DELETE RESTRICT`, тому спроба видалити кафедру з курсами видасть помилку.

## 6. Частина 4 — п'ять базових SELECT

### 6.1. Запит з псевдонімами

```sql
SELECT
    s.student_number  AS номер,
    s.full_name       AS студент,
    s.enrollment_year AS рік_вступу
FROM college.students AS s
ORDER BY s.full_name;
```

**Що показує:**

- `AS` задає псевдонім колонки — видно користувачеві й можна використати в `ORDER BY`.
- Псевдонім таблиці (`s`) скорочує синтаксис і обов'язковий при JOIN.
- `ORDER BY` сортує за прізвищем за зростанням (`ASC` — за замовчуванням).

### 6.2. Обчислювані стовпці

```sql
SELECT
    c.code,
    c.title,
    c.credits,
    c.tuition,
    (c.tuition / c.credits)::NUMERIC(10,2) AS ціна_за_кредит,
    c.title || ' (' || c.code || ')'       AS повна_назва
FROM college.courses AS c
ORDER BY ціна_за_кредит DESC;
```

**Що показує:**

- Арифметика прямо в SELECT — `tuition / credits` з приведенням типу.
- Конкатенація рядків через `||` (SQL-стандарт).
- Сортування **за псевдонімом** — PostgreSQL це дозволяє.

### 6.3. Фільтр + сортування за кількома колонками

```sql
SELECT
    e.student_id AS студент,
    e.course_id  AS курс,
    e.grade      AS оцінка,
    e.status     AS статус
FROM college.enrollments AS e
WHERE e.grade IS NOT NULL
ORDER BY e.grade DESC, e.student_id ASC;
```

**Що показує:**

- `WHERE e.grade IS NOT NULL` — відсіяти рядки без оцінки. **Не `grade != NULL`** — у SQL це завжди дає NULL!
- Сортування за двома полями: спочатку за оцінкою (спадання), потім за ID (зростання).

### 6.4. DISTINCT + LIMIT

```sql
SELECT DISTINCT
    s.enrollment_year AS рік_вступу
FROM college.students AS s
ORDER BY рік_вступу DESC
LIMIT 5;
```

**Що показує:**

- `DISTINCT` прибирає дублікати (унікальні роки).
- `LIMIT 5` обмежує вивід до 5 рядків — корисно при величезних таблицях.

### 6.5. CASE WHEN — умовний стовпець

```sql
SELECT
    e.student_id,
    e.course_id,
    e.grade,
    CASE
        WHEN e.grade IS NULL THEN 'не виставлено'
        WHEN e.grade >= 90   THEN 'відмінно'
        WHEN e.grade >= 75   THEN 'добре'
        WHEN e.grade >= 60   THEN 'задовільно'
        ELSE                     'незадовільно'
    END AS рейтинг
FROM college.enrollments AS e
ORDER BY e.grade DESC NULLS LAST;
```

**Що показує:**

- `CASE WHEN … THEN … ELSE … END` — SQL-еквівалент if/else.
- Умови перевіряються згори вниз, перша істинна виграє.
- `NULLS LAST` — явно розмістити NULL у кінці сортування (за замовчуванням для `DESC` NULL зверху).

## 7. INSERT ... SELECT — бонусний приклад

Альтернативна форма INSERT, коли дані беруться не з літералів, а з запиту:

```sql
CREATE TEMPORARY TABLE top_students AS
SELECT student_id, full_name, enrollment_year
FROM college.students
WHERE 1 = 0;  -- тільки структура

INSERT INTO top_students (student_id, full_name, enrollment_year)
SELECT s.student_id, s.full_name, s.enrollment_year
FROM college.students s
JOIN college.enrollments e ON e.student_id = s.student_id
WHERE e.grade >= 85
GROUP BY s.student_id, s.full_name, s.enrollment_year;
```

**Коли це зручно:**

- Копіювання підмножини даних в іншу таблицю (архівація, staging).
- Міграції — перенесення даних між таблицями при зміні структури.
- Створення звітних таблиць із результатів агрегатних запитів.

## 8. Чому `UPDATE` / `DELETE` обов'язково мають `WHERE`

Це **основне правило безпеки** DML. Без `WHERE`:

```sql
-- НЕБЕЗПЕЧНО: оновить ВСІ рядки в таблиці
UPDATE college.enrollments SET status = 'completed';

-- КАТАСТРОФА: видалить ВСІ записи
DELETE FROM college.enrollments;
```

Правила роботи з DML на реальній базі:

1. **Спочатку `SELECT` з тим самим WHERE**, щоб побачити, скільки рядків зачеплять.
2. **Виконуйте у транзакції** `BEGIN; UPDATE … ; SELECT … ; COMMIT;` з можливістю `ROLLBACK;`.
3. **Додавайте `RETURNING`**, щоб бачити, що реально змінилось.
4. **Робіть бекап** перед масовими операціями.
5. **Використовуйте LIMIT у UPDATE/DELETE** (PostgreSQL розширення через підзапит з `ctid`), коли не впевнені:
   ```sql
   DELETE FROM enrollments WHERE ctid IN (
       SELECT ctid FROM enrollments WHERE ... LIMIT 10
   );
   ```
6. **Увімкніть auto-commit = off** у клієнті, щоб випадкове натискання Enter не фіксувало операцію.

## 9. Відповіді на питання для захисту

### 9.1. Що станеться, якщо виконати UPDATE без WHERE?

`UPDATE` без `WHERE` оновить **усі рядки** таблиці згідно з переліком `SET`. Приклад:

```sql
UPDATE college.enrollments SET status = 'completed';
```

Усі записи в `enrollments` отримають статус `completed`, незалежно від того, яка була оцінка, чи взагалі було виставлення.

**Наслідки:**

- Втрата попередніх значень (без транзакції або бекапу — назавжди).
- Може спрацювати цілий ланцюг тригерів на всю таблицю.
- У великих таблицях — тривала операція з блокуванням.
- Складні випадки — нечутливе до бізнес-логіки оновлення, що потім виявляється через тижні.

PostgreSQL **не попереджає** — для нього це коректний SQL. Деякі клієнти (DBeaver, pgAdmin) мають налаштування «Safe mode», що запитує підтвердження на UPDATE/DELETE без WHERE.

У MySQL є параметр `sql_safe_updates`, що блокує такі запити. У PostgreSQL аналога немає — захист лежить на дисципліні розробника.

### 9.2. Для чого потрібен RETURNING?

`RETURNING` — розширення PostgreSQL, яке дозволяє INSERT/UPDATE/DELETE **повертати рядки, які вони змінили**. Корисне у трьох сценаріях:

**1. Отримати згенерований ID:**
```sql
INSERT INTO students (full_name) VALUES ('Іван')
RETURNING student_id;
```
Замість окремого `SELECT currval(...)` або `MAX(id)`.

**2. Логування операцій у транзакції:**
```sql
WITH deleted AS (
    DELETE FROM old_orders
    WHERE created_at < '2020-01-01'
    RETURNING *
)
INSERT INTO archive.orders SELECT * FROM deleted;
```
Переміщення рядків між таблицями одним кроком.

**3. Підтвердження операції користувачу:**
```sql
UPDATE enrollments SET grade = 90
WHERE student_id = 1 AND course_id = 1
RETURNING *;
```
Клієнт одразу бачить, що саме змінилось.

**4. Кількість зачеплених рядків:**
Клієнт і так отримує кількість (`UPDATE 5`), але з `RETURNING` бачить і самі значення.

**Переваги над альтернативами:**

- Без `RETURNING` потрібно два запити (INSERT + SELECT), що може дати неузгоджений результат у паралельних транзакціях.
- Атомарність — все в одній операції.
- Відкочується разом з транзакцією.

### 9.3. Як поведінка зовнішнього ключа впливає на DELETE?

Поведінка задається правилом `ON DELETE` у визначенні FK. Варіанти:

| Правило | Поведінка при `DELETE` батьківського запису |
|---|---|
| **NO ACTION** (за замовчуванням) | Операція відхиляється наприкінці транзакції, якщо є залежні записи. |
| **RESTRICT** | Операція відхиляється одразу — суворіший варіант NO ACTION. |
| **CASCADE** | Автоматично видаляються всі залежні записи. |
| **SET NULL** | FK у залежних записах стає NULL. Колонка має дозволяти NULL. |
| **SET DEFAULT** | FK отримує значення DEFAULT (яке теж має посилатися на реальний запис). |

**Приклади з нашої моделі:**

- `fk_enrollments_student` **CASCADE**: видалення студента автоматично прибирає його записи на курси. Логічно — студента звільнили, його зв'язки з курсами теж.
- `fk_courses_department` **RESTRICT**: не можна видалити кафедру, у якої є курси. Треба спочатку перенести або видалити курси.
- `fk_enrollments_course` **RESTRICT**: не можна видалити курс, на який уже зареєстровані студенти. Теж захист від втрати історії.

**Практичне правило:** CASCADE — для «слабких» дочірніх таблиць, що логічно належать батьківському запису (позиції замовлення, адреси клієнта). RESTRICT — для довідкових таблиць, видалення яких зруйнує історію (клієнти, товари, кафедри).

### 9.4. Чим `INSERT ... VALUES` відрізняється від `INSERT ... SELECT`?

Обидва додають рядки, але джерело значень різне.

**`INSERT ... VALUES`** — вставка **літеральних** значень, відомих на момент написання запиту:

```sql
INSERT INTO students (full_name, enrollment_year)
VALUES ('Іван Петренко', 2024),
       ('Марія Коваль', 2024);
```

- Кількість рядків відома заздалегідь.
- Значення — константи або параметри з коду.
- Швидко й зрозуміло для невеликої кількості рядків.
- Прив'язано до структури VALUES — кожен рядок має ту саму кількість значень.

**`INSERT ... SELECT`** — вставка **результату запиту**:

```sql
INSERT INTO archive_students (student_id, full_name, enrollment_year)
SELECT student_id, full_name, enrollment_year
FROM students
WHERE enrollment_year < 2020;
```

- Кількість рядків невідома — залежить від запиту.
- Джерело — інша таблиця (або JOIN, підзапит, WITH).
- Дозволяє перенос даних між таблицями, агрегацію при вставці, фільтрацію.
- Може бути вкладеним у транзакцію з іншими операціями.

| Критерій | `INSERT ... VALUES` | `INSERT ... SELECT` |
|---|---|---|
| Джерело даних | Константи в коді | Результат запиту |
| Кількість рядків | Фіксована | Залежить від запиту |
| Типовий сценарій | Додавання нових записів з коду | Копіювання/міграція/агрегація |
| Транзакційна атомарність | ✅ | ✅ |
| Продуктивність | Швидко для малої кількості | Швидко навіть для мільйонів рядків (все в СКБД) |

**Коли використовувати який:**

- Нові рядки від користувача або тесту → `VALUES`.
- Архівація, перенос, звітні таблиці, EAV-проекції → `SELECT`.
- Хочеться одразу поєднати додавання з агрегатом (середнє, сума, групування) → `SELECT`.

## Висновок

У межах роботи виконано повний цикл DML-операцій над схемою `college.*`:

- **Наповнено** 4 таблиці тестовими даними через `INSERT`.
- Продемонстровано `RETURNING` — ефективний спосіб отримати згенеровані ID або підтвердження операції.
- Виконано **безпечний UPDATE** з умовою `WHERE` і показом стану «до/після».
- Виконано **DELETE** і пояснено, як поведінка FK (CASCADE/RESTRICT) впливає на результат.
- Склад­ено **5 базових SELECT** з псевдонімами, обчислюваними стовпцями, CASE, DISTINCT, LIMIT.
- Додатково показано `INSERT ... SELECT` як альтернативу `VALUES`.

Усі зміни зроблено з явними умовами `WHERE` — головне правило безпеки роботи з живими даними. Транзакційна обгортка (`BEGIN … ROLLBACK`) використана для експериментів без ризику зіпсувати основну схему.

Наступний крок — **складні SELECT з JOIN, GROUP BY, HAVING, підзапитами** — тобто основна аналітична сила SQL.
