# Практична робота №14: Версіонування схем і міграції

## Мета

Опанувати практику **міграцій бази даних** у стилі Flyway / Liquibase — фіксацію змін схеми як послідовності версіонованих файлів, їх автоматичне застосування з відстеженням стану, зворотні кроки та підхід до змін, що не виконуються одним кроком.

> Робота оперує базою `college` з попередніх практичних. Нові таблиці й колонки додаються через міграції.

---

## 1. Що таке міграції й навіщо вони

**Міграція** — SQL-файл з ідентифікатором версії, який виконується **рівно один раз** на кожній базі й фіксується у спеціальній таблиці-журналі. Вся історія змін схеми живе в git поряд з кодом застосунку.

**Переваги підходу:**

- **Відтворюваність** — будь-хто з команди може підняти ту саму схему з нуля.
- **Узгодженість середовищ** — dev, staging, production отримують однакові зміни в однаковому порядку.
- **Безпечне розгортання** — CI/CD автоматично застосовує нові міграції при деплої.
- **Аудит** — видно, хто і коли яку зміну зробив.
- **Можливість відкату** — для кожної міграції готують зворотний скрипт.

### 1.1. Два найпопулярніші формати

| Інструмент | Правило іменування | Приклад |
|---|---|---|
| **Flyway** | `V<version>__<name>.sql` | `V7__add_index_on_date.sql` |
| **Liquibase** | XML/YAML/SQL changeset із власним id | `<changeSet id="7" author="student">` |

У цій роботі використовуємо стиль **Flyway** — найпростіший і найпоширеніший.

## 3. Опис кожної міграції

### 3.1. V1 — Init

**Файл:** `V1__init.sql`

**Що робить:** створює чотири базові таблиці (`departments`, `students`, `courses`, `enrollments`) з усіма обмеженнями й тестовими даними. Це початковий стан (еквівалент `schema.sql` з пр_7).

**Зворотна дія (U1):** `DROP TABLE` у зворотному порядку залежностей. Застосовується лише при повному скиданні середовища.

### 3.2. V2 — Add teacher_id

**Файл:** `V2__add_teacher_id.sql`

**Що робить:** додає обов'язковий стовпець `courses.teacher_id` з FK на нову таблицю `teachers`. Оскільки `courses` **уже містить дані**, прямо додати `NOT NULL`-колонку без DEFAULT неможливо. Тому міграція **розбита на 6 кроків**:

1. Створити таблицю `teachers`.
2. Вставити декілька записів (принаймні один — для «старих» курсів).
3. Додати колонку `teacher_id` як **NULL**.
4. Виконати backfill — `UPDATE … SET teacher_id = 2`.
5. Накласти `SET NOT NULL`.
6. Додати `FOREIGN KEY` та індекс.

**Чому не одним `ALTER`:**

```sql
-- НЕ СПРАЦЮЄ:
ALTER TABLE courses ADD COLUMN teacher_id INTEGER NOT NULL REFERENCES teachers(teacher_id);
-- ERROR: column "teacher_id" of relation "courses" contains null values
```

PostgreSQL вставить NULL у існуючі рядки й одразу ж викине помилку через `NOT NULL`. Тому і потрібен проміжний стан «спочатку NULL + backfill».

**Зворотна дія (U2):** прибрати FK, колонку та таблицю `teachers`. **УВАГА:** призначення викладачів втрачається назавжди.

### 3.3. V3 — Drop status

**Файл:** `V3__drop_status.sql`

**Що робить:** видаляє колонку `enrollments.status` (вирішено, що статус однозначно виводиться з наявності `grade` і дати). Додатково показує зміну існуючого `CHECK` — звуження до оцінок з точністю 1 знак після коми.

**Зворотна дія (U3):** повернути колонку з DEFAULT 'active' і повернути старий CHECK. **УВАГА:** оригінальні значення статусів втрачаються; відновлюється лише структура.

## 4. Таблиця відстеження виконаних міграцій

Runner `apply.sh` створює таблицю:

```sql
CREATE TABLE public.schema_migrations (
    version      VARCHAR(20)  PRIMARY KEY,   -- V1, V2, V3
    filename     VARCHAR(255) NOT NULL,
    applied_at   TIMESTAMPTZ  NOT NULL DEFAULT NOW(),
    applied_by   VARCHAR(50)  NOT NULL DEFAULT CURRENT_USER,
    checksum     TEXT                        -- SHA-256 файлу
);
```

**Призначення полів:**

- `version` — первинний ключ, забезпечує унікальність.
- `filename` — історичне ім'я, щоб бачити, що саме виконувалось.
- `applied_at` — коли (для аудиту й розслідувань інцидентів).
- `applied_by` — хто (нік БД-користувача).
- `checksum` — контрольна сума файлу. Якщо файл змінився після застосування — це проблема (міграції мусять бути **immutable** після релізу).

## 6. Приклад зміни, яку неможливо виконати як одну атомарну міграцію

### 6.1. Сценарій: розділити `full_name` на `first_name` і `last_name`

Було:
```sql
students (
    student_id INTEGER PK,
    full_name  VARCHAR(100) NOT NULL,
    ...
)
```

Стане:
```sql
students (
    student_id INTEGER PK,
    first_name VARCHAR(50) NOT NULL,
    last_name  VARCHAR(50) NOT NULL,
    ...
)
```

### 6.2. Чому не можна одним кроком

Міграція відбувається **не моментально**:

1. Є **уже задеплоєний застосунок**, який **читає і пише** колонку `full_name`.
2. Нова версія застосунку **ще не відкочена** — вона читає `first_name`/`last_name`.
3. Під час деплою частина серверів працює зі старою версією, частина — з новою.
4. Якщо видалити `full_name` одним кроком — усі старі екземпляри впадуть з помилкою `column full_name does not exist`.

Крім того, автоматично «розрізати» `full_name` на дві частини не завжди коректно: «Петренко Олег Іванович» ≠ `(first_name='Петренко', last_name='Олег Іванович')`.

### 6.3. Правильна послідовність — п'ять міграцій

**Етап 1 — V5: Додати нові колонки як NULL**

```sql
ALTER TABLE college.students
    ADD COLUMN first_name VARCHAR(50),
    ADD COLUMN last_name  VARCHAR(50);
```

**Етап 2 — Задеплоїти застосунок v2.** Нова версія пише ОДНОЧАСНО в `full_name` та `first_name/last_name`, читає з обох, з пріоритетом на нові. Стара версія продовжує писати тільки в `full_name` — це OK, бо нові колонки NULL-дозволені.

**Етап 3 — V6: Backfill** існуючих даних:

```sql
UPDATE college.students
SET
    last_name  = SPLIT_PART(full_name, ' ', 1),
    first_name = TRIM(SUBSTRING(full_name FROM POSITION(' ' IN full_name)))
WHERE first_name IS NULL AND full_name IS NOT NULL;
```

Якщо автоматика не впорається з частиною рядків — люди вручну правлять через адмінку.

**Етап 4 — V7: Накласти NOT NULL**:

```sql
ALTER TABLE college.students
    ALTER COLUMN first_name SET NOT NULL,
    ALTER COLUMN last_name  SET NOT NULL;
```

**Етап 5 — Задеплоїти застосунок v3.** Нова версія читає/пише ТІЛЬКИ `first_name/last_name`, забуває про `full_name`.

**Етап 6 — V8: Видалити стару колонку** (тільки після того, як переконалися, що v3 стабільно працює кілька днів):

```sql
ALTER TABLE college.students DROP COLUMN full_name;
```

### 6.4. Загальне правило — Expand-Contract Pattern

Патерн, за яким виконують подібні зміни:

```
┌─────────┐    ┌─────────┐    ┌─────────┐
│ Expand  │ ─▶ │ Migrate │ ─▶ │ Contract│
└─────────┘    └─────────┘    └─────────┘
```

- **Expand** (розширення): додаємо нову структуру, залишаючи стару. Схема може підтримувати і старий, і новий код.
- **Migrate** (перенесення): переносимо дані, перемикаємо код на нову структуру.
- **Contract** (стиснення): прибираємо стару структуру.

Між етапами має пройти **час на стабілізацію й відкат, якщо щось пішло не так**.

### 6.5. Інші типові «багатокрокові» зміни

| Зміна | Чому багатокрокова |
|---|---|
| **Перейменування колонки** | Старий код шукає старе ім'я. Правильно: додати нову → копіювати при INSERT/UPDATE → міграція коду → видалити стару. |
| **Зміна типу з несумісним cast** | `VARCHAR → INTEGER`: треба нова колонка, backfill, валідація, видалення старої. |
| **Розділення / об'єднання таблиць** | Обидві таблиці мусять існувати паралельно під час деплою нового коду. |
| **Переніс FK (зміна parent-таблиці)** | Нова FK стовпчик → backfill → перемикання коду → видалення старої FK. |
| **Жорстке звуження CHECK** | Спочатку валідація, виправлення даних, потім ALTER з новим CHECK. |

## 7. Відповіді на питання для захисту

### 7.1. Чому міграції зберігають у репозиторії разом із кодом?

Схема даних і код — **одна цілісна система**. Якщо вони розходяться, застосунок падає. Міграції в репозиторії дають:

1. **Синхронізацію з кодом** — новий код часто вимагає нових колонок/таблиць. Коли вони в тому ж комміті, деплой автоматично приводить базу у відповідність.
2. **Один «автор правди»** для схеми. Інакше розробник у Києві бачить колонку, яку додав колега у Львові, лише коли впаде його код.
3. **Історію змін.** `git blame V7__add_index.sql` одразу показує, хто й навіщо додав цей індекс.
4. **Автоматизацію** CI/CD — пайплайн прогону тестів може підняти БД і застосувати міграції, щоб тести мали актуальну схему.
5. **Відтворюваність середовищ.** Новий розробник клонує репо, запускає `./apply.sh` — і має робочу копію production-схеми.
6. **Контроль через code review.** Міграція проходить рев'ю, як і звичайний код — колеги ловлять помилки заздалегідь.

Альтернатива («база як окремий ресурс, яким править DBA руками») **не масштабується** — у командах понад 2-3 розробника починаються конфлікти, забуті зміни, «це на моєму локальному працює».

### 7.2. Що таке зворотна міграція і коли вона потрібна?

**Зворотна міграція (rollback / down migration)** — скрипт, який **скасовує** дію прямої міграції й повертає схему до попереднього стану.

**Коли потрібна:**

1. **Деплой пройшов невдало.** Виявили, що нова колонка/таблиця ламає продакшен. Відкочуємо схему разом із кодом.
2. **Тести на staging показали проблему** — відкочуємо для діагностики.
3. **Експериментальна зміна** — фічу не прийняли, прибираємо з бази.
4. **Відновлення з бекапу** в комбінації з реплеєм міграцій до певної точки.

**Коли зворотна міграція НЕ рятує:**

- **Зміни, що втрачають дані.** `DROP COLUMN` знищує вміст — rollback не поверне його, лише структуру. Потрібен бекап.
- **Зміни, що залежать від стану середовища.** Якщо між deploy і rollback з'явилися нові рядки з новою структурою — вони несумісні зі старим кодом.
- **Коли зворотний запит фізично неможливий** без втрат (наприклад, зміна типу з округленням).

**Практика індустрії:** багато команд (GitHub, Shopify) взагалі **відмовляються від rollback'ів для production** і замість цього пишуть «rollforward» міграції — нові V-файли, що виправляють помилку. Причина: rollback у production — рідкісна операція, краще мати «одну дорогу вперед».

У навчальному контексті зворотні скрипти корисні — вони примушують розробника думати про оборотність і наслідки кожної зміни.

### 7.3. Як міграції допомагають узгодити схеми у різних командах?

**Проблема без міграцій:** команда А додала колонку `is_premium` локально; команда Б додала колонку з такою самою назвою, але іншим типом; у production — третій варіант, який ніхто не пам'ятає. У результаті дзвінок DBA на вихідних.

**Рішення з міграціями:**

1. **Глобальна послідовність версій** (V1, V2, V3…) — кожна зміна отримує унікальний ідентифікатор.
2. **Чергування через git:** при merge конфлікту номерів розв'язують звичайним merge, перенумеровуючи або додаючи `V7a`, `V7b`.
3. **Кожне середовище застосовує той самий набір файлів** у тому самому порядку. Dev, staging, production отримують однакову схему.
4. **CI перевіряє консистентність:** у pipeline є крок «застосувати міграції на чистій базі, прогнати тести». Зламана міграція не потрапляє в main.
5. **Checksum захищає від мовчазної зміни.** Якщо хтось редагує вже застосовану `V2__init.sql`, checksum не збігається з журналом, runner видає помилку й не продовжує.
6. **Явний reviewer-процес.** Pull request з міграцією привертає увагу решти команди — обговорюють наслідки до застосування.

**Правило непорушності:** **застосована міграція не змінюється**. Потрібне виправлення — новий файл `V7__fix_V5_mistake.sql`. Це гарантує, що історія схеми послідовна й реконструйована.

### 7.4. Чому зміну NOT NULL на таблиці з даними складно зробити одним кроком?

Спроба додати `NOT NULL`-колонку одним кроком:

```sql
ALTER TABLE courses ADD COLUMN teacher_id INTEGER NOT NULL;
```

**Що відбувається:**

1. PostgreSQL додає колонку `teacher_id` з NULL для всіх існуючих рядків.
2. Одразу ж перевіряє `NOT NULL`-обмеження.
3. Бачить NULL у існуючих рядках → помилка:
   ```
   ERROR: column "teacher_id" of relation "courses" contains null values
   ```
4. Усю операцію відкочено, таблиця незмінна.

**Варіанти вирішення:**

**А) З DEFAULT (одним кроком можливо):**

```sql
ALTER TABLE courses ADD COLUMN teacher_id INTEGER NOT NULL DEFAULT 1;
```

Існуючі рядки отримують `teacher_id = 1`. Але:
- Чи існує teacher з id=1? Якщо ні — FK упаде.
- Чи логічно «всіх старих курсів» віднести до одного конкретного викладача? Зазвичай ні — потрібен **ручний або автоматичний backfill**.

**Б) Три кроки (наш варіант у V2):**

```sql
-- Крок 1: додаємо як NULL
ALTER TABLE courses ADD COLUMN teacher_id INTEGER;

-- Крок 2: заповнюємо (backfill) — може бути складна бізнес-логіка
UPDATE courses SET teacher_id = 2 WHERE teacher_id IS NULL;
-- або
UPDATE courses c SET teacher_id = (
    SELECT teacher_id FROM department_defaults WHERE dept_id = c.department_id
);

-- Крок 3: тепер колонка готова до NOT NULL
ALTER TABLE courses ALTER COLUMN teacher_id SET NOT NULL;
```

**Чому не завжди в одній міграції:**

- **На великих таблицях** `UPDATE ...` може виконуватися години з блокуванням. Його виносять в окрему міграцію або фонову задачу.
- **Backfill може потребувати бізнес-рішень** — хто з людей має прийняти рішення про «старі» дані.
- **Нова версія застосунку** мусить встигнути задеплоїтися й почати писати `teacher_id` для нових рядків до того, як накладається `NOT NULL`.
- **PostgreSQL бере ACCESS EXCLUSIVE lock** на час `ALTER TABLE SET NOT NULL` — на пару секунд блокує всі читання й запис у таблицю. На продакшені це вікно.

**Рецепт безпечного релізу:**

```
V7:  ADD COLUMN teacher_id INTEGER;  -- NULL ok
→ деплой застосунку, який пише teacher_id для нових рядків
V8:  backfill існуючих рядків (можливо, в декілька UPDATE-порцій)
V9:  ALTER COLUMN teacher_id SET NOT NULL;
V10: ADD FOREIGN KEY ... REFERENCES teachers(teacher_id);
```

Між кроками — валідація (`SELECT COUNT(*) FROM courses WHERE teacher_id IS NULL;` → має бути 0 перед V9).

## Висновок

- **Міграції** — стандартний спосіб версіонувати схему БД поряд із кодом застосунку.
- **Flyway-стиль іменування** (`V<n>__<name>.sql`) + таблиця `schema_migrations` дає ідемпотентність і аудит.
- **Зворотні скрипти** (`U<n>__…`) — для контрольованого відкату в dev/staging; у production рідко використовуються, зазвичай пишуть «rollforward».
- **Додавання `NOT NULL`-колонки на таблиці з даними** — неможливо одним кроком без DEFAULT; стандартний патерн: ADD NULL → backfill → SET NOT NULL.
- **Expand-Contract pattern** — для змін, що не виживають миттєвий деплой (перейменування, розділення колонки): додати нове, мігрувати, видалити старе через кілька релізів.
- **Правило непорушності:** вже застосована міграція не змінюється; виправлення — завжди новий файл.

Робочий `apply.sh` + папка міграцій готові для занесення в репозиторій і використання у подальших практичних роботах.
