# Міграції бази `college`

Папка містить версіоновані міграції SQL у стилі **Flyway** (`V<n>__<name>.sql`) та скрипт `apply.sh`, який їх застосовує й відстежує.

## Файли

| Файл | Призначення |
|---|---|
| `V1__init.sql` | Початкова схема (4 таблиці + тестові дані) |
| `V2__add_teacher_id.sql` | Додає `teachers` та обов'язковий FK `courses.teacher_id` |
| `V3__drop_status.sql` | Видаляє колонку `status` і звужує CHECK на `grade` |
| `U1`..`U3` | Rollback-скрипти для кожної версії (у зворотному порядку) |
| `apply.sh` | Runner: застосовує нові міграції, пропускає вже виконані |

## Як користуватися

```bash
# Застосувати все нове (ідемпотентно — повторний запуск нічого не зробить)
./apply.sh

# Побачити стан
./apply.sh --status

# Відкотити останню версію
./apply.sh --rollback V3
```

Runner створює таблицю `public.schema_migrations`, у якій зберігає:
- `version` — `V1`, `V2`, …
- `filename` — ім'я файлу
- `applied_at` — коли застосовано
- `applied_by` — хто застосував
- `checksum` — SHA-256 файлу (для виявлення змін у вже застосованих міграціях)

## Правила

1. **Нова міграція — новий файл з більшим номером.** Не змінюємо вже застосовані!
2. **Один файл = одна атомарна зміна.** Усе всередині виконується в транзакції (`-v ON_ERROR_STOP=1`).
3. **Назви описові:** `V7__add_index_on_enrollments_date.sql`, а не `V7__fix.sql`.
4. **Зворотні кроки — окремі файли** `U<n>__rollback_<name>.sql`. Застосовуються лише у виняткових випадках.
5. **Тестувати на копії БД** перед production.
