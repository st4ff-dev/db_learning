## 2. Вихідне (денормалізоване) відношення

Візьмемо «плоский звіт», який об'єднує відомості про студента, курс, кафедру та оцінку в одну широку таблицю:

**`enrollment_report`**

| Атрибут | Тип | Опис |
|---|---|---|
| `student_id` | INT | ID студента |
| `student_name` | VARCHAR | ПІБ студента |
| `student_phones` | VARCHAR | **Список телефонів через кому** ⚠ |
| `enrollment_year` | SMALLINT | Рік вступу |
| `course_code` | VARCHAR | Код курсу |
| `course_title` | VARCHAR | Назва курсу |
| `course_credits` | SMALLINT | Кредити |
| `course_tuition` | NUMERIC | Плата за курс |
| `department_id` | INT | ID кафедри |
| `department_code` | VARCHAR | Код кафедри |
| `department_name` | TEXT | Назва кафедри |
| `enrolled_at` | DATE | Дата запису |
| `grade` | NUMERIC | Оцінка |
| `status` | VARCHAR | Статус запису |

**Первинний ключ (інтуїтивно):** `(student_id, course_code)`.

### 2.1. Аномалії цього дизайну

1. **Аномалія вставки:** не можна додати нову кафедру без прив'язки хоча б до одного курсу й одного студента. Кафедра, у якій поки нуль курсів, у таблиці не з'явиться.
2. **Аномалія оновлення:** перейменування кафедри «IT» → «Інформатика та технології» потребує оновлення **всіх** рядків, де вона згадується. Якщо хоч один пропустити — отримаємо непослідовність.
3. **Аномалія видалення:** якщо видалити останній запис про кафедру (бо студент її кинув), разом з рядком зникнуть і дані про саму кафедру.
4. **Надлишковість:** назва «Інформаційні технології» повторюється десятки разів для різних курсів і студентів — марнотратство місця й ризик розбіжностей.
5. **Порушення 1НФ:** телефонні номери збережені як єдиний рядок через кому.

## 3. Карта функціональних залежностей

Функціональна залежність `X → Y` означає: якщо знаємо значення `X`, однозначно знаємо `Y`.

### 3.1. ФЗ у предметній області

| № | Залежність | Інтерпретація |
|---|---|---|
| F1 | `student_id → student_name, enrollment_year` | ID студента однозначно визначає його ПІБ і рік вступу. |
| F2 | `student_id → student_phones` (але це **багатозначна** залежність) | Один студент має багато телефонів — спеціальний випадок. |
| F3 | `course_code → course_title, course_credits, course_tuition, department_id` | Код курсу визначає всі його характеристики, включно з кафедрою. |
| F4 | `department_id → department_code, department_name` | ID кафедри визначає її код і назву. |
| F5 | `department_code → department_id, department_name` | Код кафедри теж унікальний, тому визначає ID і назву. |
| F6 | `(student_id, course_code) → enrolled_at, grade, status` | Пара «студент-курс» визначає дату, оцінку, статус. |

### 3.2. Діаграма ФЗ

```
                                        ┌───────────────────┐
                                        │   department_id   │
                                        └─────────┬─────────┘
                                                  │
                                          F4,F5 ─ │ — (code, name)
                                                  │
                                                  ▼
  ┌──────────┐              ┌───────────┐    ┌──────────────┐
  │student_id│ ── F1 ──▶    │ student_* │    │ course_code  │
  └────┬─────┘              └───────────┘    └──────┬───────┘
       │                                            │
       │                                       F3 ─ │ — (title,
       │                                            │     credits,
       │                                            │     tuition,
       │                                            │     dept_id)
       │                                            │
       │   ┌──────────────────────────────┐         │
       └──▶│ (student_id, course_code)    │◀────────┘
           └────────────┬─────────────────┘
                        │
                   F6 ─ │ — (enrolled_at, grade, status)
                        ▼
                  решта атрибутів
```

### 3.3. Кандидатні ключі

Шукаємо мінімальні набори атрибутів, замикання яких дає всі атрибути відношення.

- `{student_id, course_code}⁺ = ВСІ атрибути` (через F1, F3, F4, F6). ✅ Кандидатний ключ.
- `{student_id, course_title}` — ні, бо з `course_title` не вивести `course_code` (назв може бути кілька однакових).
- `{student_name, course_code}` — ні, бо `student_name` не визначає `student_id` однозначно.

**Єдиний кандидатний ключ: `(student_id, course_code)`.** Він же стає первинним ключем.

## 4. Перевірка на 1НФ

### 4.1. Правило 1НФ

Кожна комірка таблиці містить **атомарне (неподільне) значення**; немає списків, повторюваних груп і вкладених структур.

### 4.2. Порушення

Колонка `student_phones` зберігає **список** телефонів через кому:

```
'+380501112233, +380671234567'
```

Це явне порушення — щоб знайти всіх, хто має номер `380501112233`, доведеться робити `LIKE '%…%'`, що повільно й неточно.

### 4.3. Приведення до 1НФ

Виносимо багатозначний атрибут в окрему таблицю:

**`student_phones(student_id, phone)`** — первинний ключ `(student_id, phone)`.

Кожен телефон тепер — окремий рядок. Якщо у студента 2 номери — дві реєстрації в таблиці.

Решта таблиці `enrollment_report` залишається з атомарними колонками — 1НФ виконано.

## 5. Перевірка на 2НФ

### 5.1. Правило 2НФ

Відношення **у 1НФ**, і жоден неключовий атрибут **не залежить частково** від первинного ключа — тобто немає ФЗ, лівою частиною якої є підмножина PK.

### 5.2. Порушення

Первинний ключ: `(student_id, course_code)`. Перевіряємо ФЗ:

- F1: `student_id → student_name, enrollment_year` — **ліва частина F1 — підмножина PK**. ❌ Часткова залежність!
- F3: `course_code → course_title, course_credits, course_tuition, department_id` — **ліва частина F3 — підмножина PK**. ❌ Часткова залежність!

Отже, 2НФ **не виконується**.

### 5.3. Декомпозиція до 2НФ

Виносимо часткові залежності в окремі відношення:

**R1: `students(student_id PK, student_name, enrollment_year)`** — з F1.

**R2: `courses(course_code PK, course_title, course_credits, course_tuition, department_id, department_code, department_name)`** — з F3, разом з даними кафедри поки.

**R3: `enrollments(student_id, course_code, enrolled_at, grade, status)`** з PK `(student_id, course_code)` — з F6.

**R_phones: `student_phones(student_id, phone)`** — залишена з 1НФ.

### 5.4. Безвтратність декомпозиції 2НФ

**Теорема** (безвтратна декомпозиція): декомпозиція `R = R1 ⋈ R2` безвтратна, якщо `R1 ∩ R2` є ключем хоча б одного з `R1, R2`.

- `students ⋈ enrollments` по `student_id`: `student_id` — PK у `students`. ✅
- `courses ⋈ enrollments` по `course_code`: `course_code` — PK у `courses`. ✅

Усі факти з вихідної таблиці відновлюються через JOIN-и. **Декомпозиція безвтратна.**

### 5.5. Збереження залежностей

Усі ФЗ (F1, F3, F6) залишилися всередині якогось з відношень. **Залежності збережені.**

---

## 6. Перевірка на 3НФ

### 6.1. Правило 3НФ

Відношення **у 2НФ**, і для кожної нетривіальної ФЗ `X → A`:

- або `X` — суперключ,
- або `A` — простий атрибут (частина якогось кандидатного ключа).

Якщо є **транзитивна залежність** через неключовий атрибут — порушення 3НФ.

### 6.2. Порушення в R2 (`courses`)

У відношенні `courses(course_code, course_title, course_credits, course_tuition, department_id, department_code, department_name)`:

- PK: `course_code`.
- Є залежність: `department_id → department_code, department_name` (F4).

**`department_id` — не суперключ** у `courses`, а `department_code, department_name` — не прості атрибути (не входять у PK).

Це **транзитивна залежність**:
```
course_code → department_id → department_name
```
➡️ порушення 3НФ.

### 6.3. Декомпозиція до 3НФ

Виносимо `departments` в окреме відношення:

**R4: `departments(department_id PK, department_code UNIQUE, department_name)`** — з F4.

**R2': `courses(course_code PK, course_title, course_credits, course_tuition, department_id FK)`** — залишилися тільки прямі атрибути курсу й FK на кафедру.

### 6.4. Підсумок схеми в 3НФ

| Таблиця | Атрибути | PK |
|---|---|---|
| `students` | `student_id`, `full_name`, `enrollment_year` | `student_id` |
| `student_phones` | `student_id`, `phone` | `(student_id, phone)` |
| `departments` | `department_id`, `code`, `name` | `department_id` |
| `courses` | `course_id`, `code`, `title`, `credits`, `tuition`, `department_id` | `course_id` |
| `enrollments` | `student_id`, `course_id`, `enrolled_at`, `grade`, `status` | `(student_id, course_id)` |

### 6.5. Безвтратність і збереження залежностей

- Кожна декомпозиція робилася вздовж ключа — **безвтратна**.
- Усі ФЗ з вихідної області залишилися в якомусь відношенні — **збережені**.

## 7. Перевірка на BCNF

### 7.1. Правило BCNF

**Для кожної нетривіальної ФЗ `X → Y` у відношенні `X` має бути суперключем.**

Відмінність від 3НФ: BCNF **не має винятку** для простих атрибутів у правій частині.

### 7.2. Перевірка нашої схеми

Проходимо по кожному відношенню і дивимося кожну ФЗ:

- **`students`:** `student_id → …`, `student_id` — PK, суперключ. ✅
- **`departments`:** `department_id → …`, `department_code → …`. Обидва — суперключі. ✅
- **`courses`:** `course_id → …`, `code → …`. Обидва — суперключі. ✅
- **`enrollments`:** `(student_id, course_id) → …`. PK — суперключ. ✅
- **`student_phones`:** `(student_id, phone) → ∅` (нема залежностей, крім тривіальних). ✅

**Схема вже у BCNF** — жодне подальше дроблення не потрібне.

### 7.3. Класичний приклад, де 3НФ ≠ BCNF

Наведемо класичний академічний приклад. Нехай є відношення:

**`advisement(student_id, major_code, advisor_id)`**

Предметна область: студент навчається за кількома спеціальностями; для кожної спеціальності він має одного наукового керівника; кожен керівник спеціалізується на одній спеціальності.

**Функціональні залежності:**

- `F_A: (student_id, major_code) → advisor_id`
- `F_B: advisor_id → major_code`

**Кандидатні ключі:**

- `{student_id, major_code}` ← замикання містить `advisor_id` через F_A.
- `{student_id, advisor_id}` ← замикання містить `major_code` через F_B.

**3НФ-перевірка:**

- F_A: `(student_id, major_code) → advisor_id` — ліва частина суперключ. ✅
- F_B: `advisor_id → major_code` — `advisor_id` не суперключ, але `major_code` **є простим атрибутом** (входить у кандидатний ключ `{student_id, major_code}`). За правилом 3НФ це **прийнятно**. ✅

Отже, відношення у **3НФ**.

**BCNF-перевірка:**

- F_B: `advisor_id → major_code` — `advisor_id` не суперключ. ❌ **Порушення BCNF**.

**Декомпозиція до BCNF:**

```
R1(student_id, advisor_id)
R2(advisor_id, major_code)
```

Безвтратна: `R1 ∩ R2 = {advisor_id}`, що є PK у `R2`. ✅

**АЛЕ** — залежність `F_A: (student_id, major_code) → advisor_id` **втрачається**! Вона розкидана між двома таблицями й більше не виражається одним FD усередині якогось з них. Тепер перевірити правило «у кожного студента для кожної спеціальності рівно один керівник» можна лише кросс-табличним обмеженням.

**Це класична ситуація, коли доводиться обирати:** або 3НФ зі збереженням усіх залежностей, або BCNF із втратою однієї з них. У цьому прикладі зазвичай залишають 3НФ.

## 8. SQL-скрипт нормалізованої схеми

Файл `normalization.sql` містить повний скрипт. Основні таблиці:

```sql
CREATE TABLE college_norm.departments (
    department_id INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code          VARCHAR(10) NOT NULL UNIQUE,
    name          TEXT        NOT NULL
);

CREATE TABLE college_norm.students (
    student_id      INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    full_name       VARCHAR(100) NOT NULL,
    enrollment_year SMALLINT     NOT NULL
);

CREATE TABLE college_norm.student_phones (
    student_id INTEGER     NOT NULL REFERENCES college_norm.students(student_id) ON DELETE CASCADE,
    phone      VARCHAR(20) NOT NULL,
    PRIMARY KEY (student_id, phone)
);

CREATE TABLE college_norm.courses (
    course_id     INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    code          VARCHAR(20)    NOT NULL UNIQUE,
    title         VARCHAR(200)   NOT NULL,
    credits       SMALLINT       NOT NULL CHECK (credits BETWEEN 1 AND 30),
    tuition       NUMERIC(10,2)  NOT NULL CHECK (tuition >= 0),
    department_id INTEGER        NOT NULL REFERENCES college_norm.departments(department_id)
);

CREATE TABLE college_norm.enrollments (
    student_id  INTEGER     NOT NULL REFERENCES college_norm.students(student_id) ON DELETE CASCADE,
    course_id   INTEGER     NOT NULL REFERENCES college_norm.courses(course_id)   ON DELETE RESTRICT,
    enrolled_at DATE        NOT NULL DEFAULT CURRENT_DATE,
    grade       NUMERIC(5,2),
    status      VARCHAR(20) NOT NULL DEFAULT 'active',
    PRIMARY KEY (student_id, course_id)
);
```

Також у скрипті — `INSERT ... SELECT` з `DISTINCT`, що переносить дані з денормалізованої таблиці в нормалізовану структуру, автоматично усуваючи дублікати та розбиваючи список телефонів на окремі рядки через `string_to_array + unnest`.

## 9. Приклад усунення аномалії

### 9.1. Аномалія оновлення у денормалізованій таблиці

Перейменуємо кафедру «IT» на «Інформатика та технології»:

```sql
UPDATE enrollment_report
SET department_name = 'Інформатика та технології'
WHERE department_code = 'IT';
```

У нашому прикладі — **3 рядки** (бо 3 записи студентів на курси IT). У реальній базі з тисячами студентів — тисячі рядків, що означає:

- Велике WAL-логування.
- Ризик неузгодженості, якщо запит пройде частково через збій.
- Якщо хтось пропустить WHERE — зіпсує сусідні кафедри.

### 9.2. Те саме у нормалізованій схемі

```sql
UPDATE college_norm.departments
SET name = 'Інформатика та технології'
WHERE code = 'IT';
```

**Завжди рівно 1 рядок**, незалежно від кількості курсів і студентів, прив'язаних до цієї кафедри. Усі курси й реєстрації автоматично «бачать» нову назву через JOIN.

### 9.3. Інші аномалії, що зникли

| Аномалія | Денормалізовано | Нормалізовано |
|---|---|---|
| **Вставка** нової кафедри без курсів | Неможлива | `INSERT INTO departments ...` — працює |
| **Видалення** останнього курсу кафедри | Втратить відомості про кафедру | `departments` не зачепиться |
| **Оновлення** назви курсу | Кожен рядок з цим курсом | Рівно 1 рядок у `courses` |
| **Додавання** телефону студенту | Переформатувати CSV-рядок | Просто `INSERT INTO student_phones` |

## 10. Відповіді на питання для захисту

### 10.1. У чому різниця між 3НФ і BCNF?

**3НФ** допускає нетривіальну ФЗ `X → A`, якщо:
- `X` — суперключ, **АБО**
- `A` — простий атрибут (частина кандидатного ключа).

**BCNF** є **суворіша**: у кожній нетривіальній ФЗ `X → A` саме `X` повинен бути суперключем. Виняток для простих атрибутів у 3НФ **скасовано**.

**Коротке правило:**

- **3НФ:** суперключі + прості атрибути в правій частині.
- **BCNF:** тільки суперключі в лівій частині.

**Практичний наслідок:** BCNF стріктніша, усуває більше аномалій, але іноді:

- Декомпозиція до BCNF може **втратити залежність** (`(student, major) → advisor` у прикладі §7.3).
- 3НФ завжди можна отримати з **безвтратною декомпозицією зі збереженням усіх залежностей**.

У 99% випадків нормалізація зупиняється на 3НФ. BCNF застосовують, коли анормалії 3НФ (через складені кандидатні ключі з пересічними атрибутами) все ж заважають.

### 10.2. Що таке неключовий детермінант?

**Детермінант** — ліва частина функціональної залежності `X → Y`. Це набір атрибутів, що однозначно визначає інший атрибут.

**Неключовий детермінант** — детермінант, який **не є суперключем** відношення.

**Приклад (денормалізоване enrollment_report):**

- PK: `(student_id, course_code)`.
- ФЗ: `department_id → department_name`.
- `department_id` **не є суперключем** у цій таблиці (не визначає `student_id`, `course_code` тощо).
- Отже, `department_id` — **неключовий детермінант**.

**Чому це важливо:** наявність неключового детермінанта — **ознака порушення 3НФ/BCNF** і сигнал до декомпозиції. Виносимо такий детермінант разом з тим, що він визначає, в окрему таблицю, де він стане первинним ключем.

У прикладі: виніс `department_id, department_name` у таблицю `departments`, де `department_id` став PK — і неключовий детермінант перетворився на справжній ключ.

### 10.3. Коли декомпозиція може втратити залежність?

**Декомпозиція `R → (R1, R2, …)` втрачає залежність `X → Y`**, якщо жодне з отриманих відношень не містить одночасно всі атрибути `X` і `Y`.

**Класичний приклад:** `advisement(student_id, major_code, advisor_id)` з §7.3:

- Залежність `F_A: (student_id, major_code) → advisor_id`.
- При декомпозиції до BCNF:
  - `R1(student_id, advisor_id)`
  - `R2(advisor_id, major_code)`
- У `R1` немає `major_code`. У `R2` немає `student_id`. ❌ Залежність F_A **втрачена**.

**Наслідки втрати:**

- Правило «у кожного студента для кожної спеціальності рівно один керівник» більше не виражається одним FD на одному відношенні.
- Щоб перевірити це правило, доведеться писати складний JOIN-тригер або прикладну логіку.
- Може з'явитися непослідовність: два різні керівники для одного (студент, спеціальність).

**Як перевірити збереження:**

Для кожної ФЗ `X → Y` вихідної області перевірити, чи існує хоча б одне відношення в декомпозиції, що містить усі атрибути `XY`. Якщо так — залежність збережена.

**Теорема (без доведення):** існує алгоритм, який будує для R декомпозицію в **3НФ** зі збереженням усіх залежностей і без втрати даних. Для **BCNF** такого алгоритму немає — доводиться обирати компроміс.

### 10.4. Як перевірити, що декомпозиція безвтратна?

**Правило з'єднання без втрат (lossless-join):**

Декомпозиція `R → (R1, R2)` безвтратна, якщо **перетин атрибутів R1 і R2 є суперключем** хоча б одного з них.

**Формально:** `(R1 ∩ R2) → R1` **або** `(R1 ∩ R2) → R2`.

**Приклад:**

Розкладемо `R(course_code, title, dept_id, dept_name)` з ФЗ:
- `course_code → title, dept_id`
- `dept_id → dept_name`

Декомпозиція:
- `R1(course_code, title, dept_id)`
- `R2(dept_id, dept_name)`

`R1 ∩ R2 = {dept_id}`. Чи `dept_id` — суперключ у `R2`? Так, бо `dept_id → dept_name` (PK у `R2`). ✅ **Безвтратна.**

**Алгоритм перевірки для багатьох відношень** (алгоритм Chase / матричний метод):

1. Будуємо таблицю розміром `n × m`, де `n` — кількість відношень у декомпозиції, `m` — кількість атрибутів вихідного.
2. У клітинку `(i, j)` ставимо `a_j`, якщо атрибут `A_j` є в `R_i`, інакше `b_{ij}`.
3. Застосовуємо кожну ФЗ до таблиці, зрівнюючи рядки, що мають однакові значення в стовпцях лівої частини.
4. Якщо після застосування всіх ФЗ хоча б один рядок має всі `a_j` — декомпозиція безвтратна.

**Практична перевірка на реальних даних:**

```sql
-- Чи при з'єднанні з'являються нові «фантомні» рядки?
SELECT COUNT(*) FROM original_table;
SELECT COUNT(*) FROM R1 JOIN R2 USING (common_key);
```

Якщо кількості рівні — декомпозиція дає той самий набір фактів. Якщо з'являються нові рядки — втрата безвтратності.

## 11. Загальний підсумок декомпозицій

| Крок | Форма | Що зробили | Нові відношення |
|---|---|---|---|
| **0** | — | Денормалізована широка таблиця `enrollment_report` | 1 |
| **1НФ** | Прибрали багатозначний `phones` | Створили `student_phones` | 2 |
| **2НФ** | Прибрали часткові залежності від `student_id` і `course_code` | `students`, `courses` (з dep-даними) | 4 |
| **3НФ** | Прибрали транзитивну залежність через `department_id` | `departments` відокремлено | 5 |
| **BCNF** | Уже виконано на етапі 3НФ (немає неключових детермінантів) | без змін | 5 |

### Переваги фінальної схеми

- **Нема надлишковості:** кожен факт зберігається рівно в одному місці.
- **Нема аномалій:** вставка/оновлення/видалення не зачіпає зайвих рядків.
- **Безвтратна:** оригінальну таблицю можна відновити через JOIN.
- **Усі ФЗ збережено:** правила предметної області виражаються обмеженнями на одному відношенні.
- **Підтримка 1:N і M:N** — стандартними зовнішніми ключами.

### Коли денормалізація виправдана

Нормалізація — за замовчуванням, але бувають випадки, де 3НФ погіршує продуктивність:

- Аналітичні системи (OLAP, data warehouse) часто використовують **star schema** з денормалізованими розмірностями.
- Матеріалізовані уявлення (materialized views) з попередньо обчисленими JOIN-ами.
- Кешовані копії певних даних для швидкого доступу.

Денормалізація — свідомий компроміс: платимо надлишковістю за швидкість. Вона застосовується **після** нормалізації, коли проблеми продуктивності виміряні.

Денормалізація — свідомий крок назад для продуктивності, що робиться після виміряних проблем, а не превентивно.
