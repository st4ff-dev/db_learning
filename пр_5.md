## 2. Встановлення PostgreSQL на macOS

### 2.1. Через Homebrew (рекомендовано)

```bash
# 1. Встановити Homebrew (якщо ще не встановлено)
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"

# 2. Встановити PostgreSQL
brew install postgresql@17

# 3. Запустити сервіс (автозапуск при вході в систему)
brew services start postgresql@17

# 4. Перевірити статус
brew services list | grep postgres
```

Очікуваний вивід:
```
postgresql@17   started   st4ff   ~/Library/LaunchAgents/homebrew.mxcl.postgresql@17.plist
```

### 2.2. Додавання psql до PATH (якщо потрібно)

```bash
echo 'export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"' >> ~/.zshrc
source ~/.zshrc
```

### 2.3. Перевірка встановлення

```bash
# Версія клієнта
psql --version
# → psql (PostgreSQL) 17.2

# Версія сервера
pg_config --version
# → PostgreSQL 17.2

# Підключення суперкористувачем
psql postgres
```

### 2.4. Встановлення пароля суперкористувача

За замовчуванням Homebrew створює суперкористувача з іменем поточного користувача системи (`st4ff`) **без пароля**, покладаючись на peer-автентифікацію через сокет. Для навчальних цілей встановлюємо явний пароль:

```sql
-- Увійшли як psql postgres
ALTER USER st4ff WITH PASSWORD 'your_strong_password';
\q
```

> **Записати пароль суперкористувача:** `your_strong_password` (для навчального середовища).
> У виробництві пароль зберігають у password-менеджері, не в текстовому файлі.

### 2.5. Альтернативний варіант — Postgres.app

Для тих, хто не любить CLI: [https://postgresapp.com](https://postgresapp.com)
Просто завантажити `.dmg`, перетягнути в Applications, натиснути **Initialize**. У меню статус-бару з'явиться слоник і команда `psql` стане доступною.

## 4. Створення ролі користувача

### 4.1. Теорія: роль vs користувач

У PostgreSQL є єдина концепція **роль** (`ROLE`), яка об'єднує і користувачів, і групи. Різниця лише в атрибуті `LOGIN`:

- Роль з атрибутом `LOGIN` — це **користувач** (може підключатися).
- Роль без `LOGIN` — це **група** (використовується для видачі прав декільком користувачам).
- Команди `CREATE USER` і `CREATE ROLE ... LOGIN` — синоніми.

### 4.2. Створення ролі `student` з правом створювати БД

Підключаємось як суперкористувач:

```bash
psql postgres
```

Виконуємо:

```sql
-- Створити роль із логіном, паролем і правом створювати БД
CREATE ROLE student
    WITH LOGIN
         PASSWORD 'student_pass'
         CREATEDB;

-- Перевірити, що роль створена
\du
```

Очікуваний вивід `\du`:

```
                            List of roles
 Role name |                         Attributes
-----------+------------------------------------------------------------
 st4ff     | Superuser, Create role, Create DB, Replication, Bypass RLS
 student   | Create DB
```

### 4.3. Альтернативна команда через CLI

Те саме можна зробити одразу з shell:

```bash
createuser --createdb --pwprompt student
# введіть пароль двічі
```

## 5. Створення бази даних `college`

### 5.1. Через psql

Залишаємось у psql як суперкористувач:

```sql
CREATE DATABASE college
    WITH OWNER     = student
         ENCODING  = 'UTF8'
         LC_COLLATE = 'uk_UA.UTF-8'
         LC_CTYPE   = 'uk_UA.UTF-8'
         TEMPLATE  = template0;

-- Перевірка
\l college
```

Очікуваний вивід `\l college`:

```
                              List of databases
  Name   |  Owner  | Encoding |  Collate    |   Ctype     | Access privileges
---------+---------+----------+-------------+-------------+-------------------
 college | student | UTF8     | uk_UA.UTF-8 | uk_UA.UTF-8 |
```

> **Якщо українська локаль недоступна** — використайте `'C.UTF-8'`:
> ```sql
> CREATE DATABASE college WITH OWNER = student ENCODING = 'UTF8' TEMPLATE = template0;
> ```
> UTF-8 кодування все одно коректно збереже кирилицю; локаль впливає лише на правила сортування рядків.

### 5.2. Через CLI

```bash
createdb -O student -E UTF8 -T template0 college
```

### 5.3. Перевірка кодування

```sql
SELECT datname, pg_encoding_to_char(encoding) AS encoding
FROM pg_database
WHERE datname = 'college';
```

Очікуваний вивід:

```
 datname | encoding
---------+----------
 college | UTF8
```


Промпт зміниться на `college=>` (ознака, що ми не суперкористувач).

Виконуємо перевірочні команди:

```sql

```
**Очікуваний результат:**
```

---------------------------------------------------------------------------------------------------

```

```sql
SELECT current_database();
```
**Очікуваний результат:**
```

------------------

```

```sql
SELECT current_user;
```
**Очікуваний результат:**
```
 current_user
--------------

```

> **📸 СКРІНШОТ 1:** Вікно терміналу з виконаними командами `SELECT version()`, `SELECT current_database()`, `SELECT current_user`.

### 6.2. Підключення через pgAdmin

1. Запустити **pgAdmin 4** → у лівій панелі правою кнопкою на **Servers → Register → Server…**
2. Вкладка **General:** `Name = College Local`
3. Вкладка **Connection:**
   - Host name/address: `localhost`
   - Port: `5432`
   - Maintenance database: `college`
   - Username: `student`
   - Password: `student_pass` (поставити галочку **Save password**)
4. **Save**.
5. У лівому дереві: **Servers → College Local → Databases → college** — база має відкритися.
6. Відкрити **Tools → Query Tool** і виконати ті самі три команди.

> **📸 СКРІНШОТ 2:** pgAdmin з розгорнутим деревом і результатом запитів у Query Tool.

### 6.3. Підключення через DBeaver

1. Запустити **DBeaver** → **Database → New Database Connection** (або `⌘ N`).
2. Обрати **PostgreSQL** → Next.
3. У діалозі:
   - Host: `localhost`
   - Port: `5432`
   - Database: `college`
   - Username: `student`
   - Password: `student_pass`
4. Натиснути **Test Connection** — має з'явитися «Connected».
   - Якщо DBeaver запропонує завантажити драйвер — погодитись.
5. **Finish**.
6. У лівій панелі розгорнути **college → Schemas** — побачите `public` і (після наступного кроку) `college`.
7. Правою кнопкою на базі → **SQL Editor → New SQL script**, виконати три команди.

> **📸 СКРІНШОТ 3:** DBeaver з підключеною базою і результатами запитів у SQL Editor.

## 7. Створення схеми `college`

### 7.1. Теорія: що таке схема

**Схема** — це іменований простір імен усередині бази даних, у якому живуть таблиці, представлення, функції та інші об'єкти. Аналогія: якщо база — це папка-контейнер, то схема — це підпапка всередині неї.

За замовчуванням у кожній новій базі є схема `public`, і всі об'єкти створюються в ній. Власні схеми використовують, щоб:

- **Розділити логічні модулі** системи (наприклад, `sales`, `warehouse`, `hr` в одній базі).
- **Розмежувати права доступу** — різним ролям видати права на різні схеми.
- **Уникнути конфліктів імен** — таблиця `users` може існувати в кількох схемах одночасно.
- **Спростити міграції** — одна схема під dev-дані, інша під тестові.

### 7.2. Створення схеми

У psql (підключені до `college` як `student`):

```sql
CREATE SCHEMA college;
```

**Очікуваний результат:**
```
CREATE SCHEMA
```

### 7.3. Перевірка

```sql
SELECT schema_name
FROM information_schema.schemata
ORDER BY schema_name;
```

**Очікуваний результат:**
```
    schema_name
--------------------
 college
 information_schema
 pg_catalog
 pg_toast
 public
```

Схема `college` з'явилася поряд із системними (`information_schema`, `pg_catalog`, `pg_toast`) та користувацькою `public`.

### 7.4. Встановлення схеми за замовчуванням для сесії

Щоб у кожному запиті не писати `college.table_name`, встановлюємо її в `search_path`:

```sql
-- Для поточної сесії
SET search_path TO college, public;

-- Назавжди для ролі student у цій базі
ALTER ROLE student IN DATABASE college SET search_path TO college, public;
```

Перевіряємо:

```sql
SHOW search_path;
```
**Очікуваний результат:**
```
   search_path
------------------
 college, public
```

> **📸 СКРІНШОТ 4:** Результат виконання `CREATE SCHEMA` і `SELECT schema_name FROM information_schema.schemata`.

## 9. Поширені проблеми та їх розв'язання

| Проблема | Причина | Розв'язання |
|---|---|---|
| `psql: command not found` | Шлях до бінарників не в `PATH` | Додати в `~/.zshrc`: `export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"` |
| `connection refused` | Сервер не запущено | `brew services start postgresql@17` |
| `role "st4ff" does not exist` | Homebrew не створив суперкористувача з іменем системного користувача | `createuser -s st4ff` |
| `password authentication failed` | Неправильний пароль або `pg_hba.conf` вимагає іншого методу | Перевірити пароль; у `pg_hba.conf` замінити `peer` на `md5` і перезапустити сервіс |
| `invalid locale "uk_UA.UTF-8"` | Локаль відсутня в системі | Використати `LC_COLLATE='C.UTF-8'` |
| DBeaver не бачить драйвер | Не завантажено JDBC-драйвер | У майстрі підключення натиснути **Download driver files** |

## 10. Відповіді на питання для захисту

### 10.1. Чим роль відрізняється від користувача?

У PostgreSQL **роль** (`ROLE`) — це єдина концепція, яка охоплює і користувачів, і групи. Поняття «користувач» і «група» з інших СКБД зведено до одного — ролі з різними атрибутами:

- **Користувач** = роль з атрибутом `LOGIN` (може підключатися до сервера).
- **Група** = роль без `LOGIN` (використовується для об'єднання кількох користувачів і масової видачі прав).
- Команди `CREATE USER x` і `CREATE ROLE x LOGIN` — повні синоніми.
- Ролі можуть **належати одна одній** (роль успадковує права від батьківської через `GRANT role_parent TO role_child`), що й дає функціональність груп.
- Інші важливі атрибути ролі: `SUPERUSER`, `CREATEDB`, `CREATEROLE`, `REPLICATION`, `BYPASSRLS`, `CONNECTION LIMIT`.

Отже, «роль» — ширше поняття. «Користувач» — спрощена назва для ролі, яка вміє логінитися.

### 10.2. Що таке схема і навіщо її створювати?

**Схема** — це іменований простір імен усередині бази даних, у якому живуть таблиці, представлення, функції, тригери та послідовності. Повне ім'я об'єкта має формат `database.schema.object` (у SQL пишемо `schema.object`).

Схеми створюють для:

1. **Логічного розділення модулів** однієї системи — наприклад, `sales`, `warehouse`, `hr` окремо.
2. **Розмежування прав доступу** — одна роль має права на `sales`, інша на `warehouse`; SQL-команда `GRANT USAGE ON SCHEMA sales TO role_x`.
3. **Уникнення конфліктів імен** — таблиці `users` можуть співіснувати в різних схемах, бо повні імена різні (`crm.users` і `blog.users`).
4. **Багатокористувацької розробки** — кожен розробник має свою схему для експериментів.
5. **Multi-tenancy** — один сервер обслуговує багатьох клієнтів, кожному — окрема схема.
6. **Міграцій і версіонування** — схема `v1`, `v2` паралельно, перемикання при релізі.

За замовчуванням існує схема `public`. Порядок пошуку задає параметр `search_path`.

### 10.3. Як підключитися до бази через командний рядок?

Через утиліту `psql` із різними варіантами параметрів:

**Повний варіант з усіма параметрами:**
```bash
psql -h localhost -p 5432 -U student -d college
```
де `-h` = хост, `-p` = порт, `-U` = користувач, `-d` = база.

**Коротко через connection URI:**
```bash
psql "postgresql://student:student_pass@localhost:5432/college"
```

**Без явного вказання імені БД (підключиться до бази з іменем користувача):**
```bash
psql -U student
```

**Через змінні середовища:**
```bash
export PGUSER=student
export PGPASSWORD=student_pass
export PGHOST=localhost
export PGDATABASE=college
psql
```

**Корисні внутрішні команди psql:**

| Команда | Дія |
|---|---|
| `\l` | список баз |
| `\c dbname` | переключитися на іншу базу |
| `\dt` | список таблиць поточної схеми |
| `\d tablename` | структура таблиці |
| `\du` | список ролей |
| `\dn` | список схем |
| `\q` | вийти з psql |
| `\?` | довідка |

### 10.4. Яке кодування потрібне для роботи з українським текстом?

**UTF-8 (Unicode)** — єдине правильне кодування для будь-якого сучасного тексту, у тому числі українського. Створюючи базу, явно задаємо:

```sql
CREATE DATABASE college
    WITH ENCODING  = 'UTF8'
         LC_COLLATE = 'uk_UA.UTF-8'
         LC_CTYPE   = 'uk_UA.UTF-8'
         TEMPLATE  = template0;
```

**Чому саме UTF-8:**

- **UTF-8** — універсальне кодування Unicode, яке підтримує усі алфавіти світу (у тому числі українські символи `і`, `ї`, `є`, `ґ`).
- Один символ займає 1–4 байти (ASCII — 1 байт, кирилиця — 2 байти, емодзі — 4 байти).
- **LC_COLLATE** (`uk_UA.UTF-8`) — правила **сортування** українських рядків: `а, б, в… є, ж…` замість `a, b, c… є…` в алфавітному порядку за байтами.
- **LC_CTYPE** (`uk_UA.UTF-8`) — правила визначення типів символів: яка літера велика/мала, що є цифрою тощо.

**Застарілі кодування, яких слід уникати:**

- `KOI8-U`, `Windows-1251`, `CP866` — однобайтові кодування, що працюють тільки з кирилицею; не сумісні з емодзі, іншими алфавітами, сучасними API.
- `LATIN1 / SQL_ASCII` — не містять кирилиці взагалі; при спробі зберегти українське слово або видадуть помилку, або збережуть «кракозябри».

**Правило:** нова база даних сьогодні повинна бути в **UTF-8**, крапка. Будь-яке інше кодування — технічний борг з першого дня.
