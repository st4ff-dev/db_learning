## 2. Багатозначні залежності та 4НФ

### 2.1. Коли нормалізації до BCNF недостатньо

BCNF усуває аномалії, спричинені **функціональними** залежностями. Але існує інший вид аномалій — через **багатозначні залежності** (Multi-Valued Dependencies, **MVD**).

Виникають, коли один атрибут визначає **набір значень** іншого атрибута **незалежно** від третього.

### 2.2. Класичний приклад: фахівець, навички й технології

Нехай є відношення `SPECIALIST_PROFILE`:

| specialist | skill | technology |
|---|---|---|
| Іван | Backend | PostgreSQL |
| Іван | Backend | Redis |
| Іван | DevOps | PostgreSQL |
| Іван | DevOps | Redis |
| Марія | Frontend | React |
| Марія | Frontend | TypeScript |

Правило предметної області:

- Фахівець має **набір навичок** (Backend, DevOps).
- Фахівець знає **набір технологій** (PostgreSQL, Redis).
- Ці два набори **незалежні** — усі навички можна застосувати до всіх відомих технологій.

### 2.3. Що породжує надмірність

Щоб коректно відобразити «Іван знає PostgreSQL і Redis, а також вміє Backend і DevOps», ми змушені зберігати **декартів добуток** — усі можливі комбінації. Це:

- **4 рядки** замість 2 навичок + 2 технологій = 4 фактів.
- При 5 навичках × 10 технологіях — **50 рядків** для однієї людини.
- Додавання нової технології — **стільки нових рядків, скільки навичок**.
- Видалення навички — **треба видалити N рядків** (по одному на кожну технологію).

### 2.4. Формальне визначення MVD

**Багатозначна залежність** `X →→ Y` (читається «X багатозначно визначає Y»):

Для кожного значення `X` існує набір значень `Y`, що **не залежить** від значень інших атрибутів.

У нашому прикладі:

- `specialist →→ skill` (кожному фахівцю відповідає незалежний набір навичок)
- `specialist →→ technology` (кожному фахівцю відповідає незалежний набір технологій)

### 2.5. Правило 4НФ

Відношення **у BCNF**, і для кожної нетривіальної багатозначної залежності `X →→ Y` ліва частина `X` є **суперключем**.

У нашому прикладі `specialist` **не є суперключем** (PK = (specialist, skill, technology)). Тому відношення **порушує 4НФ**.

### 2.6. Декомпозиція до 4НФ

Розкладаємо відношення на **два незалежних** за MVD:

**R1: `SKILLS(specialist, skill)`**

| specialist | skill |
|---|---|
| Іван | Backend |
| Іван | DevOps |
| Марія | Frontend |

**R2: `TECHNOLOGIES(specialist, technology)`**

| specialist | technology |
|---|---|
| Іван | PostgreSQL |
| Іван | Redis |
| Марія | React |
| Марія | TypeScript |

Тепер зберігаємо **2 + 2 + 2 = 6** фактів (а було 4 + 2 = 6 рядків на двох людей, проте в нашому прикладі показано лише 4 для Івана через нестачу місця — реально у BCNF було б **4 (Іван) + 2 (Марія) = 6**).

При розширенні:

- **BCNF-схема:** Іван з 5 навичками і 10 технологіями → **50 рядків**.
- **4НФ-схема:** **5 + 10 = 15 рядків**.

Декомпозиція **безвтратна** (перетин `{specialist}` — суперключ у обох).

## 3. Залежності з'єднання та 5НФ

### 3.1. Коли 4НФ недостатньо

Іноді відношення можна **розкласти лише на 3+ відношень**, не вдвоє. Такі випадки регулює 5НФ через **залежності з'єднання** (Join Dependencies, **JD**).

### 3.2. Приклад: фахівець × технологія × тип проєкту

Розглянемо відношення `ASSIGNMENT(specialist, technology, project_type)` з правилом:

> Фахівець використовує технологію тільки в певних типах проєктів.

**Варіант A** — нема залежності з'єднання:

| specialist | technology | project_type |
|---|---|---|
| Іван | PostgreSQL | API |
| Іван | PostgreSQL | Analytics |
| Марія | React | API |
| Марія | React | Dashboard |

Тут можна виразити трійки лише як є — трійки **довільні**, їх не можна відновити через JOIN двох двійкових відношень.

**Варіант B** — залежність з'єднання існує:

Якщо виконується правило:

> Якщо фахівець знає технологію AND фахівець працював у типі проєкту AND технологія використовується в типі проєкту, то фахівець використовує технологію в цьому типі проєкту.

Тоді з'являється **JD**:

```
*(spec, tech), (spec, proj_type), (tech, proj_type)
```

І відношення можна розкласти на **три** проєкції без втрат:

- `KNOWS(specialist, technology)`
- `WORKS_IN(specialist, project_type)`
- `USED_IN(technology, project_type)`

Оригінальні трійки відновлюються через **тройний JOIN**, і результат збігається з вихідним відношенням. У цьому випадку відношення **має бути декомпозоване** для 5НФ.

### 3.3. Правило 5НФ (Project-Join Normal Form)

Відношення **у 4НФ**, і для кожної нетривіальної залежності з'єднання `*(R1, R2, …, Rn)` кожна `Ri` є суперключем.

### 3.4. Коли JD немає

Якщо у Варіанті A з попереднього пункту трійку `(Іван, PostgreSQL, Analytics)` знаємо з практики, але **з двійкових проєкцій не виводиться автоматично**, що саме Іван робить PostgreSQL в Analytics — JD **відсутня**, і 5НФ **не потрібна**.

У більшості реальних схем 4НФ достатньо. 5НФ застосовується вкрай рідко — переважно у специфічних наукових і планувальних системах.

## 4. Аналіз нашої схеми — чи потрібні 4НФ і 5НФ

Розглянемо наші таблиці з пр_7 — пр_12 (college.*).

### 4.1. Таблиця `student_phones(student_id, phone)`

- Чи є два незалежних набори? **Ні** — лише один атрибут `phone`.
- MVD: `student_id →→ phone` — існує, але ліва частина (`student_id`) **одинока** у відношенні, і `(student_id, phone)` є PK.
- Відношення у **4НФ** — порушень немає.

### 4.2. Таблиця `enrollments(student_id, course_id, enrolled_at, grade, status)`

- Багатозначних залежностей не видно: `enrolled_at`, `grade`, `status` функціонально залежать від PK.
- **4НФ виконано.**

### 4.3. Таблиця `courses(course_id, code, title, credits, tuition, department_id)`

- Усі атрибути функціонально залежать від `course_id` (і від `code` як альтернативного ключа).
- Багатозначних залежностей немає.
- **4НФ виконано.**

### 4.4. Гіпотетичне розширення — коли 4НФ знадобилася б

Уявімо, що ми додали б таблицю:

**`STUDENT_INTERESTS(student_id, hobby, sport)`**

- Студент має кілька хобі (читання, малювання).
- Студент займається кількома видами спорту (теніс, біг).
- Ці набори **незалежні** — усі хобі можна поєднувати з будь-якими видами спорту.

Тоді ми отримали б класичну ситуацію з §2 і довелося б розкласти на `STUDENT_HOBBIES` і `STUDENT_SPORTS`.

У поточній схемі такого **немає** — кожна таблиця містить лише один логічний «аспект» своєї сутності.

### 4.5. 5НФ у нашій схемі

Відсутня потреба. Немає трійок атрибутів з нетривіальною JD. Усі зв'язки описуються парами FK + додаткові атрибути зв'язку (кількість, оцінка, статус).

### 4.6. Висновок про нашу схему

Наша схема перебуває в **4НФ** (і, за §4.5, у 5НФ). Подальша нормалізація не потрібна:

- Жодна таблиця не має двох незалежних багатозначних атрибутів.
- Структура відповідає класичній реляційній моделі з чіткими 1:N і M:N зв'язками.
- Усі аномалії, які можна усунути структурно, усунені на етапі 3НФ/BCNF.

## 5. Денормалізація — гіпотеза для нашої схеми

### 5.1. Який звіт гальмує

**Звіт «Топ курсів за кількістю студентів»** з пр_11 вимагає JOIN трьох таблиць:

```sql
SELECT
    c.code, c.title, d.code AS dep, COUNT(e.student_id) AS students
FROM college.courses c
LEFT JOIN college.enrollments e ON e.course_id = c.course_id
JOIN college.departments d      ON d.department_id = c.department_id
GROUP BY c.course_id, c.code, c.title, d.code
ORDER BY students DESC;
```

На кілька десятків курсів і реєстрацій запит миттєвий. Але якщо виросте до:

- **5 000 курсів**,
- **500 000 активних реєстрацій**,
- звіт запитується **з головної сторінки дашборду** кожні 30 секунд,

— повний скан з агрегацією може зайняти секунди, а в години пік — десятки секунд.

### 5.2. Пропозиція денормалізації

Додаємо **лічильник студентів** прямо в таблицю `courses`:

```sql
ALTER TABLE college.courses
    ADD COLUMN current_students_count INTEGER NOT NULL DEFAULT 0
        CHECK (current_students_count >= 0);
```

Тепер звіт стає тривіальним:

```sql
SELECT code, title, current_students_count
FROM college.courses
ORDER BY current_students_count DESC
LIMIT 10;
```

Запит читає **одну таблицю**, використовує індекс по `current_students_count DESC` — відповідь у мілісекундах незалежно від кількості записів.

### 5.3. Ризики денормалізації

| Ризик | Як проявляється | Як мітигувати |
|---|---|---|
| **Неузгодженість** | `current_students_count` не відповідає реальній кількості в `enrollments` | Тригери AFTER INSERT/UPDATE/DELETE на `enrollments`, що оновлюють лічильник |
| **Складніший код запису** | Треба оновлювати лічильник при кожній зміні запису | Інкапсулювати в тригер — прикладний код не змінюється |
| **Конкуренція** | Паралельні INSERT'и в enrollments блокують `courses` | Використати UPDATE з `WHERE … AND` на level READ COMMITTED |
| **Прихована помилка** | Якщо хтось виконає INSERT напряму в `pg_catalog` або переналаштує тригер — лічильник піде гулять | Регулярна перевірка (CRON-задача) порівнює лічильник із `SELECT COUNT(*)` |
| **Складніший розвиток схеми** | Додавання нового атрибута «кількість активних vs завершених» потребує нового лічильника + тригера | Переосмислити — може, час перейти на матеріалізоване уявлення |

### 5.4. Підтримка узгодженості — тригери

```sql
CREATE OR REPLACE FUNCTION college.trg_update_course_count()
RETURNS TRIGGER AS $$
BEGIN
    IF TG_OP = 'INSERT' THEN
        UPDATE college.courses
        SET current_students_count = current_students_count + 1
        WHERE course_id = NEW.course_id;
    ELSIF TG_OP = 'DELETE' THEN
        UPDATE college.courses
        SET current_students_count = current_students_count - 1
        WHERE course_id = OLD.course_id;
    ELSIF TG_OP = 'UPDATE' AND NEW.course_id <> OLD.course_id THEN
        UPDATE college.courses
        SET current_students_count = current_students_count - 1
        WHERE course_id = OLD.course_id;
        UPDATE college.courses
        SET current_students_count = current_students_count + 1
        WHERE course_id = NEW.course_id;
    END IF;
    RETURN NULL;
END;
$$ LANGUAGE plpgsql;

CREATE TRIGGER tg_sync_course_count
AFTER INSERT OR UPDATE OR DELETE ON college.enrollments
FOR EACH ROW EXECUTE FUNCTION college.trg_update_course_count();
```

### 5.5. Альтернатива: матеріалізоване уявлення

Замість денормалізації колонки можна створити матеріалізоване уявлення:

```sql
CREATE MATERIALIZED VIEW college.course_stats AS
SELECT
    c.course_id, c.code, c.title,
    COUNT(e.student_id) AS students,
    ROUND(AVG(e.grade), 2) AS avg_grade
FROM college.courses c
LEFT JOIN college.enrollments e ON e.course_id = c.course_id
GROUP BY c.course_id, c.code, c.title;

CREATE INDEX idx_course_stats_students ON college.course_stats(students DESC);

-- Оновлення за графіком, наприклад раз на годину:
REFRESH MATERIALIZED VIEW CONCURRENTLY college.course_stats;
```

**Переваги:** оригінальна схема незмінна, статистика ізольована, оновлення планове.
**Недоліки:** дані застарівають між оновленнями; дані дублюються.

## 6. Критерій прийняття рішення про денормалізацію

### 6.1. Трикутник компромісу

```
       Продуктивність
            /\
           /  \
          /    \
Простота ─────  Цілісність
```

Денормалізація посилює **продуктивність**, але послаблює **цілісність** і ускладнює **код**.

### 6.2. Коли денормалізація виправдана

Денормалізувати слід **тільки за наявності виміряних проблем**. Ключові критерії:

1. **Запит вимірюється повільно** — EXPLAIN ANALYZE показує сканування мільйонів рядків, JOIN-и > 100 мс.
2. **Запит виконується часто** — не ad-hoc звіт, а регулярний (кілька разів на секунду / хвилину).
3. **Частка читань переважає над записом** — для нашого випадку: студенти записуються на курси рідко, а звіт переглядається часто. Правило великого пальця: **>10 читань на одне оновлення**.
4. **Фактична проблема, а не припущення** — не денормалізуйте «на всяк випадок», лише коли метрики підтверджують.
5. **Простіших оптимізацій вичерпано** — індекси, партиціювання, кеш запиту, матеріалізовані уявлення вже перевірені.

### 6.3. Коли НЕ слід денормалізувати

- Запит виконується **рідко** (раз на день для звіту менеджера) — досить індексів.
- Дані **часто змінюються** — тригери постійно спрацьовуватимуть, і запис стане повільнішим.
- Прикладна логіка **не терпить затримки консистентності** (фінансові операції, залишки).
- Таблиця **невелика** — JOIN однаково швидкий, витрати не окупляться.
- Інфраструктурою керують **кілька команд** — складність координації перевищить виграш.

### 6.4. Порядок дій

1. **Виміряти** поточний запит: `EXPLAIN (ANALYZE, BUFFERS)`.
2. **Додати індекс** на поля, за якими фільтрує/сортує. Виміряти знову.
3. **Переписати запит** на більш ефективний (наприклад, прибрати зайві JOIN). Виміряти.
4. Якщо проблема не зникла — **матеріалізоване уявлення з плановим REFRESH**.
5. Якщо потрібна миттєва консистентність і matview не підходить — **денормалізація з тригерами**.
6. **Моніторинг:** CRON-задача раз на тиждень порівнює денормалізовану колонку з `COUNT(*)`, попереджає про розбіжності.

### 6.5. Приклад виміру

```sql
-- До денормалізації
EXPLAIN (ANALYZE, BUFFERS)
SELECT c.code, COUNT(e.student_id) AS students
FROM college.courses c
LEFT JOIN college.enrollments e ON e.course_id = c.course_id
GROUP BY c.code
ORDER BY students DESC
LIMIT 10;
-- Execution Time: 143.56 ms на великих даних

-- Після денормалізації
EXPLAIN (ANALYZE, BUFFERS)
SELECT code, current_students_count
FROM college.courses
ORDER BY current_students_count DESC
LIMIT 10;
-- Execution Time: 0.82 ms
-- Виграш: ~170×
```

Якщо запит викликається 10 разів на секунду, економія становить 1.4 с CPU на секунду реального часу — **суттєва для масштабування**.

## 7. Чи потрібні вищі нормальні форми нашій схемі

### Висновок:

| Форма | Потрібно нашій схемі? | Причина |
|---|---|---|
| 1НФ | ✅ так, виконано | атомарні колонки |
| 2НФ | ✅ так, виконано | повні залежності від PK |
| 3НФ | ✅ так, виконано | немає транзитивних залежностей |
| BCNF | ✅ так, виконано | кожен детермінант — суперключ |
| **4НФ** | ✅ **виконано автоматично** | жодне відношення не має двох незалежних багатозначних атрибутів |
| **5НФ** | ✅ **виконано автоматично** | немає нетривіальних залежностей з'єднання |

**4НФ і 5НФ стали непотрібними додатковими кроками**, бо ми ретельно пройшли 3НФ: винесли всі багатозначні факти в окремі таблиці ще на етапі 1НФ (приклад: `student_phones`).

На практиці 4НФ рідко є окремим кроком — вона «виходить сама» з грамотної 3НФ. 5НФ — ще рідше.

## 8. Відповіді на питання для захисту

### 8.1. Чим багатозначна залежність відрізняється від функціональної?

**Функціональна залежність `X → Y`:** значення `X` однозначно визначає **одне значення** `Y`.

Приклад: `student_id → student_name` — у студента з ID=1 рівно одне ПІБ.

**Багатозначна залежність `X →→ Y`:** значення `X` визначає **набір значень** `Y`, причому цей набір **не залежить** від інших атрибутів відношення.

Приклад: `specialist →→ skill` — у фахівця «Іван» є **набір** навичок (Backend, DevOps), і цей набір є таким самим незалежно від того, які технології Іван знає.

| Критерій | ФЗ `X → Y` | MVD `X →→ Y` |
|---|---|---|
| Кардинальність Y | 1 значення | N значень |
| Відношення зі всіма атрибутами | Повне | Декартів добуток незалежних наборів |
| Усувається | Декомпозиція до BCNF | Декомпозиція до 4НФ |
| Символ | `→` (одна стрілка) | `→→` (подвійна) |

**Важливо:** будь-яка ФЗ є часткою MVD (одноелементний набір). MVD — узагальнення ФЗ.

### 8.2. Коли 4НФ необхідна, а коли надмірна?

**4НФ необхідна**, коли у відношенні:

- Є **два або більше** незалежних багатозначних атрибутів.
- Структура провокує зберігання **декартового добутку** їх значень.
- Збільшення одного набору призводить до **каскадного зростання** рядків.

**Приклад, де необхідна:**

- `(співробітник, вільна_мова, роль_у_проєкті)` — мови й ролі незалежні, кожна комбінація зберігається окремо.
- `(лектор, курс_викладає, кафедра_за_сумісництвом)` — курси й кафедри незалежні.

**4НФ надмірна**, коли:

- У відношенні **лише один** багатозначний атрибут.
- Усі «набори» в таблиці пов'язані з рештою через функціональну залежність.
- Нормалізації до 3НФ/BCNF достатньо (і це найчастіший випадок).

**Приклад, де надмірна:**

- `(student_id, phone)` — лише один багатозначний атрибут (phone), 4НФ автоматично виконана.
- `(order_id, product_id, quantity)` — `quantity` функціонально залежить від пари, MVD не виникає.

**Практичне правило:** якщо ви грамотно виконали 3НФ (кожне відношення описує одну сутність або один тип зв'язку), 4НФ зазвичай «виходить сама».

### 8.3. Що означає «свідома денормалізація»?

**Свідома денормалізація** — цілеспрямоване порушення нормальних форм (зазвичай 3НФ) заради **виміряного виграшу у продуктивності**, за умови:

1. **Виміряна проблема.** Денормалізація починається з метрик (EXPLAIN ANALYZE, профілі запитів), а не з інтуїції «це буде повільно».
2. **Чітке обґрунтування.** Задокументовано, який запит прискорюється, наскільки, скільки разів на день він викликається, чому індексів недостатньо.
3. **Контрольовані ризики.** Усі ризики консистентності перераховані й мітиговані (тригери, перевірки, матеріалізовані уявлення).
4. **Механізм підтримки.** Існує автоматичний спосіб підтримати узгодженість — тригери, задачі, refresh materialized view.
5. **Моніторинг.** Регулярна перевірка, що денормалізовані дані дійсно відповідають нормалізованим.
6. **План відкату.** Є план повернення до нормалізованої схеми, якщо виграш не підтвердиться або ризики стануть надмірними.

**Антипаттерн: «несвідома» денормалізація** — коли дублювання виникає спонтанно, без плану («давайте додамо копію назви категорії, щоб не робити JOIN»), без тригерів, без моніторингу. Через кілька місяців дані розходяться й починаються аномалії.

### 8.4. Як зберігати узгодженість за наявності дублювання?

Існує кілька механізмів, від простого до складного:

**1. Тригери на базовій таблиці.**

```sql
CREATE TRIGGER tg_sync_count
AFTER INSERT OR DELETE ON enrollments
FOR EACH ROW EXECUTE FUNCTION trg_update_course_count();
```

- **Переваги:** миттєва консистентність; прикладний код не змінюється.
- **Недоліки:** додаткова робота на кожному INSERT/DELETE; складно дебажити; невидимі для розробника.

**2. Матеріалізовані уявлення з REFRESH.**

```sql
CREATE MATERIALIZED VIEW course_stats AS SELECT ...;
REFRESH MATERIALIZED VIEW CONCURRENTLY course_stats;
```

- **Переваги:** оригінальна схема незмінна; можна планово оновлювати.
- **Недоліки:** дані застарівають між оновленнями; на дуже великих таблицях refresh довгий.

**3. Прикладний рівень.**

```python
# У бізнес-логіці
def enroll_student(student_id, course_id):
    with transaction():
        db.execute("INSERT INTO enrollments ...")
        db.execute("UPDATE courses SET count = count + 1 WHERE course_id = %s", course_id)
```

- **Переваги:** явно у коді, зрозуміло.
- **Недоліки:** будь-який обхід (прямий SQL, інший сервіс, скрипт міграції) зіпсує консистентність.

**4. Періодичне звіряння (reconciliation).**

```sql
-- CRON-задача, раз на годину:
UPDATE courses c SET current_students_count = e.cnt
FROM (SELECT course_id, COUNT(*) AS cnt FROM enrollments GROUP BY course_id) e
WHERE c.course_id = e.course_id
  AND c.current_students_count <> e.cnt;
```

- **Переваги:** виправляє дрейф.
- **Недоліки:** між запусками дані можуть бути неузгодженими.

**5. Event sourcing / CQRS.**

Складна архітектура для великих систем: усі зміни пишуться як events, read-моделі окремо.

**Правило великого пальця:** якщо дублювання критичне (гроші, залишки) — тригери + reconciliation. Якщо не критичне (статистика, лічильники) — матеріалізоване уявлення з REFRESH.

**Найголовніше:** якщо ви зберігаєте однаковий факт у двох місцях, завжди має бути **один «автор правди»** (source of truth), а другий — похідний. Автор правди змінюється прикладним кодом, похідний — автоматично.

## 9. Підсумкова таблиця

| Форма | Критерій | Усуває | Коли нашій схемі потрібна |
|---|---|---|---|
| 1НФ | Атомарні значення | Повторювані групи, списки у клітинках | ✅ виконано |
| 2НФ | Повні залежності від PK | Часткові залежності | ✅ виконано |
| 3НФ | Прямі залежності від PK | Транзитивні залежності | ✅ виконано |
| BCNF | Усі детермінанти — суперключі | Залишкові аномалії через складені ключі | ✅ виконано |
| **4НФ** | Усі MVD — суперключеві | Надмірність через декартів добуток незалежних багатозначних атрибутів | ✅ автоматично (немає двох MVD в одній таблиці) |
| **5НФ** | Усі JD — тривіальні або суперключеві | Залишкові аномалії через залежності з'єднання | ✅ автоматично (немає нетривіальних JD) |

## Висновок

- **4НФ і 5НФ — спеціалізовані форми**, що розв'язують аномалії, недосяжні для BCNF.
- **4НФ необхідна**, коли в одному відношенні є два незалежних багатозначних атрибути — ситуація, яку ми **уникли ще на етапі 1НФ**, винісши `student_phones` в окрему таблицю.
- **5НФ потрібна вкрай рідко** — коли існують нетривіальні залежності з'єднання. У нашій схемі таких немає.
- **Наша схема перебуває у BCNF/4НФ/5НФ автоматично**, бо грамотне 3НФ-проєктування закрило всі потенційні місця порушень.
- **Денормалізація — свідомий крок назад для продуктивності**. Пропозиція додати `current_students_count` до `courses` обґрунтована лише для сценарію з сотнями тисяч реєстрацій і частих звітів; на поточних даних виграш незначний, тому впровадження передчасне.
- **Підтримка консистентності** денормалізованих даних здійснюється через тригери (миттєва узгодженість), матеріалізовані уявлення (планова узгодженість) або бізнес-логіку (менш надійно).

Головне правило: **нормалізуйте за замовчуванням, денормалізуйте за необхідністю й з вимірюванням**. Передчасна денормалізація ускладнює код, збільшує ризики і рідко виправдана до появи реальних виміряних проблем.
