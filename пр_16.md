## 2. Класифікація підзапитів

| Тип | Повертає | Де використовується | Приклад |
|---|---|---|---|
| **Скалярний** | рівно 1 рядок × 1 колонку | там, де очікується одне значення | `WHERE x > (SELECT AVG(y) FROM t)` |
| **Багаторядковий** | N рядків × 1 колонку | з `IN`, `ANY`, `ALL`, `EXISTS` | `WHERE id IN (SELECT ...)` |
| **Багатоколонковий (табличний)** | N рядків × M колонок | у `FROM`, `WITH`, `EXISTS` | `FROM (SELECT ...) t` |
| **Корельований** | залежить від зовнішнього рядка | з `EXISTS`, у SELECT, WHERE | `WHERE EXISTS (SELECT 1 FROM t WHERE t.x = outer.x)` |

**Ключова ознака:**

- **Некорельований** підзапит виконується **один раз** — результат підставляється в зовнішній.
- **Корельований** — виконується **один раз на кожен зовнішній рядок**, бо його умова залежить від поточного рядка.

## 3. Скалярний підзапит

### 3.1. Поведінка

Повертає **одне значення**. Поводиться як константа:

```sql
SELECT ..., (SELECT AVG(x) FROM t) AS avg_x FROM ...;
```

Якщо підзапит повертає **більше одного рядка** — PostgreSQL видає помилку:

```
ERROR: more than one row returned by a subquery used as an expression
```

### 3.2. Курси, дорожчі за середню плату

```sql
SELECT code, title, tuition
FROM college.courses
WHERE tuition > (SELECT AVG(tuition) FROM college.courses)
ORDER BY tuition DESC;
```

**Як працює:**

1. Внутрішній підзапит обчислює середнє — одне число (у нас ≈4280.00).
2. Зовнішній запит фільтрує курси, де `tuition` > 4280.
3. Підзапит виконується **один раз** — оптимізатор кешує результат.

**Очікуваний результат:**

```
 code |     title      | tuition
------+----------------+---------
 ALG  | Алгоритми      | 5200.00
 DB   | Бази даних     | 4500.00
```

### 3.3. Скалярний у списку SELECT

```sql
SELECT code, tuition,
       tuition - (SELECT AVG(tuition) FROM college.courses) AS diff
FROM college.courses;
```

Підзапит обчислюється **раз**, значення використовується у кожному рядку.

### 3.4. Важлива пастка

```sql
-- НЕБЕЗПЕЧНО: підзапит може повернути >1 рядка
SELECT * FROM students WHERE student_id = (
    SELECT student_id FROM enrollments WHERE grade >= 90
);
```

Якщо студентів з оцінкою ≥90 кілька — помилка. Правильно: `IN` замість `=`.

## 4. Багаторядковий підзапит з IN

### 4.1. Поведінка

Повертає список значень, перевіряється включення зовнішньої колонки:

```sql
WHERE col IN (SELECT ... FROM ...)
-- Еквівалент: col = ANY (...)
```

### 4.2. Студенти на курсах з > 4 кредитами

```sql
SELECT DISTINCT s.student_number, s.full_name
FROM college.students s
WHERE s.student_id IN (
    SELECT e.student_id FROM college.enrollments e
    WHERE e.course_id IN (
        SELECT course_id FROM college.courses WHERE credits > 4
    )
)
ORDER BY s.full_name;
```

**Логіка:** внутрішній знаходить ID курсів із credits > 4; середній — ID студентів, записаних на ці курси; зовнішній — самих студентів.

### 4.3. NOT IN — пастка з NULL

```sql
-- Знайти курси, на які НІХТО не записаний
SELECT code FROM college.courses
WHERE course_id NOT IN (
    SELECT course_id FROM college.enrollments
);
```

**Проблема:** якщо `enrollments.course_id` містить NULL хоча б в одному рядку, **весь NOT IN** повертає FALSE для всіх зовнішніх рядків. Логіка SQL: `x NOT IN (a, b, NULL)` = `x <> a AND x <> b AND x <> NULL`, остання частина — NULL, і весь AND стає NULL/FALSE.

**Безпечний варіант:** `NOT EXISTS` (див. §5) або явний `WHERE course_id IS NOT NULL` у підзапиті:

```sql
WHERE course_id NOT IN (
    SELECT course_id FROM college.enrollments WHERE course_id IS NOT NULL
)
```

## 5. ANY і ALL

### 5.1. Семантика

- `x > ANY (SELECT y FROM t)` — TRUE, якщо x більше **хоча б одного** значення y. Еквівалент: `x > MIN(y)`.
- `x > ALL (SELECT y FROM t)` — TRUE, якщо x більше **всіх** значень y. Еквівалент: `x > MAX(y)`.
- `x = ANY (...)` — еквівалент `x IN (...)`.
- `x <> ALL (...)` — еквівалент `x NOT IN (...)`.

### 5.2. Курси з credits > ANY (курси фізики)

```sql
SELECT code, title, credits FROM college.courses
WHERE credits > ANY (
    SELECT credits FROM college.courses
    WHERE department_id = (SELECT department_id FROM college.departments WHERE code = 'FIZ')
);
```

Якщо у фізики є курси з 4 кредитами — умова `credits > ANY (4)` виконується для 5 і 6.

### 5.3. Курси з credits > ALL (курси фізики)

```sql
SELECT code, title, credits FROM college.courses
WHERE credits > ALL (
    SELECT credits FROM college.courses
    WHERE department_id = (SELECT department_id FROM college.departments WHERE code = 'FIZ')
);
```

Якщо максимальний курс фізики — 4 кредити, умова `> ALL (4)` виконується лише для курсів з 5+ кредитами.

### 5.4. Еквівалент через MIN/MAX

```sql
-- ANY ≡ > MIN
SELECT code FROM courses
WHERE credits > (SELECT MIN(credits) FROM courses WHERE department_id = 2);

-- ALL ≡ > MAX
SELECT code FROM courses
WHERE credits > (SELECT MAX(credits) FROM courses WHERE department_id = 2);
```

Часто оптимізатор робить таку заміну автоматично, бо `MIN/MAX` ефективніші за ANY/ALL.

### 5.5. Коли ANY/ALL зручніші

- Коли лівою частиною є **не стандартна** колонка, а вираз: `name <> ALL (SELECT ...)`.
- Коли треба **все або жоден** через `= ALL` / `<> ALL`.
- У більшості випадків MIN/MAX або IN читабельніші.

## 6. Корельовані підзапити з EXISTS

### 6.1. Семантика

**Корельований підзапит** посилається на колонки зовнішнього запиту:

```sql
SELECT ... FROM outer o
WHERE EXISTS (
    SELECT 1 FROM inner i WHERE i.x = o.x   ← кореляція!
);
```

Виконується **один раз на кожен рядок** `outer`. У кожній ітерації `o.x` — поточне значення.

**EXISTS:** TRUE, якщо підзапит повертає хоч один рядок. Не важливо, який рядок — тому пишуть `SELECT 1`.

### 6.2. Кафедри з курсами, на які є реєстрації

```sql
SELECT d.code, d.name
FROM college.departments d
WHERE EXISTS (
    SELECT 1 FROM college.courses c
    WHERE c.department_id = d.department_id
      AND EXISTS (
          SELECT 1 FROM college.enrollments e
          WHERE e.course_id = c.course_id
      )
);
```

**Як працює:** для кожної кафедри перевіряємо, чи знайдеться курс цієї кафедри, на який записано хоч одного студента.

### 6.3. NOT EXISTS — безпечна альтернатива NOT IN

```sql
SELECT c.code, c.title FROM college.courses c
WHERE NOT EXISTS (
    SELECT 1 FROM college.enrollments e
    WHERE e.course_id = c.course_id
);
```

Повертає курси, на які **ніхто не записаний**. На відміну від `NOT IN`, коректно обробляє NULL.

### 6.4. EXISTS vs IN — коли що швидше

| Критерій | IN | EXISTS |
|---|---|---|
| Поведінка | матеріалізує список | short-circuit на першому матчі |
| Швидкість на малих даних | швидко | трохи швидше |
| Швидкість на великих даних | може бути повільніше | **зазвичай швидше** |
| NULL у підзапиті | ризиковано для NOT IN | коректно |
| Корельованість | може бути як не-корельованим, так і корельованим | зазвичай корельований |

**Правило:** якщо не впевнені — EXISTS. Він безпечніший з NULL і майже завжди не повільніший.

## 7. Підзапит у FROM — похідна таблиця

### 7.1. Поведінка

Підзапит у `FROM` поводиться як **тимчасова таблиця**. Їй обов'язково треба дати псевдонім.

### 7.2. Статистика по кафедрах через per-course агрегат

```sql
SELECT d.code, d.name,
       COUNT(*) AS courses_cnt,
       SUM(cs.students) AS total_students,
       ROUND(AVG(cs.avg_grade), 2) AS avg_dept_grade
FROM college.departments d
JOIN (
    SELECT c.course_id, c.department_id,
           COUNT(e.student_id) AS students,
           AVG(e.grade)        AS avg_grade
    FROM college.courses c
    LEFT JOIN college.enrollments e ON e.course_id = c.course_id
    GROUP BY c.course_id, c.department_id
) cs USING (department_id)
GROUP BY d.code, d.name;
```

**Навіщо:** SQL не дозволяє «вкладені агрегати» (`AVG(COUNT(*))`). Треба спочатку зробити агрегат нижнього рівня, потім агрегат вищого.

### 7.3. Еквівалентна форма — CTE (`WITH`)

```sql
WITH course_stats AS (
    SELECT c.course_id, c.department_id,
           COUNT(e.student_id) AS students,
           AVG(e.grade)        AS avg_grade
    FROM college.courses c
    LEFT JOIN college.enrollments e USING (course_id)
    GROUP BY c.course_id, c.department_id
)
SELECT d.code, d.name, SUM(cs.students) AS total_students
FROM college.departments d
JOIN course_stats cs USING (department_id)
GROUP BY d.code, d.name;
```

**Переваги CTE:**

- Читається зверху вниз.
- Можна посилатися на CTE кілька разів у головному запиті.
- Підтримує **рекурсію** (`WITH RECURSIVE`) для ієрархічних даних.

## 8. Підзапит vs JOIN — порівняння на прикладі

**Задача:** знайти студентів, зареєстрованих на курс `DB`.

### 8.1. Через IN

```sql
SELECT s.student_number, s.full_name
FROM college.students s
WHERE s.student_id IN (
    SELECT e.student_id FROM college.enrollments e
    JOIN college.courses c USING (course_id)
    WHERE c.code = 'DB'
);
```

### 8.2. Через JOIN

```sql
SELECT DISTINCT s.student_number, s.full_name
FROM college.students s
JOIN college.enrollments e ON e.student_id = s.student_id
JOIN college.courses     c ON c.course_id  = e.course_id
WHERE c.code = 'DB';
```

### 8.3. Через EXISTS

```sql
SELECT s.student_number, s.full_name
FROM college.students s
WHERE EXISTS (
    SELECT 1 FROM college.enrollments e
    JOIN college.courses c USING (course_id)
    WHERE e.student_id = s.student_id AND c.code = 'DB'
);
```

### 8.4. Таблиця порівняння

| Критерій | IN | JOIN | EXISTS |
|---|---|---|---|
| **Результат** | однаковий | однаковий | однаковий |
| **Потребує DISTINCT** | ні (semi-join) | так (через множення) | ні |
| **Читабельність** | природно для «входить у список» | природно для «розширити даними» | «чи існує» |
| **Швидкість на малому** | схоже | схоже | схоже |
| **Швидкість на великому** | помірно | гарно при наявності індексів | гарно (short-circuit) |
| **Поведінка з NULL** | OK для IN, проблеми для NOT IN | OK | завжди OK |
| **Повертає дані з right-таблиці** | ні | **так** | ні |

### 8.5. Коли що обирати

- **JOIN** — якщо потрібні **колонки з обох таблиць** у вихідному наборі.
- **IN** — коли «просто перевірити, чи входить», без потреби в даних з іншої таблиці.
- **EXISTS** — коли потрібна перевірка існування, особливо з корельованою умовою.

**Правило:** якщо з іншої таблиці нічого не виводите — не робіть JOIN, зайве множення зайве.

### 8.6. План виконання

Сучасні оптимізатори (PostgreSQL 10+) **розпізнають еквівалентні форми** й часто виконують їх однаково. Різниця може проявлятися лише в екзотичних випадках (кореляції, NULL, складні умови).

## 9. Корельований підзапит у SELECT-списку

```sql
SELECT c.code, c.title,
       (SELECT COUNT(*) FROM college.enrollments e
        WHERE e.course_id = c.course_id) AS enrolled_cnt,
       (SELECT ROUND(AVG(e.grade),2) FROM college.enrollments e
        WHERE e.course_id = c.course_id AND e.grade IS NOT NULL) AS avg_grade
FROM college.courses c;
```

Для кожного рядка `c` виконується **2 корельовані підзапити**.

**Переваги:**

- Читається природно: «візьми курс і одразу покажи його метрики».
- Якщо колонок-агрегатів багато — не потрібно додавати їх у `GROUP BY`.

**Недоліки:**

- **Повільно на великих даних** — N курсів × 2 підзапити = 2N звернень до `enrollments`.
- Альтернатива: `LEFT JOIN + GROUP BY` — один прохід.

Оптимізатор PostgreSQL може перетворити такий запит у JOIN, але не завжди.

## 10. Відповіді на питання для захисту

### 10.1. Чим скалярний підзапит відрізняється від багаторядкового?

**Скалярний** повертає **рівно 1 рядок × 1 колонку** — одне значення. Використовується там, де очікується константа:

```sql
WHERE price > (SELECT AVG(price) FROM products)   -- OK
SELECT ..., (SELECT COUNT(*) FROM t) AS cnt       -- OK
```

**Багаторядковий** повертає **список** значень або повну таблицю. Використовується з конструкціями, що розуміють список:

```sql
WHERE id IN (SELECT id FROM ...)
WHERE EXISTS (SELECT 1 FROM ...)
FROM (SELECT ... FROM ...) t
```

**Приклад помилки:**

```sql
-- Якщо курсів з credits=5 кілька — помилка
SELECT * FROM courses WHERE course_id = (SELECT course_id FROM courses WHERE credits = 5);
```

**Виправлення:**
```sql
SELECT * FROM courses WHERE course_id IN (SELECT course_id FROM courses WHERE credits = 5);
```

### 10.2. Що відбувається, якщо скалярний підзапит повертає кілька рядків?

**PostgreSQL видає помилку виконання:**

```
ERROR: more than one row returned by a subquery used as an expression
```

Запит **повністю відхиляється**. Нічого не виконується, транзакція (якщо є) може бути відкочена.

**Чому так:** SQL-семантика очікує скалярний результат у контексті, де є `=`, `>`, `<`, арифметика тощо. `x > (щось)` вимагає, щоб `щось` було одним значенням, бо `x > {5, 7, 9}` не визначено.

**Два винятки:**

- **Порожній результат (0 рядків):** підзапит повертає **NULL**. Тоді `x > NULL` дає NULL → фільтр відхиляє рядок.
- **1 рядок, NULL-значення:** просто NULL. Так само `x > NULL` → NULL.

**Захист:**

1. Переконатись, що внутрішній запит завжди повертає 1 рядок (`LIMIT 1`, агрегат).
2. Використовувати `IN`, `ANY`, `ALL`, `EXISTS` — вони очікують множину.
3. Для обов'язково одного рядка — `SELECT MAX(...)` або `SELECT ... LIMIT 1`.

### 10.3. Коли доцільний EXISTS замість IN?

**EXISTS краще за IN у кількох випадках:**

**1. При роботі з NULL.** NOT IN ламається, якщо підзапит повертає NULL. NOT EXISTS працює коректно.

**2. На великих даних — часто швидше.** EXISTS має **short-circuit семантику**: зупиняється на першому знайденому рядку. IN зазвичай матеріалізує весь список.

**3. Коли підзапит корельований.** `EXISTS (SELECT 1 FROM t WHERE t.x = outer.x)` — природна форма. IN з кореляцією виглядає штучно.

**4. Коли потрібна лише перевірка існування.** Не важливий сам результат — важливий факт наявності. `EXISTS` явно передає цей намір.

**IN краще, коли:**

- Список маленький і некорельований: `WHERE status IN ('new', 'active')`.
- Явно потрібна «перевірка на список значень».
- Читабельність важливіша за оптимізацію на мікрорівні.

**Правило:** якщо не впевнені і дані великі — EXISTS. На малих обох варіантах оптимізатор видасть той самий план.

### 10.4. Чому корельований підзапит виконується для кожного зовнішнього рядка?

Бо він **залежить від поточного зовнішнього рядка**:

```sql
SELECT ... FROM outer o
WHERE EXISTS (
    SELECT 1 FROM inner i WHERE i.x = o.x   -- o.x — поточний рядок!
);
```

Без значення `o.x` підзапит не можна виконати — він не самостійний. Тому для кожного рядка `o` підзапит виконується **з підставленим `o.x`**.

**Обчислювальна складність:** якщо outer має N рядків, а inner — M, корельований підзапит робить до **N × M** звернень. На малих даних непомітно; на мільйонах — катастрофа.

**Оптимізація оптимізатором:**

PostgreSQL часто **перетворює корельований EXISTS у semi-join**, що фактично є ефективним JOIN'ом. Тоді складність стає O(N + M) замість O(N × M). Перевірити можна через `EXPLAIN`:

```
Hash Semi Join  (cost=... rows=...)
```

— знак, що оптимізатор зробив цю оптимізацію.

**Коли не оптимізується:**

- Коли підзапит має несхожі на JOIN умови (LATERAL, аналітичні функції, складні умови).
- Коли корельований підзапит у SELECT-списку з агрегатами.

**Правило:** якщо запит з корельованим підзапитом помітно повільний — переписати як JOIN + GROUP BY. Зазвичай пришвидшує у десятки разів.

## 11. Шпаргалка «коли який підзапит»

| Задача | Форма |
|---|---|
| Фільтр за одним обчисленим значенням | Скалярний: `WHERE x > (SELECT AVG(y) FROM t)` |
| Фільтр за списком | `IN (SELECT ...)` або `EXISTS` |
| Заперечення зі NULL | `NOT EXISTS` (не `NOT IN`) |
| Порівняння з мінімумом/максимумом | `> ALL (...)` або `> (SELECT MAX ...)` |
| Перевірка наявності | `EXISTS (SELECT 1 FROM ...)` |
| Множник ряду (попередня агрегація) | Підзапит у FROM або CTE |
| Багаторазове посилання на проміжний запит | CTE (`WITH`) |
| Колонка з іншої таблиці | **JOIN**, не підзапит |

---

## Висновок

- **Скалярні підзапити** — повертають одне значення, підставляються як константа; помилка при кількох рядках.
- **Багаторядкові** (IN, ANY, ALL) — список значень; `NOT IN` небезпечний з NULL.
- **EXISTS** — найпотужніший для перевірки існування, безпечний з NULL, часто швидший.
- **Корельовані** — залежать від зовнішнього рядка; у кращих випадках оптимізатор перетворює в semi-join.
- **Підзапит у FROM** — похідна таблиця для попередньої агрегації, альтернатива — CTE.
- **Підзапит vs JOIN** — JOIN якщо потрібні колонки іншої таблиці; IN/EXISTS якщо лише перевірка.
- **CTE (WITH)** — зручніша форма підзапиту у FROM, підтримує рекурсію.

Підзапити разом з JOIN і агрегатами — ядро аналітичних запитів у SQL. Наступний крок — **віконні функції** (`OVER`, `PARTITION BY`, `ROW_NUMBER`, `LAG/LEAD`), що дають аналітичну силу без втрати рядків при агрегації.
