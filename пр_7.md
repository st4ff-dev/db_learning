# Практична робота №7: Визначення схем у SQL / DDL

## Мета

Опанувати мову **DDL** (Data Definition Language) PostgreSQL: створення таблиць, доменів, обмежень цілісності (`PRIMARY KEY`, `FOREIGN KEY`, `UNIQUE`, `CHECK`, `NOT NULL`), а також усвідомлений вибір типів даних.

## 1. Логічна модель

Робота №7 розширює базу `college` чотирма пов'язаними таблицями, що моделюють **навчальний процес**:

```
┌──────────────┐          ┌──────────────┐
│ departments  │─ 1:N ───▶│   courses    │
│ (кафедри)    │          │ (дисципліни) │
└──────────────┘          └──────┬───────┘
                                 │
                                 │ M:N
                                 ▼
┌──────────────┐          ┌──────────────┐
│   students   │─ M:N ───▶│ enrollments  │
│ (студенти)   │          │(записи на курс)│
└──────────────┘          └──────────────┘
```

| Таблиця | Призначення |
|---|---|
| `departments` | Кафедри навчального закладу |
| `courses` | Дисципліни, кожна належить кафедрі |
| `students` | Студенти |
| `enrollments` | Запис студента на курс з оцінкою (розв'язання M:N) |

## 2. SQL-скрипт `schema.sql`

Скрипт створює схему з нуля: спочатку видаляє старі таблиці (якщо є), потім створює нові у правильному порядку залежностей.

```sql
-- =========================================================
-- schema.sql — визначення схеми college.*
-- СКБД: PostgreSQL 14+
-- Автор: student
-- =========================================================

-- Підключаємось до бази college та працюємо у схемі college
SET search_path TO college, public;

-- ---------- Очищення (DROP у зворотному порядку залежностей) ----------
DROP TABLE IF EXISTS college.enrollments CASCADE;
DROP TABLE IF EXISTS college.courses     CASCADE;
DROP TABLE IF EXISTS college.students    CASCADE;
DROP TABLE IF EXISTS college.departments CASCADE;

-- =========================================================
-- 1. departments — кафедри
-- =========================================================
CREATE TABLE college.departments (
    department_id INTEGER GENERATED ALWAYS AS IDENTITY,
    code          VARCHAR(10) NOT NULL,
    name          TEXT        NOT NULL,

    CONSTRAINT pk_departments        PRIMARY KEY (department_id),
    CONSTRAINT uq_departments_code   UNIQUE      (code),
    CONSTRAINT ck_departments_code_len
        CHECK (LENGTH(code) BETWEEN 2 AND 10)
);

COMMENT ON TABLE  college.departments IS 'Кафедри навчального закладу';
COMMENT ON COLUMN college.departments.code IS 'Коротка абревіатура, напр. CS, MATH';

-- =========================================================
-- 2. students — студенти
-- =========================================================
CREATE TABLE college.students (
    student_id      INTEGER     GENERATED ALWAYS AS IDENTITY,
    student_number  VARCHAR(20) NOT NULL,
    full_name       VARCHAR(100) NOT NULL,
    email           VARCHAR(100),
    birth_date      DATE,
    enrollment_year SMALLINT    NOT NULL,

    CONSTRAINT pk_students                    PRIMARY KEY (student_id),
    CONSTRAINT uq_students_student_number     UNIQUE      (student_number),
    CONSTRAINT uq_students_email              UNIQUE      (email),
    CONSTRAINT ck_students_enrollment_year
        CHECK (enrollment_year BETWEEN 1990 AND 2100),
    CONSTRAINT ck_students_email_format
        CHECK (email IS NULL OR email LIKE '%@%.%')
);

COMMENT ON TABLE college.students IS 'Студенти коледжу';

-- =========================================================
-- 3. courses — навчальні дисципліни
-- =========================================================
CREATE TABLE college.courses (
    course_id     INTEGER        GENERATED ALWAYS AS IDENTITY,
    code          VARCHAR(20)    NOT NULL,
    title         VARCHAR(200)   NOT NULL,
    department_id INTEGER        NOT NULL,
    credits       SMALLINT       NOT NULL,
    tuition       NUMERIC(10, 2) NOT NULL DEFAULT 0.00,

    CONSTRAINT pk_courses               PRIMARY KEY (course_id),
    CONSTRAINT uq_courses_code          UNIQUE      (code),
    CONSTRAINT fk_courses_department
        FOREIGN KEY (department_id)
        REFERENCES college.departments (department_id)
        ON DELETE RESTRICT
        ON UPDATE CASCADE,
    CONSTRAINT ck_courses_credits       CHECK (credits BETWEEN 1 AND 30),
    CONSTRAINT ck_courses_tuition       CHECK (tuition >= 0)
);

COMMENT ON TABLE  college.courses IS 'Навчальні дисципліни';
COMMENT ON COLUMN college.courses.credits IS 'Кількість кредитів ECTS (1..30)';
COMMENT ON COLUMN college.courses.tuition IS 'Плата за навчання, грн';

-- =========================================================
-- 4. enrollments — записи на курс (M:N students ↔ courses)
-- =========================================================
CREATE TABLE college.enrollments (
    student_id  INTEGER        NOT NULL,
    course_id   INTEGER        NOT NULL,
    enrolled_at DATE           NOT NULL DEFAULT CURRENT_DATE,
    grade       NUMERIC(5, 2),
    status      VARCHAR(20)    NOT NULL DEFAULT 'active',

    CONSTRAINT pk_enrollments
        PRIMARY KEY (student_id, course_id),
    CONSTRAINT fk_enrollments_student
        FOREIGN KEY (student_id)
        REFERENCES college.students (student_id)
        ON DELETE CASCADE,
    CONSTRAINT fk_enrollments_course
        FOREIGN KEY (course_id)
        REFERENCES college.courses (course_id)
        ON DELETE RESTRICT,
    CONSTRAINT ck_enrollments_grade
        CHECK (grade IS NULL OR grade BETWEEN 0 AND 100),
    CONSTRAINT ck_enrollments_status
        CHECK (status IN ('active', 'completed', 'dropped', 'failed'))
);

COMMENT ON TABLE  college.enrollments IS 'Записи студентів на курси';
COMMENT ON COLUMN college.enrollments.grade IS 'Підсумкова оцінка 0..100; NULL — ще не виставлена';

-- ---------- Індекси для прискорення типових запитів ----------
CREATE INDEX idx_courses_department  ON college.courses (department_id);
CREATE INDEX idx_enrollments_course  ON college.enrollments (course_id);
CREATE INDEX idx_students_year       ON college.students (enrollment_year);

-- ---------- Тестові дані для перевірки ----------
INSERT INTO college.departments (code, name) VALUES
    ('CS',   'Комп''ютерні науки'),
    ('MATH', 'Математика'),
    ('PHYS', 'Фізика');

INSERT INTO college.students (student_number, full_name, email, birth_date, enrollment_year) VALUES
    ('ST-2024-001', 'Петренко Олег Іванович',  'petrenko@college.ua',  '2005-03-12', 2024),
    ('ST-2024-002', 'Іваненко Марія Сергіївна', 'ivanenko@college.ua', '2005-07-08', 2024),
    ('ST-2023-017', 'Коваль Назар Петрович',    'koval@college.ua',    '2004-11-22', 2023);

INSERT INTO college.courses (code, title, department_id, credits, tuition) VALUES
    ('CS101', 'Основи баз даних', 1, 5, 4500.00),
    ('CS102', 'Алгоритми',        1, 6, 5000.00),
    ('MATH201', 'Дискретна математика', 2, 4, 3800.00);

INSERT INTO college.enrollments (student_id, course_id, grade, status) VALUES

    (2, 1, NULL, 'active'),
```

## 3. Пояснення вибору типів даних

### 3.1. Загальні принципи

| Принцип | Пояснення |
|---|---|
| **Найвужчий тип, що покриває діапазон** | SMALLINT замість INTEGER, якщо значення ≤ 32767; економія пам'яті та кешу. |
| **Фіксована точність для грошей** | NUMERIC/DECIMAL замість REAL/DOUBLE — уникаємо помилок округлення. |
| **VARCHAR з явною довжиною для кодів** | Код факультету чи артикул мають стабільну довжину; обмеження додає захист. |
| **TEXT для довільного рядка** | Назва кафедри чи заголовок курсу — довільна довжина, PostgreSQL зберігає ефективно. |
| **DATE замість TIMESTAMP, коли час не потрібен** | Дата народження, дата запису на курс — тільки календар. |
| **IDENTITY замість SERIAL** | Стандартний SQL-синтаксис, безпечніший за SERIAL (не дозволяє вручну вставити значення). |

### 3.2. `departments`

| Колонка | Тип | Чому саме цей тип |
|---|---|---|
| `department_id` | **INTEGER IDENTITY** | Сурогатний PK. INTEGER (4 байти) покриває до 2.1 млрд записів — з надлишком. IDENTITY гарантує, що значення призначає тільки СКБД. |
| `code` | **VARCHAR(10)** | Короткий код (CS, MATH, PHYS). Фіксована верхня межа запобігає випадковим довгим рядкам. |
| `name` | **TEXT** | Повна назва кафедри може бути різної довжини. У PostgreSQL TEXT і VARCHAR зберігаються однаково ефективно, але TEXT не накладає зайвого обмеження. |

### 3.3. `students`

| Колонка | Тип | Чому саме цей тип |
|---|---|---|
| `student_id` | **INTEGER IDENTITY** | Внутрішній ключ — так само, як у `departments`. |
| `student_number` | **VARCHAR(20)** | Бізнес-ідентифікатор формату `ST-2024-001` — обмежена довжина. |
| `full_name` | **VARCHAR(100)** | ПІБ практично не перевищує 100 символів навіть з по батькові. |
| `email` | **VARCHAR(100)** | RFC 5321 обмежує email до 254 символів, але реальні значення коротші. |
| `birth_date` | **DATE** | Час не потрібен — лише календарна дата. |
| `enrollment_year` | **SMALLINT** | Рік вступу — ціле число до ≈2100. SMALLINT (2 байти) замість INTEGER (4 байти) економить пам'ять удвічі. |

### 3.4. `courses`

| Колонка | Тип | Чому саме цей тип |
|---|---|---|
| `course_id` | **INTEGER IDENTITY** | Сурогатний ключ. |
| `code` | **VARCHAR(20)** | Код курсу (CS101, MATH201). |
| `title` | **VARCHAR(200)** | Назва дисципліни з розумною межею. |
| `department_id` | **INTEGER** | Зовнішній ключ має той самий тип, що й PK `departments.department_id`. |
| `credits` | **SMALLINT** | За завданням `BETWEEN 1 AND 30`. SMALLINT (діапазон -32768..32767) — з величезним запасом. |
| `tuition` | **NUMERIC(10, 2)** | **Гроші** вимагають точної десяткової арифметики. 10 знаків, 2 після коми — до 99 999 999.99 грн. REAL/DOUBLE ніколи не використовують для сум. |

### 3.5. `enrollments`

| Колонка | Тип | Чому саме цей тип |
|---|---|---|
| `student_id` | **INTEGER** | FK такого ж типу, як PK у `students`. Разом з `course_id` утворює **складений PK**. |
| `course_id` | **INTEGER** | FK до `courses`. |
| `enrolled_at` | **DATE** | Дата запису. `DEFAULT CURRENT_DATE` автоматизує заповнення. |
| `grade` | **NUMERIC(5, 2)** | Оцінка 0.00–100.00. Точно 5 знаків — три до коми плюс два після. NULL дозволений (оцінка ще не виставлена). |
| `status` | **VARCHAR(20)** | Статус запису. Обмежено CHECK до 4 значень; альтернатива — створити справжній ENUM-тип. |

### 3.6. Чому не BIGINT / REAL / DOUBLE

| Відхилений тип | Чому | Коли все ж доречний |
|---|---|---|
| **BIGINT** (8 байт) | Витрачає зайві 4 байти на запис. Для коледжу з тисячами студентів INTEGER вистачить з мільйонним запасом. | Логи, аналітика, системи з мільярдами записів. |
| **REAL / FLOAT4** | Втрачає точність (0.1 + 0.2 ≠ 0.3 у бінарному представленні). | Наукові обчислення, координати GPS, фізичні вимірювання. |
| **DOUBLE / FLOAT8** | Та сама причина — наближене представлення. | Тільки коли точність до 15 цифр достатня і економиться місце порівняно з NUMERIC. |
| **CHAR(n)** | Доповнює значення пробілами до фіксованої довжини — марнотратно й вимагає `TRIM` при порівнянні. | Код країни ISO (`UA`, `US`) — суворо фіксовано 2 символи. |

### 4.5. Перевірка цілісності обмежень

Спробуємо порушити обмеження — кожна операція повинна бути відхилена:

```sql
-- Порушення CHECK: кредити поза діапазоном
INSERT INTO college.courses (code, title, department_id, credits)
VALUES ('CS999', 'Тест', 1, 50);
-- ERROR: new row for relation "courses" violates check constraint "ck_courses_credits"

-- Порушення FK: неіснуюча кафедра
INSERT INTO college.courses (code, title, department_id, credits)
VALUES ('CS999', 'Тест', 999, 5);
-- ERROR: insert or update on table "courses" violates foreign key constraint "fk_courses_department"

-- Порушення UNIQUE: дублікат коду
INSERT INTO college.departments (code, name) VALUES ('CS', 'Інша кафедра');
-- ERROR: duplicate key value violates unique constraint "uq_departments_code"

-- Порушення NOT NULL
INSERT INTO college.departments (code) VALUES ('BIO');
-- ERROR: null value in column "name" violates not-null constraint
```

Усі чотири INSERT'и відхиляються СКБД — обмеження працюють правильно.

## 6. Відповіді на питання для захисту

### 6.1. Чому для грошей використали NUMERIC, а не REAL?

**Головна причина — точність.** Тип `REAL` (та `DOUBLE PRECISION`) зберігає числа у **двійковому форматі з плаваючою комою** (IEEE 754). У цьому форматі деякі десяткові дроби не мають точного представлення. Наприклад:

```sql
SELECT 0.1::REAL + 0.2::REAL;
-- Результат: 0.30000001 (а не 0.3!)
```

Для сум грошей — платежів, залишків, нарахувань — такі «мікропохибки» накопичуються й призводять до:

- Балансів, які не сходяться на копійку.
- Втрати довіри клієнтів та аудиту.
- Юридичних ризиків — у фінансовій звітності 0.01 грн теж має значення.

**`NUMERIC(10, 2)` зберігає число в десятковому форматі точно** — 10 значущих цифр, з яких 2 після коми. `0.1 + 0.2` завжди дає рівно `0.3`.

**Коротке правило:** гроші, курси валют, оцінки, відсотки, ваги в торгівлі — завжди NUMERIC. REAL/DOUBLE — для наукових обчислень, де 15 значущих цифр достатньо й важлива швидкість.

### 6.2. Навіщо задавати імена обмеженням?

Якщо явно не вказати `CONSTRAINT <name>`, PostgreSQL згенерує автоматичне ім'я виду `courses_credits_check` або `courses_department_id_fkey`. Назвати обмеження вручну варто з **п'яти причин**:

1. **Зрозумілі помилки.** Коли INSERT порушує обмеження, у повідомленні буде зрозуміла назва:
   ```
   ERROR: violates check constraint "ck_courses_credits"
   ```
   замість автозгенерованого `courses_credits_check456789`. Розробник одразу бачить, яке саме правило порушено.

2. **Явний контроль у міграціях.** Автоматичні імена залежать від порядку створення й можуть відрізнятися між середовищами (dev / test / prod). Явні імена роблять схему детермінованою.

3. **Можливість видалити чи змінити.** Щоб виконати `ALTER TABLE … DROP CONSTRAINT xxx`, потрібно знати ім'я. З явним ім'ям його легко прочитати у вихідному коді.

4. **Документація коду.** Ім'я на кшталт `ck_enrollments_grade` одразу говорить, що й де перевіряється.

5. **Конвенція команди.** Префікси (`pk_`, `fk_`, `uq_`, `ck_`) допомагають швидко візуально розрізняти типи обмежень при читанні схеми.

### 6.3. Що означає GENERATED ALWAYS AS IDENTITY?

Це сучасний стандарт SQL (SQL:2003+) для **автоматичної генерації унікальних значень** колонки — альтернатива застарілому `SERIAL`.

**Синтаксис і семантика:**

```sql
column_name INTEGER GENERATED ALWAYS AS IDENTITY
```

- **GENERATED** — значення генерує СКБД (а не користувач).
- **ALWAYS** — користувачеві **заборонено** вручну вставляти значення у цю колонку. Спроба зробити `INSERT INTO ... VALUES (42, ...)` для IDENTITY-колонки поверне помилку.
- **BY DEFAULT** (альтернатива) — користувач може вручну задати значення, але якщо не задасть — СКБД згенерує.
- **AS IDENTITY** — використовується внутрішня послідовність (sequence), значення якої зростає з кожним INSERT'ом.

**Типовий сценарій:**

```sql
INSERT INTO departments (code, name) VALUES ('BIO', 'Біологія');
-- department_id СКБД встановить сама: 4, 5, 6...

INSERT INTO departments (department_id, code, name) VALUES (100, 'XX', 'Тест');
-- ERROR: cannot insert a non-DEFAULT value into column "department_id"
```

**Переваги над SERIAL:**

| Критерій | `SERIAL` | `GENERATED ALWAYS AS IDENTITY` |
|---|---|---|
| Стандарт SQL | Ні (PostgreSQL-специфічний) | Так (SQL:2003) |
| Захист від випадкової вставки | Ні | Так (`ALWAYS`) |
| Переносимість між СКБД | Погана | Добра |
| Керування послідовністю | Через окремий об'єкт | Автоматично прив'язана |

**Коли використовувати BY DEFAULT:** при міграції даних, коли треба тимчасово вставляти записи з уже відомими ID.

### 6.4. У якому порядку потрібно створювати пов'язані таблиці?

**Правило:** таблицю можна створити тільки **після** всіх таблиць, на які вона посилається через зовнішні ключі. Інакше при створенні FK СКБД видасть помилку `relation does not exist`.

**Порядок обчислюють через топологічне сортування графа залежностей.**

Для нашої схеми граф залежностей:

```
departments ───▶ courses ───▶ enrollments
                                  ▲
                                  │
                              students
```

**Коректний порядок створення (зверху вниз):**

1. **departments** — немає FK, можна створити першою.
2. **students** — немає FK, незалежна.
3. **courses** — залежить від `departments`.
4. **enrollments** — залежить від `students` і `courses`.

**Порядок видалення — зворотний:**

1. `enrollments` — скасовуємо посилання на `students` і `courses`.
2. `courses` — скасовуємо посилання на `departments`.
3. `students` — незалежна.
4. `departments` — незалежна.

Саме тому у нашому `schema.sql` на початку йдуть `DROP TABLE IF EXISTS` **у зворотному порядку** від створення.

**Альтернативи для складних випадків:**

- `DROP ... CASCADE` — видалить таблицю разом з усім, що на неї посилається.
- `CREATE TABLE ... ( ... );` + окремо `ALTER TABLE ... ADD CONSTRAINT fk_... FOREIGN KEY ...` — спочатку створюємо всі таблиці без FK, потім додаємо FK. Корисно при циклічних залежностях.
- `DEFERRABLE INITIALLY DEFERRED` — перевірка FK відкладається до кінця транзакції, що дозволяє тимчасово порушувати цілісність усередині неї.

## Висновок

Скрипт `schema.sql` створює повну навчальну схему `college.*` з чотирьох таблиць:

- **4 таблиці** з продуманими типами даних (INTEGER/SMALLINT/VARCHAR/NUMERIC/DATE).
- **13 іменованих обмежень цілісності** (4 PRIMARY KEY, 3 FOREIGN KEY, 3 UNIQUE, 5 CHECK — плюс неявні NOT NULL).
- **3 індекси** для оптимізації типових запитів.
- **4 тестові записи** для перевірки працездатності.

Схема готова до наступної практичної роботи — заповнення даними через DML (`INSERT`, `UPDATE`, `DELETE`) та виконання запитів (`SELECT` з `JOIN`).
