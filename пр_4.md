# Практична робота №4: Перетворення ER-діаграми у реляційну схему

## Предметна область: Магазин електроніки

> Продовження робіт №1–№3. Беремо концептуальну ER-модель з практичної №3 і переводимо її в **логічну реляційну схему** з первинними та зовнішніми ключами, обмеженнями цілісності та готовим SQL-скриптом для PostgreSQL.

---

## 1. Правила перетворення ER-моделі в реляційну схему

| № | Елемент ER-моделі | Правило перетворення |
|---|---|---|
| 1 | **Сильна сутність** | Стає таблицею. Атрибути — колонками. Ідентифікатор — первинним ключем. |
| 2 | **Багатозначний атрибут** | Виноситься в окрему таблицю з FK на батьківську сутність. |
| 3 | **Складений атрибут** | Розкладається на атомарні колонки (1NF). |
| 4 | **Зв'язок 1:1** | FK на одній зі сторін (обирається та, що більш обов'язкова), з UNIQUE-обмеженням. |
| 5 | **Зв'язок 1:N** | FK у таблиці на стороні «багато», посилається на PK батьківської таблиці. |
| 6 | **Зв'язок M:N** | Окрема **асоціативна таблиця** зі складеним первинним ключем з двох FK. |
| 7 | **Рекурсивний 1:N** | FK на ту ж таблицю (наприклад, `parent_id` у `category`). |
| 8 | **Обов'язкова участь** | FK отримує обмеження `NOT NULL`. |
| 9 | **Необов'язкова участь** | FK допускає `NULL`. |
| 10 | **Обмеження домену** | Реалізується через типи, `CHECK`, `ENUM`, `DEFAULT`. |

## 2. Таблиця відповідності «сутність → таблиця, зв'язок → правило»

### 2.1. Сутності

| Сутність ER-моделі | Таблиця | Коментар |
|---|---|---|
| CLIENT | `client` | Пряме перетворення сильної сутності |
| CATEGORY | `category` | Рекурсивний зв'язок через `parent_category_id` |
| PRODUCT | `product` | `category_id` як FK |
| WAREHOUSE | `warehouse` | Пряме перетворення |
| SUPPLIER | `supplier` | Пряме перетворення |
| ORDER | `orders` | Назва змінена — `order` зарезервоване слово в SQL |
| ORDER_ITEM (асоціативна) | `order_item` | Розв'язок M:N між `orders` та `product` |
| STOCK (асоціативна) | `stock` | Розв'язок M:N між `product` та `warehouse` |
| SUPPLY (асоціативна) | `supply` | Розв'язок M:N між `supplier` та `product` |

### 2.2. Зв'язки

| Зв'язок у ER-моделі | Тип | Правило перетворення | Де FK |
|---|---|---|---|
| CLIENT —оформлює— ORDER | 1:N | Правило №5 | `orders.client_id` → `client.client_id` |
| CATEGORY —містить— PRODUCT | 1:N | Правило №5 | `product.category_id` → `category.category_id` |
| CATEGORY —підкатегорія— CATEGORY | 1:N (рекурсія) | Правило №7 | `category.parent_category_id` → `category.category_id` |
| ORDER ↔ PRODUCT | M:N | Правило №6 | Таблиця `order_item` з двома FK |
| PRODUCT ↔ WAREHOUSE | M:N | Правило №6 | Таблиця `stock` з двома FK |
| SUPPLIER ↔ PRODUCT | M:N | Правило №6 | Таблиця `supply` з двома FK |

## 3. Реляційна схема — опис таблиць

### 3.1. `client` — Клієнти

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `client_id` | SERIAL | **PK** | автоінкремент |
| `full_name` | VARCHAR(100) | NOT NULL | |
| `phone` | VARCHAR(20) | UNIQUE, NOT NULL | формат `+380XXXXXXXXX` |
| `email` | VARCHAR(100) | UNIQUE | не обов'язкове |
| `bonus_balance` | INTEGER | NOT NULL, DEFAULT 0, CHECK (≥ 0) | |
| `registration_date` | DATE | NOT NULL, DEFAULT CURRENT_DATE | |

### 3.2. `category` — Категорії

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `category_id` | SERIAL | **PK** | |
| `name` | VARCHAR(100) | NOT NULL | |
| `parent_category_id` | INTEGER | FK → `category(category_id)` ON DELETE SET NULL | NULL для кореневої |

Обмеження рівня таблиці: `UNIQUE(name, parent_category_id)` — ім'я унікальне у межах одного батька.

### 3.3. `product` — Товари

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `product_id` | SERIAL | **PK** | |
| `sku` | VARCHAR(50) | UNIQUE, NOT NULL | унікальний артикул |
| `name` | VARCHAR(200) | NOT NULL | |
| `price` | NUMERIC(10,2) | NOT NULL, CHECK (price > 0) | |
| `brand` | VARCHAR(50) | | |
| `warranty_months` | INTEGER | NOT NULL, DEFAULT 12, CHECK (≥ 0) | |
| `category_id` | INTEGER | NOT NULL, FK → `category(category_id)` ON DELETE RESTRICT | |

### 3.4. `warehouse` — Склади й магазини

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `warehouse_id` | SERIAL | **PK** | |
| `code` | VARCHAR(20) | UNIQUE, NOT NULL | напр. `WH-KYIV-01` |
| `address` | VARCHAR(200) | NOT NULL | |
| `warehouse_type` | VARCHAR(20) | NOT NULL, CHECK (IN 'склад', 'магазин') | |

### 3.5. `supplier` — Постачальники

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `supplier_id` | SERIAL | **PK** | |
| `name` | VARCHAR(100) | NOT NULL | |
| `tax_id` | VARCHAR(20) | UNIQUE, NOT NULL | ЄДРПОУ |
| `contact_phone` | VARCHAR(20) | | |
| `contact_email` | VARCHAR(100) | | |

### 3.6. `orders` — Замовлення

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `order_id` | SERIAL | **PK** | |
| `order_number` | VARCHAR(20) | UNIQUE, NOT NULL | напр. `ORD-2026-00412` |
| `created_at` | TIMESTAMP | NOT NULL, DEFAULT NOW() | |
| `status` | VARCHAR(20) | NOT NULL, CHECK (IN 'новий', 'оплачено', 'доставляється', 'завершено', 'скасовано') | |
| `total_amount` | NUMERIC(10,2) | NOT NULL, DEFAULT 0, CHECK (≥ 0) | |
| `client_id` | INTEGER | NOT NULL, FK → `client(client_id)` ON DELETE RESTRICT | |

### 3.7. `order_item` — Позиції замовлень (M:N)

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `order_item_id` | SERIAL | **PK** | |
| `order_id` | INTEGER | NOT NULL, FK → `orders(order_id)` ON DELETE CASCADE | |
| `product_id` | INTEGER | NOT NULL, FK → `product(product_id)` ON DELETE RESTRICT | |
| `quantity` | INTEGER | NOT NULL, CHECK (> 0) | |
| `unit_price` | NUMERIC(10,2) | NOT NULL, CHECK (> 0) | ціна на момент продажу |

Обмеження рівня таблиці: `UNIQUE(order_id, product_id)` — один товар не дублюється у позиціях одного замовлення.

### 3.8. `stock` — Складські залишки (M:N)

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `stock_id` | SERIAL | **PK** | |
| `product_id` | INTEGER | NOT NULL, FK → `product(product_id)` ON DELETE CASCADE | |
| `warehouse_id` | INTEGER | NOT NULL, FK → `warehouse(warehouse_id)` ON DELETE RESTRICT | |
| `quantity` | INTEGER | NOT NULL, DEFAULT 0, CHECK (≥ 0) | |
| `reserved` | INTEGER | NOT NULL, DEFAULT 0, CHECK (≥ 0 AND ≤ quantity) | |

Обмеження рівня таблиці: `UNIQUE(product_id, warehouse_id)` — одна пара (товар, склад) не повторюється.

### 3.9. `supply` — Постачання (M:N)

| Колонка | Тип | Обмеження | Коментар |
|---|---|---|---|
| `supply_id` | SERIAL | **PK** | |
| `supplier_id` | INTEGER | NOT NULL, FK → `supplier(supplier_id)` ON DELETE RESTRICT | |
| `product_id` | INTEGER | NOT NULL, FK → `product(product_id)` ON DELETE RESTRICT | |
| `supply_date` | DATE | NOT NULL, DEFAULT CURRENT_DATE | |
| `quantity` | INTEGER | NOT NULL, CHECK (> 0) | |
| `purchase_price` | NUMERIC(10,2) | NOT NULL, CHECK (> 0) | |

## 4. Матриця правил ON DELETE для зовнішніх ключів

| Зовнішній ключ | Правило | Обґрунтування |
|---|---|---|
| `category.parent_category_id` → `category` | **SET NULL** | Видалення категорії «Електроніка» не має видаляти «Смартфони» — вони стають кореневими. |
| `product.category_id` → `category` | **RESTRICT** | Не можна видалити категорію, у якій є товари — спочатку перенести або списати товари. |
| `orders.client_id` → `client` | **RESTRICT** | Клієнта не можна видалити, якщо є замовлення (аудит, фінансовий облік). |
| `order_item.order_id` → `orders` | **CASCADE** | Видалення замовлення автоматично видаляє всі його позиції. |
| `order_item.product_id` → `product` | **RESTRICT** | Товар, проданий у замовленні, не можна видалити — порушить історію продажів. |
| `stock.product_id` → `product` | **CASCADE** | Якщо товар видаляємо з каталогу — знімаємо залишки на всіх складах. |
| `stock.warehouse_id` → `warehouse` | **RESTRICT** | Склад не видаляємо, поки на ньому є залишки. |
| `supply.supplier_id` → `supplier` | **RESTRICT** | Постачальник з історією постачань не видаляється. |
| `supply.product_id` → `product` | **RESTRICT** | Товар з історією постачань не видаляється. |

## 5. Перелік усіх обмежень цілісності

### 5.1. Обмеження сутнісної цілісності (PRIMARY KEY)

Кожна таблиця має сурогатний первинний ключ з автоінкрементом (`SERIAL`). Це гарантує унікальність записів і не залежить від бізнес-даних.

### 5.2. Обмеження посилальної цілісності (FOREIGN KEY)

Усі 9 зовнішніх ключів з §4. Забезпечують неможливість посилання на неіснуючий запис.

### 5.3. Обмеження домену

| Таблиця | Колонка | Обмеження |
|---|---|---|
| `client` | `bonus_balance` | `CHECK (bonus_balance >= 0)` |
| `product` | `price` | `CHECK (price > 0)` |
| `product` | `warranty_months` | `CHECK (warranty_months >= 0)` |
| `warehouse` | `warehouse_type` | `CHECK (warehouse_type IN ('склад','магазин'))` |
| `orders` | `status` | `CHECK (status IN (...))` |
| `orders` | `total_amount` | `CHECK (total_amount >= 0)` |
| `order_item` | `quantity` | `CHECK (quantity > 0)` |
| `order_item` | `unit_price` | `CHECK (unit_price > 0)` |
| `stock` | `quantity` | `CHECK (quantity >= 0)` |
| `stock` | `reserved` | `CHECK (reserved >= 0 AND reserved <= quantity)` |
| `supply` | `quantity` | `CHECK (quantity > 0)` |
| `supply` | `purchase_price` | `CHECK (purchase_price > 0)` |

### 5.4. Обмеження унікальності (UNIQUE)

| Таблиця | Колонки | Коментар |
|---|---|---|
| `client` | `phone`, `email` | Контакти не дублюються |
| `category` | `(name, parent_category_id)` | Ім'я унікальне у межах батька |
| `product` | `sku` | Артикул унікальний |
| `warehouse` | `code` | Код складу унікальний |
| `supplier` | `tax_id` | ЄДРПОУ унікальний |
| `orders` | `order_number` | Номер замовлення унікальний |
| `order_item` | `(order_id, product_id)` | Товар не дублюється в одному замовленні |
| `stock` | `(product_id, warehouse_id)` | Один залишок на пару товар-склад |

### 5.5. Значення за замовчуванням (DEFAULT)

| Таблиця | Колонка | Значення |
|---|---|---|
| `client` | `bonus_balance` | 0 |
| `client` | `registration_date` | CURRENT_DATE |
| `product` | `warranty_months` | 12 |
| `orders` | `created_at` | NOW() |
| `orders` | `total_amount` | 0 |
| `stock` | `quantity`, `reserved` | 0 |
| `supply` | `supply_date` | CURRENT_DATE |

### 5.6. Обмеження NOT NULL

Застосовано до всіх колонок, без яких запис не має сенсу: назви, ціни, статуси, зовнішні ключі обов'язкових зв'язків.

## 6. Повний SQL-скрипт створення схеми (PostgreSQL)

Файл можна зберегти як `schema.sql` поруч з цим звітом і виконати командою:
```bash
psql -U postgres -d electronics_store -f schema.sql
```

```sql
-- =========================================================
-- Магазин електроніки — реляційна схема
-- СКБД: PostgreSQL 14+
-- =========================================================

-- ---------- 1. client ----------
CREATE TABLE client (
    client_id         SERIAL       PRIMARY KEY,
    full_name         VARCHAR(100) NOT NULL,
    phone             VARCHAR(20)  NOT NULL UNIQUE,
    email             VARCHAR(100) UNIQUE,
    bonus_balance     INTEGER      NOT NULL DEFAULT 0
                                   CHECK (bonus_balance >= 0),
    registration_date DATE         NOT NULL DEFAULT CURRENT_DATE
);

-- ---------- 2. category (рекурсивна) ----------
CREATE TABLE category (
    category_id        SERIAL       PRIMARY KEY,
    name               VARCHAR(100) NOT NULL,
    parent_category_id INTEGER      REFERENCES category(category_id)
                                    ON DELETE SET NULL,
    UNIQUE (name, parent_category_id)
);

-- ---------- 3. product ----------
CREATE TABLE product (
    product_id      SERIAL         PRIMARY KEY,
    sku             VARCHAR(50)    NOT NULL UNIQUE,
    name            VARCHAR(200)   NOT NULL,
    price           NUMERIC(10, 2) NOT NULL CHECK (price > 0),
    brand           VARCHAR(50),
    warranty_months INTEGER        NOT NULL DEFAULT 12
                                   CHECK (warranty_months >= 0),
    category_id     INTEGER        NOT NULL
                                   REFERENCES category(category_id)
                                   ON DELETE RESTRICT
);

-- ---------- 4. warehouse ----------
CREATE TABLE warehouse (
    warehouse_id   SERIAL       PRIMARY KEY,
    code           VARCHAR(20)  NOT NULL UNIQUE,
    address        VARCHAR(200) NOT NULL,
    warehouse_type VARCHAR(20)  NOT NULL
                                CHECK (warehouse_type IN ('склад', 'магазин'))
);

-- ---------- 5. supplier ----------
CREATE TABLE supplier (
    supplier_id   SERIAL       PRIMARY KEY,
    name          VARCHAR(100) NOT NULL,
    tax_id        VARCHAR(20)  NOT NULL UNIQUE,
    contact_phone VARCHAR(20),
    contact_email VARCHAR(100)
);

-- ---------- 6. orders ----------
CREATE TABLE orders (
    order_id     SERIAL         PRIMARY KEY,
    order_number VARCHAR(20)    NOT NULL UNIQUE,
    created_at   TIMESTAMP      NOT NULL DEFAULT NOW(),
    status       VARCHAR(20)    NOT NULL
                                CHECK (status IN (
                                    'новий', 'оплачено', 'доставляється',
                                    'завершено', 'скасовано'
                                )),
    total_amount NUMERIC(10, 2) NOT NULL DEFAULT 0
                                CHECK (total_amount >= 0),
    client_id    INTEGER        NOT NULL
                                REFERENCES client(client_id)
                                ON DELETE RESTRICT
);

-- ---------- 7. order_item (M:N orders ↔ product) ----------
CREATE TABLE order_item (
    order_item_id SERIAL         PRIMARY KEY,
    order_id      INTEGER        NOT NULL
                                 REFERENCES orders(order_id)
                                 ON DELETE CASCADE,
    product_id    INTEGER        NOT NULL
                                 REFERENCES product(product_id)
                                 ON DELETE RESTRICT,
    quantity      INTEGER        NOT NULL CHECK (quantity > 0),
    unit_price    NUMERIC(10, 2) NOT NULL CHECK (unit_price > 0),
    UNIQUE (order_id, product_id)
);

-- ---------- 8. stock (M:N product ↔ warehouse) ----------
CREATE TABLE stock (
    stock_id     SERIAL  PRIMARY KEY,
    product_id   INTEGER NOT NULL
                         REFERENCES product(product_id)
                         ON DELETE CASCADE,
    warehouse_id INTEGER NOT NULL
                         REFERENCES warehouse(warehouse_id)
                         ON DELETE RESTRICT,
    quantity     INTEGER NOT NULL DEFAULT 0 CHECK (quantity >= 0),
    reserved     INTEGER NOT NULL DEFAULT 0
                         CHECK (reserved >= 0 AND reserved <= quantity),
    UNIQUE (product_id, warehouse_id)
);

-- ---------- 9. supply (M:N supplier ↔ product) ----------
CREATE TABLE supply (
    supply_id      SERIAL         PRIMARY KEY,
    supplier_id    INTEGER        NOT NULL
                                  REFERENCES supplier(supplier_id)
                                  ON DELETE RESTRICT,
    product_id     INTEGER        NOT NULL
                                  REFERENCES product(product_id)
                                  ON DELETE RESTRICT,
    supply_date    DATE           NOT NULL DEFAULT CURRENT_DATE,
    quantity       INTEGER        NOT NULL CHECK (quantity > 0),
    purchase_price NUMERIC(10, 2) NOT NULL CHECK (purchase_price > 0)
);

-- ---------- Індекси для прискорення запитів ----------
CREATE INDEX idx_product_category     ON product(category_id);
CREATE INDEX idx_orders_client        ON orders(client_id);
CREATE INDEX idx_orders_created_at    ON orders(created_at);
CREATE INDEX idx_order_item_order     ON order_item(order_id);
CREATE INDEX idx_order_item_product   ON order_item(product_id);
CREATE INDEX idx_stock_warehouse      ON stock(warehouse_id);
CREATE INDEX idx_supply_supplier      ON supply(supplier_id);
CREATE INDEX idx_supply_product_date  ON supply(product_id, supply_date);
```

## 7. Чому зв'язки M:N перетворилися на окремі таблиці

У реляційній моделі кожна комірка таблиці зберігає **атомарне значення**. Пряма реалізація зв'язку «багато-до-багатьох» неможлива з трьох причин:

1. **Порушення першої нормальної форми (1NF)** — не можна зберігати в одній комірці список ідентифікаторів (наприклад, `order.products = "1,5,12"`), бо це ламає SQL-запити й цілісність.
2. **Невизначена кількість зв'язків** — у замовленні може бути 1, 10 або 100 товарів; скільки колонок додавати заздалегідь — невідомо.
3. **Втрата атрибутів самого зв'язку** — кількість, ціна на момент продажу, дата постачання стосуються саме зв'язку, а не жодної зі сторін.

### Рішення — асоціативна таблиця

Асоціативна (проміжна, join) таблиця розкладає M:N на два зв'язки 1:N:

```
PRODUCT (1) ──< ORDER_ITEM >── (1) ORDERS
```

Така таблиця:

- має власний первинний ключ (сурогатний або складений з двох FK);
- містить **по одному зовнішньому ключу** на кожну зі сторін;
- може мати **власні атрибути зв'язку** (quantity, unit_price, supply_date);
- може мати **обмеження унікальності** `UNIQUE(fk1, fk2)`, щоб не дублювати пару.

### Приклад з моделі

У нас три таких таблиці:

| Асоціативна таблиця | Розв'язує | Власні атрибути зв'язку |
|---|---|---|
| `order_item` | `orders` ↔ `product` | кількість, ціна на момент продажу |
| `stock` | `product` ↔ `warehouse` | поточний залишок, зарезервовано |
| `supply` | `supplier` ↔ `product` | дата, кількість, закупівельна ціна |

Без них довелося б дублювати дані або втрачати важливу інформацію про сам факт зв'язку.

## 9. Відповіді на питання для захисту

### 9.1. Чому для зв'язку 1:N зовнішній ключ розміщують на стороні «багато»?

У колонці може зберігатися **одне значення**, а на стороні «один» зв'язку таких значень потенційно багато. Приклад:

- **Правильно:** у `orders.client_id` стоїть один ідентифікатор клієнта. Один клієнт пов'язаний з багатьма замовленнями — кожне з них у своєму рядку просто посилається на нього.
- **Неправильно:** у `client` робити колонку `order_ids` зі списком замовлень — порушить 1NF і стане некерованим.

Таким чином, FK кладуть **на бік «багато»** (`orders`), а він вказує на PK **на бік «один»** (`client`). Один запис CLIENT – багато записів ORDERS, у кожному з яких FK → client.

### 9.2. Що таке посилальна цілісність і як її забезпечити?

**Посилальна цілісність** (referential integrity) — гарантія, що кожне значення зовнішнього ключа або **посилається на існуючий запис** батьківської таблиці, або дорівнює NULL (якщо FK не обов'язковий).

Забезпечується:

- **Оголошенням FK у СХБД** (`REFERENCES parent(id)`) — СКБД автоматично відхиляє INSERT/UPDATE з неіснуючим значенням.
- **Правилами ON DELETE / ON UPDATE** — визначають поведінку при видаленні або зміні батьківського запису: `CASCADE`, `RESTRICT`, `SET NULL`, `SET DEFAULT`.
- **Транзакціями** — зміни кількох пов'язаних таблиць виконуються атомарно.
- **Індексами на FK-колонках** — для швидкої перевірки й пошуку залежних записів.

У нашій моделі всі 9 зовнішніх ключів оголошено з конкретними правилами ON DELETE (§4), що гарантує: неможливо вставити позицію замовлення для неіснуючого замовлення; неможливо видалити категорію, у якій ще є товари.

### 9.3. Як перетворити зв'язок M:N без втрати даних?

Алгоритм перетворення:

1. **Створити нову таблицю** з назвою, що відображає зв'язок (наприклад, `order_item`, `enrollment`).
2. **Додати по одному FK** на кожну сторону зв'язку — обидва `NOT NULL` з доцільним правилом ON DELETE.
3. **Перенести атрибути зв'язку** (кількість, дата, ціна тощо) в цю нову таблицю.
4. **Визначити первинний ключ** — або сурогатний `SERIAL`, або складений `PRIMARY KEY (fk1, fk2)` (якщо не потрібно дозволяти повторення пари у часі).
5. **Додати обмеження унікальності** `UNIQUE(fk1, fk2)`, якщо пара має бути єдиною (наприклад, один товар не дублюється у позиціях одного замовлення).
6. **Якщо дані вже існували у вигляді списків** — розбити кожен список на окремі рядки (INSERT... SELECT), зберігаючи зв'язок кожного елемента з «батьківським» записом.

Жодні дані не втрачаються: усе, що раніше було «в одному записі зі списком», тепер розкладено на окремі рядки асоціативної таблиці, а атрибути зв'язку вперше отримують належне місце.

### 9.4. Що станеться, якщо видалити запис батьківської таблиці без каскаду?

Поведінка залежить від **правила ON DELETE**, оголошеного для FK:

| Правило | Поведінка |
|---|---|
| **RESTRICT / NO ACTION** (за замовчуванням) | СКБД **відхилить** DELETE і поверне помилку `foreign key violation`. Батьківський запис залишиться. |
| **CASCADE** | Автоматично видаляться всі дочірні записи. |
| **SET NULL** | FK у дочірніх записах стане NULL (колонка має дозволяти NULL). |
| **SET DEFAULT** | FK у дочірніх записах отримає значення за замовчуванням (яке теж має посилатися на існуючий запис). |

**Якщо правила не оголошено взагалі** — у більшості СКБД діє `NO ACTION`: видалення відхиляється. У MySQL/InnoDB поведінка схожа, у SQLite без увімкнення `foreign_keys = ON` цілісність узагалі не перевіряється.

**Приклад з моделі:** спробуємо `DELETE FROM client WHERE client_id = 42`, коли цей клієнт має замовлення. Через `ON DELETE RESTRICT` у `orders.client_id` СКБД поверне помилку:

```
ERROR: update or delete on table "client" violates foreign key constraint
       "orders_client_id_fkey" on table "orders"
DETAIL: Key (client_id)=(42) is still referenced from table "orders".
```

Це бажана поведінка — втрата клієнта разом з його історією замовлень зламає фінансову звітність. Замість видалення зазвичай використовують **soft delete** (прапорець `is_deleted`) або **анонімізацію** (заміну особистих даних на знеособлені).

## Висновок

Концептуальну ER-модель з практичної №3 успішно перетворено у **повну реляційну схему з 9 таблицями**, з яких 6 — сильні сутності й 3 — асоціативні (розв'язок M:N). Схема містить:

- 9 первинних ключів;
- 9 зовнішніх ключів з явними правилами ON DELETE;
- 12 CHECK-обмежень доменів;
- 8 UNIQUE-обмежень;
- 8 індексів для оптимізації типових запитів.

Схема готова до **виконання SQL-скрипта** у PostgreSQL і початку розробки прикладного рівня. У наступній практичній роботі можна буде перевірити нормалізацію (1NF → 3NF → BCNF) і спроєктувати SQL-запити для операційних і аналітичних сценаріїв.
