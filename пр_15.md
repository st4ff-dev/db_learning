## 2. Підготовка «асиметричних» даних

Щоб OUTER JOIN показали вагомий результат, у даних потрібна **асиметрія** — рядки без пари з іншого боку.

### 2.1. У схемі `college.*`

| Асиметрія | Як створено |
|---|---|
| **Кафедра без курсів** | Додано `('HR', 'Гуманітарні науки')` — ще не має жодного курсу. |
| **Студент без реєстрацій** | Додано `('ST-LONELY-001', 'Самітник Одинокий')` — не записався ні на що. |

**Чому не можна створити «курс без кафедри»** у `college.*`:  обмеження `fk_courses_department` вимагає `NOT NULL` + посилання на існуючу кафедру.

### 2.2. Допоміжна схема `join_demo`

Для демонстрації `FULL JOIN` з «дірками» з обох боків створено окрему схему з релаксованими обмеженнями (без FK, з NULL):

```sql
-- departments: 4 рядки (одна без курсів)
(1, 'IT'), (2, 'Фізика'), (3, 'Математика'), (4, 'HR — без курсів')

-- courses: 4 рядки (один без кафедри — NULL FK)
(10, 'Бази даних',      1)
(20, 'Вебтехнології',    1)
(30, 'Загальна фізика',  2)
(40, 'Сирота-курс',      NULL)
```

Тепер маємо асиметрію з обох боків для FULL JOIN демо.

## 3. INNER JOIN

### 3.1. Поведінка

**INNER JOIN** (або просто `JOIN`) залишає **тільки ті рядки, де є пара в обох таблицях**. Усе без пари — зникає.

### 3.2. Запит на `college.*`

```sql
SELECT d.name AS department, c.title AS course
FROM college.courses AS c
JOIN college.departments AS d USING (department_id)
ORDER BY d.name, c.title;
```

**Очікуваний результат:**

```
      department          |      course
--------------------------+-------------------
 Інформаційні технології  | Алгоритми
 Інформаційні технології  | Бази даних
 Інформаційні технології  | Вебтехнології
 Математика               | Дискретна математика
 Фізика                   | Загальна фізика
```

**Пояснення:**

- **Кафедра `HR` не з'явилася** — для неї немає жодного курсу.
- Усі курси з'явилися — у кожного є своя кафедра.
- У результаті `N × M` реально існуючих пар.

### 3.3. Запит на `join_demo`

```sql
SELECT d.name AS department, c.title AS course
FROM join_demo.courses c
JOIN join_demo.departments d USING (department_id);
```

**Результат:**

```
 department | course
------------+-----------------
 IT         | Бази даних
 IT         | Вебтехнології
 Фізика     | Загальна фізика
(3 rows)
```

**Що зникло:**

- **Кафедра «HR — без курсів» (id=4)** — немає курсів.
- **Курс «Сирота-курс» (id=40)** — `department_id = NULL`, тому JOIN не знаходить пари (навіть якби була кафедра з NULL — порівняння `NULL = NULL` дає NULL, не TRUE).

З 4 кафедр + 4 курсів залишилося 3 пари.

## 4. LEFT JOIN

### 4.1. Поведінка

**LEFT JOIN** залишає **ВСІ рядки лівої таблиці**. Для рядків без пари у правій таблиці — колонки правої заповнюються NULL.

### 4.2. Запит: кафедри + їхні курси (включно з порожніми)

```sql
SELECT d.name AS department, c.title AS course
FROM college.departments AS d
LEFT JOIN college.courses AS c USING (department_id)
ORDER BY d.name, c.title;
```

**Результат:**

```
      department          |      course
--------------------------+-------------------
 Гуманітарні науки        | NULL           ← нова, не було в INNER JOIN
 Інформаційні технології  | Алгоритми
 Інформаційні технології  | Бази даних
 Інформаційні технології  | Вебтехнології
 Математика               | Дискретна математика
 Фізика                   | Загальна фізика
```

**Пояснення:**

- Додався **1 рядок** порівняно з INNER JOIN — кафедра `HR` з `course = NULL`.
- Усі інші рядки — такі самі, як у INNER JOIN.
- Коли у правій таблиці є кілька пар (у IT — 3 курси), лівий рядок дублюється по кількості пар.

### 4.3. Anti-join паттерн — знайти кафедри БЕЗ курсів

```sql
SELECT d.code, d.name
FROM college.departments AS d
LEFT JOIN college.courses AS c USING (department_id)
WHERE c.course_id IS NULL;
```

**Результат:**

```
 code |       name
------+-------------------
 HR   | Гуманітарні науки
```

**Трюк:** `LEFT JOIN + WHERE child IS NULL` — класичний патерн для «записів лівої таблиці, які НЕ мають пари у правій». Альтернатива — `NOT EXISTS` або `NOT IN`.

## 5. RIGHT JOIN

### 5.1. Поведінка

**RIGHT JOIN** — дзеркальне відображення LEFT JOIN. Залишає **ВСІ рядки правої таблиці**, доповнюючи NULL з лівої, якщо пари немає.

### 5.2. Запит на `join_demo`

```sql
SELECT d.name AS department, c.title AS course
FROM join_demo.departments d
RIGHT JOIN join_demo.courses c USING (department_id)
ORDER BY c.title;
```

**Результат:**

```
 department | course
------------+-----------------
 IT         | Бази даних
 IT         | Вебтехнології
 Фізика     | Загальна фізика
 NULL       | Сирота-курс     ← додано порівняно з INNER JOIN
```

**Що додалося:** курс «Сирота-курс» — з `department = NULL`, бо його `department_id = NULL`.

**Що НЕ з'явилося:** кафедра «HR — без курсів» — її рядки у лівій таблиці, а RIGHT JOIN лишає тільки праву.

### 5.3. Чому RIGHT JOIN рідко використовують

Будь-який `RIGHT JOIN` можна переписати як `LEFT JOIN` зі зміною порядку таблиць:

```sql
-- Еквівалент
SELECT d.name AS department, c.title AS course
FROM join_demo.courses c
LEFT JOIN join_demo.departments d USING (department_id)
ORDER BY c.title;
```

У більшості стилей коду `LEFT JOIN` вважається **читабельнішим**: читач зліва направо бачить «від яких рядків залежить звіт».

**Правило:** як ліву таблицю ставте ту, рядки якої повинні гарантовано з'явитися в результаті.

## 6. FULL JOIN

### 6.1. Поведінка

**FULL JOIN** (або `FULL OUTER JOIN`) залишає **ВСІ рядки з обох таблиць**. Де пари немає — NULL з протилежного боку.

### 6.2. Запит

```sql
SELECT
    COALESCE(d.name, '— без кафедри —')  AS department,
    COALESCE(c.title, '— без курсу —')    AS course
FROM join_demo.departments d
FULL JOIN join_demo.courses c USING (department_id)
ORDER BY department, course;
```

**Результат (5 рядків):**

```
      department        |      course
------------------------+-----------------
 HR — без курсів        | — без курсу —      ← з лівої без пари
 IT                     | Бази даних
 IT                     | Вебтехнології
 Фізика                 | Загальна фізика
 — без кафедри —        | Сирота-курс        ← з правої без пари
```

**Пояснення:**

- Порівняно з INNER JOIN додалося **2 рядки**:
  - «HR» без курсу (рядок лівої таблиці без пари справа);
  - «Сирота-курс» без кафедри (рядок правої таблиці без пари зліва).
- `COALESCE(col, 'за замовчуванням')` замінює NULL на людиночитабельний текст.

### 6.3. Патерн «знайти всі розсинхронізації»

```sql
SELECT d.department_id, d.name, c.course_id, c.title,
       CASE
           WHEN c.course_id IS NULL       THEN 'кафедра без курсів'
           WHEN d.department_id IS NULL   THEN 'курс без кафедри'
           ELSE 'match'
       END AS problem
FROM join_demo.departments d
FULL JOIN join_demo.courses c USING (department_id)
WHERE d.department_id IS NULL OR c.course_id IS NULL;
```

Повертає тільки «проблемні» рядки з обох боків — зручно для перевірки цілісності даних.

## 7. Звіт «студент — курс — оцінка» (3 JOIN)

### 7.1. INNER JOIN — тільки студенти з реєстраціями

```sql
SELECT
    s.student_number AS номер,
    s.full_name      AS студент,
    c.code           AS курс_код,
    c.title          AS курс_назва,
    e.grade          AS оцінка,
    d.name           AS кафедра
FROM college.enrollments e
JOIN college.students   s USING (student_id)
JOIN college.courses    c USING (course_id)
JOIN college.departments d USING (department_id)
ORDER BY s.full_name, c.code;
```

**Семантика:** `enrollments` — центральна таблиця зв'язку. Три JOIN «збагачують» кожну реєстрацію даними студента, курсу й кафедри.

### 7.2. LEFT JOIN — показати ВСІХ студентів

```sql
SELECT
    s.student_number                AS номер,
    s.full_name                     AS студент,
    COALESCE(c.code,  '—')          AS курс_код,
    COALESCE(c.title, '— немає —')  AS курс_назва,
    e.grade                         AS оцінка
FROM college.students      s
LEFT JOIN college.enrollments e USING (student_id)
LEFT JOIN college.courses     c USING (course_id)
ORDER BY s.full_name, c.code;
```

У виводі з'явиться **«Самітник Одинокий»** з NULL у колонках курсу — хоча він не записався ні на що, у звіті «усі студенти» він має бути присутнім.

## 8. USING vs ON — різниця

### 8.1. USING — короткий, об'єднує однойменні колонки

```sql
SELECT *
FROM join_demo.courses c
JOIN join_demo.departments d USING (department_id);
```

У виводі:
```
 department_id | course_id | title | name
---------------+-----------+-------+------
 1             | 10        | ...   | IT
```

**Одна колонка `department_id`** у результаті.

### 8.2. ON — гнучкий, зберігає обидві колонки

```sql
SELECT *
FROM join_demo.courses c
JOIN join_demo.departments d ON c.department_id = d.department_id;
```

У виводі:
```
 course_id | title | department_id (з c) | department_id (з d) | name
-----------+-------+---------------------+---------------------+------
 10        | ...   | 1                   | 1                   | IT
```

**Дві колонки `department_id`** — одна з лівої таблиці, друга з правої.

### 8.3. ON дозволяє складні умови

```sql
-- Складна умова: рівність + додатковий фільтр, виконаний В JOIN
SELECT c.title, d.name
FROM join_demo.courses c
JOIN join_demo.departments d
    ON c.department_id = d.department_id
   AND d.department_id <> 2;
```

**USING такого не вміє** — лише рівність однойменних колонок.

### 8.4. Інша різниця імен

```sql
-- USING не працює, якщо колонки мають різні імена:
SELECT * FROM a JOIN b USING (???);
-- Для a.user_id = b.customer_id треба ON:
SELECT * FROM a JOIN b ON a.user_id = b.customer_id;
```

### 8.5. Порівняльна таблиця

| Критерій | `USING` | `ON` |
|---|---|---|
| Синтаксис | коротший | розширений |
| Колонки у результаті | однойменна об'єднана в ОДНУ | обидві зберігаються |
| Умова | тільки рівність | будь-яка (AND, OR, >, <, функції) |
| Різні імена колонок | ❌ не можна | ✅ будь-які |
| Читабельність для простих JOIN | ✅ краще | трохи багатослівніше |

**Правило:** `USING` — для простих JOIN за однойменною колонкою; `ON` — завжди, коли умова складніша за просте рівняння або коли імена колонок різні.

## 9. Запобігання помилковому множенню рядків

### 9.1. Класична помилка

Запит «скільки курсів у кожного студента + сума годин» іноді пишуть так:

```sql
-- НЕБЕЗПЕЧНО: результат буде «надутий»
SELECT s.full_name,
       SUM(c.credits) AS credits,
       COUNT(p.phone) AS phones_count
FROM students s
JOIN enrollments e USING (student_id)
JOIN courses c USING (course_id)
JOIN student_phones p USING (student_id)
GROUP BY s.student_id, s.full_name;
```

**Проблема:** якщо у студента 3 телефони і 2 курси, JOIN створить `3 × 2 = 6` рядків. `SUM(credits)` потрійно завищить реальну кількість кредитів.

### 9.2. Правильні патерни

**А) Агрегувати в підзапиті перед JOIN:**

```sql
SELECT s.full_name, credits.total AS credits, phones.cnt AS phones
FROM students s
LEFT JOIN (
    SELECT e.student_id, SUM(c.credits) AS total
    FROM enrollments e JOIN courses c USING (course_id)
    GROUP BY e.student_id
) credits USING (student_id)
LEFT JOIN (
    SELECT student_id, COUNT(*) AS cnt
    FROM student_phones
    GROUP BY student_id
) phones USING (student_id);
```

Кожен підзапит дає **не більше одного рядка на студента** — множення не відбудеться.

**Б) Використати CTE (WITH):**

```sql
WITH credits_per_student AS (
    SELECT e.student_id, SUM(c.credits) AS total
    FROM enrollments e JOIN courses c USING (course_id)
    GROUP BY e.student_id
),
phones_per_student AS (
    SELECT student_id, COUNT(*) AS cnt
    FROM student_phones GROUP BY student_id
)
SELECT s.full_name, cps.total, pps.cnt
FROM students s
LEFT JOIN credits_per_student cps USING (student_id)
LEFT JOIN phones_per_student  pps USING (student_id);
```

Читається легше, ніж підзапити.

**В) Віконні функції (без агрегату на зовнішньому рівні):**

```sql
SELECT DISTINCT s.student_id, s.full_name,
       SUM(c.credits) OVER (PARTITION BY s.student_id) AS credits
FROM students s JOIN enrollments e USING (student_id) JOIN courses c USING (course_id);
```

### 9.3. Швидка перевірка

Якщо в звіті з JOIN виходять надмірні числа:

```sql
-- Скільки рядків до JOIN:
SELECT COUNT(*) FROM enrollments;

-- Скільки після:
SELECT COUNT(*) FROM enrollments e
JOIN student_phones p USING (student_id);
```

Якщо числа різні — JOIN множить рядки. Це нормально, якщо саме це потрібно; підозріло, якщо ні.

## 10. Відповіді на питання для захисту

### 10.1. Що повертає `LEFT JOIN`, якщо для лівого рядка немає пари?

**Рядок лівої таблиці зберігається**, а всі колонки правої таблиці заповнюються **NULL**.

Приклад:

```
students: (1, 'Петренко'), (2, 'Іваненко'), (3, 'Самітник')
enrollments: (1, 101, 90), (2, 102, 85)

SELECT s.full_name, e.grade
FROM students s
LEFT JOIN enrollments e USING (student_id);
```

**Результат:**

```
 full_name | grade
-----------+-------
 Петренко  |    90
 Іваненко  |    85
 Самітник  |  NULL   ← ось так виглядає "немає пари"
```

**Важливо:** якщо після LEFT JOIN додати `WHERE e.grade > 80`, рядок із NULL **зникне** — умова `NULL > 80` → NULL → FALSE. Тому для фільтрації з урахуванням «сиріт» треба писати:

```sql
WHERE e.grade > 80 OR e.grade IS NULL
```

### 10.2. Чим `INNER JOIN` відрізняється від `LEFT JOIN`?

**INNER JOIN:**

- Повертає **тільки рядки з парами в обох таблицях**.
- Без пари з будь-якого боку → рядок **не з'являється**.
- Семантика: «перетин».

**LEFT JOIN:**

- Повертає **ВСІ рядки лівої таблиці**.
- Для правої: пара, якщо є; NULL, якщо немає.
- Семантика: «ліва таблиця + опціональне доповнення правою».

**Приклад на наших даних:**

| Варіант | Кількість рядків | Чому |
|---|---|---|
| INNER JOIN departments + courses | 5 | 5 курсів, кожен з кафедрою |
| LEFT JOIN departments + courses | 6 | +1 кафедра HR без курсів |
| LEFT JOIN students + enrollments | 7 | 6 реєстрацій + 1 студент-«Самітник» без них |

**Коли який вибирати:**

- Якщо важливо показати **тільки реально існуючі зв'язки** (наприклад, «курси та їхні викладачі») → INNER JOIN.
- Якщо потрібно показати **всі об'єкти, включно з «порожніми»** (всі студенти, навіть без оцінок) → LEFT JOIN.

### 10.3. Коли доцільний FULL JOIN?

FULL JOIN потрібен, коли ми хочемо побачити **ВСІ записи з обох таблиць**, включно з тими, що не мають пари з жодного боку. Типові сценарії:

**1. Виявлення розсинхронізацій між двома джерелами.**

У нас є дві системи, що ведуть одні й ті самі довідники: HR-база клієнтів і бухгалтерська. Треба знайти:

```sql
SELECT hr.client_id, acc.client_id,
       CASE
           WHEN acc.client_id IS NULL THEN 'тільки в HR'
           WHEN hr.client_id  IS NULL THEN 'тільки в бухгалтерії'
           ELSE 'в обох'
       END AS status
FROM hr_clients hr
FULL JOIN accounting_clients acc USING (client_id);
```

**2. Звірка між старою й новою таблицями при міграції.**

```sql
SELECT old.id, new.id
FROM old_table old
FULL JOIN new_table new USING (id)
WHERE old.id IS NULL OR new.id IS NULL;
```

Повертає рядки, які «не переїхали» або «з'явилися з нізвідки».

**3. Аналітика «усі категорії × усі періоди»**, коли деякі комбінації пусті:

```sql
SELECT period, category, COUNT(sale.id)
FROM periods
FULL JOIN sales USING (period, category)
GROUP BY period, category;
```

**Коли FULL JOIN НЕ потрібен:**

- Для звичайних звітів типу «клієнт + його замовлення» достатньо LEFT JOIN.
- Коли дані прийшли з одного джерела й FK гарантовано валідні — «сирітних» рядків там і так немає.

**FULL JOIN — інструмент діагностики й звірки, не повсякденний запит.**

### 10.4. Як запобігти помилковому множенню рядків при JOIN?

**Корінь проблеми:** JOIN будує декартів добуток збігів. Якщо з лівого боку рядок A має 3 пари справа, він **дублюється 3 рази**. При кількох JOIN'ах множення — декартове: `3 × 2 = 6` рядків замість очікуваних.

**Патерни запобігання:**

**1. Перевірка кардинальності пар.** Перш ніж робити JOIN, запитайте себе:

- Чи унікальна комбінація у правій таблиці за колонкою з'єднання?
- Якщо `students JOIN enrollments USING (student_id)` — на одного студента може бути N реєстрацій. Якщо далі агрегувати, усе OK; якщо ні — рядки студента дублюватимуться.

**2. Агрегація перед JOIN:** якщо потрібна лише сума/кількість, спочатку згрупуйте в підзапиті:

```sql
LEFT JOIN (
    SELECT student_id, SUM(amount) AS total
    FROM payments GROUP BY student_id
) p USING (student_id)
```

**3. CTE** (`WITH … AS`) — те саме, але читабельніше.

**4. Віконні функції** замість GROUP BY у деяких випадках.

**5. DISTINCT як «пожежний вихід»:**

```sql
SELECT DISTINCT s.full_name, c.title FROM ...;
```

Працює, але сповільнює запит і приховує архітектурну проблему.

**6. Явні обмеження унікальності:** якщо `UNIQUE (student_id, course_id)` на `enrollments` — пара гарантовано унікальна.

**7. EXPLAIN ANALYZE** на реальних даних:

```sql
EXPLAIN ANALYZE
SELECT COUNT(*) FROM original;
EXPLAIN ANALYZE
SELECT COUNT(*) FROM original JOIN other USING (id);
```

Якщо число після JOIN більше — множення є.

**Правило:** якщо у звіті з JOIN раптово з'являються дивні числа, перше, що перевіряється — **кардинальність пар**. Найчастіша помилка новачків — не помічати «одне до багатьох» у другому боці.

## 11. Шпаргалка

### 11.1. Візуальне порівняння

```
       A         B
    ┌─────┐   ┌─────┐
    │  1  │   │  1  │
    │  2  │   │  2  │
    │  3  │   │  4  │
    │  5  │   │  5  │
    └─────┘   └─────┘

INNER JOIN:          LEFT JOIN:
  1, 2, 5              1, 2, 5, 3 (B=NULL)

RIGHT JOIN:          FULL JOIN:
  1, 2, 5, 4 (A=NULL)  1, 2, 5, 3 (B=NULL), 4 (A=NULL)
```

### 11.2. Коли який

| Хочу... | JOIN |
|---|---|
| Лише факти з обох таблиць | INNER |
| Усі рядки лівої, доповнити правою | LEFT |
| Усі рядки правої | RIGHT (або LEFT з обміном порядку) |
| Усі рядки з обох | FULL |
| Записи лівої БЕЗ пари справа | LEFT + WHERE right IS NULL |
| Усі розсинхронізації | FULL + WHERE left IS NULL OR right IS NULL |

### 11.3. USING vs ON

| | USING | ON |
|---|---|---|
| Короткий синтаксис | ✅ | ❌ |
| Однойменні колонки | ✅ (об'єднує) | ✅ (зберігає обидві) |
| Різні імена | ❌ | ✅ |
| Складна умова | ❌ | ✅ |

## Висновок

- **INNER JOIN** — перетин: тільки реально існуючі пари.
- **LEFT/RIGHT JOIN** — асиметрія: усі з однієї сторони, NULL з іншої якщо пари немає.
- **FULL JOIN** — об'єднання: усі з обох сторін, NULL із відсутньої.
- **Правило вибору:** як ліву беріть ту, рядки якої гарантовано повинні з'явитися у звіті.
- **USING** — короткий для однойменних колонок, об'єднує в одну; **ON** — гнучкий, для складних умов.
- **Множення рядків** — головний підводний камінь: якщо дві сторони «один до багатьох», рядки дублюються. Патерни запобігання — агрегація в підзапиті, CTE, віконні функції.

JOIN — основа аналітики в SQL. Разом з GROUP BY (пр_11), підзапитами й віконними функціями закривають майже всі задачі звітності. Наступним кроком можуть стати **рекурсивні CTE**, **lateral JOIN** і **віконні функції** — поглиблена аналітика.
