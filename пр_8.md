# Практична робота №8: Створення структури бази та її об'єктів (SQL DDL)

## Мета

Опанувати повний цикл керування структурою бази через **DDL-команди** PostgreSQL: `CREATE`, `ALTER`, `DROP`, `TRUNCATE`. Зрозуміти різницю між операціями, їхню поведінку з обмеженнями цілісності та ризики для даних.

## 3. Зміна структури: `ALTER TABLE`

Файл `alter.sql` починається з демонстрації трьох варіантів `ALTER`:

```sql
-- 1. Додати нову колонку
ALTER TABLE college.courses ADD COLUMN description TEXT;

-- 2. Встановити значення за замовчуванням
ALTER TABLE college.courses ALTER COLUMN description SET DEFAULT 'опис відсутній';

-- 3. Видалити колонку
ALTER TABLE college.courses DROP COLUMN description;
```

### 3.1. Що відбувається всередині PostgreSQL

| Крок | Під капотом |
|---|---|
| `ADD COLUMN description TEXT` | Додає колонку в каталог метаданих (`pg_attribute`); існуючі рядки отримують `NULL`. Фізичні блоки даних переписуються лише при додаванні NOT NULL без DEFAULT. |
| `SET DEFAULT 'опис відсутній'` | Зберігається тільки в метаданих, існуючих рядків не змінює. Застосовується лише до майбутніх INSERT без явного значення. |
| `DROP COLUMN description` | Колонка **позначається як видалена** у метаданих, але фізично дані залишаються в рядках до наступного `VACUUM FULL`. Місце звільняється лазі. |

### 3.2. Інші корисні форми `ALTER`

Форми, які реально знадобляться в роботі з живою базою:

```sql
-- Перейменування колонки
ALTER TABLE college.courses RENAME COLUMN title TO course_title;

-- Перейменування таблиці
ALTER TABLE college.courses RENAME TO disciplines;

-- Зміна типу колонки (ризиковано — див. §7)
ALTER TABLE college.courses ALTER COLUMN credits TYPE INTEGER;

-- Додавання NOT NULL (вимагає відсутності NULL у наявних даних)
ALTER TABLE college.courses ALTER COLUMN tuition SET NOT NULL;

-- Додавання CHECK-обмеження на існуючу таблицю
ALTER TABLE college.courses
    ADD CONSTRAINT ck_courses_tuition_max CHECK (tuition <= 100000);

-- Видалення обмеження
ALTER TABLE college.courses DROP CONSTRAINT ck_courses_tuition_max;

-- Додавання зовнішнього ключа після створення таблиці
ALTER TABLE college.enrollments
    ADD CONSTRAINT fk_enrollments_course
    FOREIGN KEY (course_id) REFERENCES college.courses(course_id);
```

## 4. `DROP` vs `TRUNCATE` — різниця

### 4.1. Створення тестової таблиці

```sql
CREATE TABLE college.test_truncate (
    id   INTEGER GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    name TEXT
);

INSERT INTO college.test_truncate (name) VALUES
    ('перший'), ('другий'), ('третій');

SELECT COUNT(*) FROM college.test_truncate;
-- count: 3
```

### 4.2. Застосування `TRUNCATE`

```sql
TRUNCATE TABLE college.test_truncate;
SELECT COUNT(*) FROM college.test_truncate;
-- count: 0

-- Структура збережена
\d college.test_truncate
```

**Висновок:** `TRUNCATE` **видалив усі рядки** (0 записів), але **структура, PK, індекси, обмеження та сама таблиця залишились** — її можна знову наповнювати даними.

### 4.3. Застосування `DROP`

```sql
DROP TABLE college.test_truncate;
SELECT COUNT(*) FROM college.test_truncate;
-- ERROR: relation "college.test_truncate" does not exist
```

**Висновок:** `DROP` знищив **і дані, і структуру повністю**. Таблиця більше не існує.

### 4.4. Порівняльна таблиця

| Критерій | `DELETE` | `TRUNCATE` | `DROP` |
|---|---|---|---|
| Видаляє рядки | ✅ так | ✅ так | ✅ так (разом зі всім) |
| Зберігає структуру | ✅ так | ✅ так | ❌ ні |
| Можна з `WHERE` | ✅ так | ❌ ні, тільки повне очищення | ❌ ні |
| Скидає `IDENTITY` / sequence | ❌ ні | ✅ опціонально (`RESTART IDENTITY`) | ✅ автоматично |
| Запускає тригери `BEFORE/AFTER DELETE` | ✅ так | ❌ ні (запускає TRUNCATE-тригери) | ❌ ні |
| Транзакційність | ✅ повна | ✅ повна (PostgreSQL) | ✅ повна |
| Швидкість на великих таблицях | ❌ повільно | ⚡ швидко (інстантно) | ⚡ швидко |
| Логування кожного рядка (WAL) | ✅ так | ❌ мінімальне | ❌ мінімальне |
| Можна відкотити (`ROLLBACK`) | ✅ так | ✅ так (у PostgreSQL) | ✅ так (у PostgreSQL) |

**Коли що використовувати:**

- **`DELETE FROM t WHERE …`** — коли треба видалити **частину** рядків за умовою.
- **`TRUNCATE TABLE t`** — коли треба швидко очистити **всю** таблицю, але зберегти її структуру (наприклад, при щоденному оновленні staging-даних).
- **`DROP TABLE t`** — коли таблиця більше **не потрібна взагалі**.

## 5. Спроба видалити таблицю з посиланням зовнішнього ключа

### 5.1. Експеримент

Спробуємо видалити таблицю `departments`, на яку посилається `courses.department_id`:

```sql
DROP TABLE college.departments;
```

### 5.2. Повідомлення PostgreSQL

```
ERROR:  cannot drop table college.departments because other objects depend on it
DETAIL:  constraint fk_courses_department on table college.courses depends on table college.departments
HINT:  Use DROP ... CASCADE to drop the dependent objects too.
```

### 5.3. Розшифровка повідомлення

PostgreSQL знаходить, що:

- **У таблиці `college.courses` є обмеження `fk_courses_department`**, яке посилається на `college.departments`.
- Якщо видалити батьківську таблицю, FK стане **«зламаним»** — посилатиметься на неіснуючий об'єкт.
- Це порушить **посилальну цілісність** усієї бази.

Тому PostgreSQL **відмовляється видаляти** і показує:

- **`cannot drop …`** — пряма причина відмови.
- **`because other objects depend on it`** — хтось залежить від цього об'єкта.
- **`DETAIL: constraint fk_courses_department on table college.courses`** — точно який об'єкт і де.
- **`HINT: Use DROP … CASCADE`** — як обійти (якщо справді цього хочемо).

### 5.4. Безпечні варіанти вирішення

**Варіант 1 — явне каскадне видалення (обережно!):**

```sql
DROP TABLE college.departments CASCADE;
```

PostgreSQL попередить, що буде видалено:
```
NOTICE: drop cascades to constraint fk_courses_department on table college.courses
```

У результаті таблиця `departments` видалиться, а FK у `courses` теж — але сама таблиця `courses` і її дані залишаться. Проте **цілісність даних порушиться** — у `courses.department_id` будуть значення, яким більше нема на що посилатися.

**Варіант 2 — спочатку прибрати залежні таблиці:**

```sql
DROP TABLE college.courses CASCADE;   -- заодно видалить enrollments
DROP TABLE college.departments;        -- тепер можна
```

**Варіант 3 — видалити FK, а тоді таблицю:**

```sql
ALTER TABLE college.courses DROP CONSTRAINT fk_courses_department;
DROP TABLE college.departments;
```

**Варіант 4 — не видаляти, а перепризначити:**

Перевести всі курси на іншу кафедру:
```sql
UPDATE college.courses SET department_id = 2 WHERE department_id = 1;
DELETE FROM college.departments WHERE department_id = 1;
```

У виробничій системі найчастіше обирають **варіант 4** — дані дорогоцінні, й втрачати їх через каскадне видалення небезпечно.

## 6. Які зміни структури небезпечні для даних

У проєкті з живими даними кожна зміна `DDL` — це потенційний ризик. Класифікація за рівнем небезпеки:

### 6.1. ✅ Безпечні зміни

Не впливають на наявні дані, лише розширюють можливості:

| Зміна | Чому безпечно |
|---|---|
| `ADD COLUMN ... NULL` (без NOT NULL) | Нова колонка заповнюється NULL, існуючі рядки не чіпаються. |
| `ADD COLUMN ... DEFAULT value` (без NOT NULL) | У наявних рядках буде NULL; DEFAULT стосується лише майбутніх INSERT. |
| `ALTER COLUMN … SET DEFAULT` | Зачіпає тільки майбутні INSERT, старі значення залишаються. |
| `ADD CONSTRAINT … CHECK (...)` | Не змінює дані, тільки блокує нові порушення (хіба що існуючі рядки вже порушують — тоді помилка). |
| `CREATE INDEX` | Чисте доповнення, пришвидшує запити. |
| `RENAME COLUMN` / `RENAME TABLE` | Дані незачеплені, тільки метадані. ⚠️ Але зламає застосунки, що посилаються на старе ім'я. |
| `COMMENT ON` | Метадані, не впливає ні на що. |

### 6.2. ⚠️ Потенційно небезпечні — вимагають перевірки

| Зміна | Чому ризиковано |
|---|---|
| `ALTER COLUMN TYPE` (звуження) | `VARCHAR(100)` → `VARCHAR(50)`: усі рядки довші за 50 символів втратяться / помилка. |
| `ALTER COLUMN TYPE` (несумісний) | `TEXT` → `INTEGER`: PostgreSQL спробує cast, якщо хоч один рядок не каститься — вся операція відкотиться. |
| `SET NOT NULL` | Якщо хоч один існуючий рядок має NULL — помилка. Потрібно спочатку заповнити. |
| `ADD CONSTRAINT UNIQUE` | Якщо є дублікати — помилка. Потрібна дедуплікація. |
| `ADD CONSTRAINT FK` | Якщо є «осиротілі» значення — помилка. Потрібно почистити. |
| `DROP CONSTRAINT UNIQUE` / `CHECK` | Дані не пошкодяться, але застосунок може почати вставляти некоректні — логічна небезпека. |

### 6.3. ❌ Небезпечні — ведуть до втрати даних

| Зміна | Що втрачається |
|---|---|
| `DROP COLUMN` | **Повністю** втрачається вміст колонки. Відновити можна тільки з бекапу. |
| `DROP TABLE` | Вся таблиця з усіма рядками. |
| `TRUNCATE` | Усі рядки таблиці (хоча структура лишається). |
| `DROP CONSTRAINT FK` + потім `DROP TABLE` батьківської | Порушить логіку застосунку, у дочірній таблиці лишаться «мертві» ID. |
| `DROP CASCADE` | Видаляє не тільки вказаний об'єкт, а й усе, що на нього посилається. |

### 6.4. Правила безпечної зміни структури на продакшені

1. **Завжди робити бекап перед DDL** — `pg_dump -U user -d db > backup.sql`.
2. **Виконувати в транзакції** — `BEGIN; … ; ROLLBACK;` — щоб перевірити без наслідків.
3. **Спочатку перевірити дані** — `SELECT COUNT(*) FROM t WHERE col IS NULL;` перед `SET NOT NULL`.
4. **Міграції робити маленькими кроками** — одна зміна = один DDL, кожна з перевіркою.
5. **Використовувати dev/staging для репетицій** — ніколи не тестувати DDL одразу на production.
6. **На великих таблицях — у технічне вікно** — деякі `ALTER` беруть ексклюзивний лок і блокують читання/запис.
7. **Для онлайн-міграцій** — спеціальні інструменти (pg_repack, pt-online-schema-change).

## 8. Відповіді на питання для захисту

### 8.1. Чим `TRUNCATE` відрізняється від `DELETE`?

Обидві команди **видаляють рядки**, але по-різному:

| Критерій | `DELETE FROM t` | `TRUNCATE TABLE t` |
|---|---|---|
| Фільтр `WHERE` | ✅ так | ❌ ні, тільки все одразу |
| Швидкість | O(n) — проходить кожен рядок | O(1) — звільняє блоки цілком |
| WAL-логування | повне (кожний рядок) | мінімальне |
| Тригери `BEFORE/AFTER DELETE` | ✅ запускаються | ❌ не запускаються (є окремі `BEFORE/AFTER TRUNCATE`) |
| Скидання `IDENTITY` / sequence | ❌ ні, продовжує з попереднього | ✅ опціонально через `RESTART IDENTITY` |
| Блокування | `ROW EXCLUSIVE` — читачі не блокуються | `ACCESS EXCLUSIVE` — блокує всіх |
| Транзакційність у PostgreSQL | ✅ можна відкотити | ✅ можна відкотити (в інших СКБД — не завжди) |

**Коли що використовувати:**

- `DELETE WHERE …` — коли треба видалити **частину** рядків за умовою або коли потрібні тригери.
- `TRUNCATE` — коли треба **швидко очистити всю** таблицю (наприклад, staging-таблиця щодня) і не потрібні DELETE-тригери.

### 8.2. Як безпечно змінити структуру таблиці з даними?

Алгоритм безпечної зміни:

1. **Зробити бекап** усієї бази або принаймні цієї таблиці:
   ```bash
   pg_dump -U student -d college -t college.courses > courses_backup.sql
   ```
2. **Виконати діагностичні запити** — переконатися, що дані не порушать нове обмеження:
   ```sql
   SELECT COUNT(*) FROM college.courses WHERE credits > 30;  -- перед CHECK (credits BETWEEN 1 AND 30)
   SELECT COUNT(*) FROM college.courses WHERE tuition IS NULL;  -- перед SET NOT NULL
   ```
3. **Загорнути зміну в транзакцію з перевіркою**:
   ```sql
   BEGIN;
   ALTER TABLE college.courses ADD COLUMN new_col TEXT;
   -- перевірити результат
   SELECT new_col FROM college.courses LIMIT 5;
   -- якщо все OK:
   COMMIT;
   -- якщо щось не так:
   -- ROLLBACK;
   ```
4. **Для несумісної зміни типу — проміжна колонка**:
   ```sql
   ALTER TABLE t ADD COLUMN new_price NUMERIC(10,2);
   UPDATE t SET new_price = CAST(price AS NUMERIC);
   ALTER TABLE t DROP COLUMN price;
   ALTER TABLE t RENAME COLUMN new_price TO price;
   ```
5. **На великих таблицях** — у технічне вікно або через онлайн-інструменти (pg_repack).
6. **Перевірити застосунок** — ім'я колонки могло змінитися, типи — звузитися.

### 8.3. Чому PostgreSQL забороняє `DROP` таблиці, на яку є посилання?

Для збереження **посилальної цілісності** (referential integrity).

Якщо б видалити таблицю `departments`, на яку посилається `courses.department_id`, у базі з'явилися б **«висячі» зовнішні ключі**:

- Обмеження `fk_courses_department` залишилося б у визначенні `courses`, але вказувало б на **неіснуючий об'єкт**.
- Усі значення `courses.department_id` стали б **логічно недійсними** — вказували б на кафедри, яких уже немає.
- Будь-який наступний `INSERT` у `courses` з посиланням на `department_id` упав би з дивною помилкою — у кращому випадку.
- Застосунок, що робить `JOIN … ON courses.department_id = departments.department_id`, вилетів би з помилкою.

PostgreSQL бере на себе **контроль цілісності** і не дозволяє власноруч її зламати. Повідомлення містить:

- **Причину** (`cannot drop table because other objects depend on it`).
- **Деталі** (яке саме обмеження й у якій таблиці залежить).
- **Підказку** (`Use DROP ... CASCADE`), якщо справді треба продовжувати.

Це класичний приклад **fail-safe** дизайну: небезпечну операцію заборонено за замовчуванням; користувач повинен явно підтвердити, що розуміє наслідки.

### 8.4. Коли `ALTER` може призвести до втрати даних?

Основні небезпечні сценарії:

**1. `DROP COLUMN` — пряма втрата:**
```sql
ALTER TABLE college.students DROP COLUMN birth_date;
```
Увесь вміст колонки `birth_date` **видаляється остаточно**. Відновити — тільки з бекапу.

**2. `ALTER COLUMN TYPE` зі звуженням або несумісністю:**
```sql
ALTER TABLE college.courses ALTER COLUMN title TYPE VARCHAR(50);
```
Якщо є назви курсів довші за 50 символів — вони або обріжуться, або операція впаде (залежно від версії й USING-кастингу).

```sql
ALTER TABLE t ALTER COLUMN age TYPE INTEGER USING age::INTEGER;
```
Якщо хоч один рядок має нечислові дані — помилка, вся транзакція відкотиться.

**3. `ALTER COLUMN SET NOT NULL` на колонці з NULL:**
```sql
ALTER TABLE college.students ALTER COLUMN email SET NOT NULL;
```
Впаде, якщо є рядки з NULL. Але якщо перед цим ви зробили `UPDATE … SET email = ''`, дані змінилися й можуть бути некоректними.

**4. `ADD CONSTRAINT UNIQUE` з наступним ручним видаленням:**
```sql
ALTER TABLE t ADD CONSTRAINT uq UNIQUE (email);
-- помилка через дублікати
-- розробник видаляє "зайві" рядки, не розібравшись
DELETE FROM t WHERE ...;
```
Небезпека не в самому ALTER, а в поспішних виправленнях.

**5. `TRUNCATE` та `DROP TABLE`:**
Формально це DDL — повна втрата даних, як обговорювалося в §4.

**6. `ADD COLUMN NOT NULL` без DEFAULT на непорожній таблиці:**
```sql
ALTER TABLE college.courses ADD COLUMN syllabus_url TEXT NOT NULL;
```
Впаде, бо існуючі рядки отримали б NULL, а колонка NOT NULL. Треба: `ADD COLUMN syllabus_url TEXT NOT NULL DEFAULT ''` або в два кроки.

**Золоте правило:** будь-який ALTER на живій таблиці — як операція на пацієнті. Спочатку діагностика (аналіз даних), потім тестування (на dev-копії), потім виконання (в транзакції з бекапом).

## Висновок

Фінальний `schema.sql` відтворює повну структуру навчальної бази `college` з нуля без помилок. Окремий `alter.sql` демонструє:

- **Три варіанти `ALTER`** — додавання колонки, задання DEFAULT, видалення колонки.
- **Різницю `DROP` і `TRUNCATE`** — очищення зі збереженням структури проти повного знищення.
- **Помилку при видаленні таблиці з FK-посиланням** — захисний механізм PostgreSQL.

Головний висновок: DDL — потужний, але небезпечний інструмент. Будь-яка структурна зміна на живій базі вимагає бекапу, тестування на staging і виконання в транзакції. Безпечніше додавати, ніж змінювати; безпечніше змінювати, ніж видаляти.
