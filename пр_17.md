## 2. Запит 1 — Підрозділ → курси → реєстрації

### 2.1. Мета

Dashboard-звіт по кафедрах: скільки курсів кожна має й скільки реєстрацій студентів зібрала загалом.

### 2.2. SQL

```sql
SELECT
    d.name                              AS department,
    COUNT(DISTINCT c.course_id)         AS courses,
    COUNT(e.student_id)                 AS enrollments
FROM college.departments AS d
LEFT JOIN college.courses     AS c USING (department_id)
LEFT JOIN college.enrollments AS e USING (course_id)
GROUP BY d.department_id, d.name
ORDER BY enrollments DESC;
```

### 2.3. Очікуваний результат

```
       department          | courses | enrollments
---------------------------+---------+-------------
 Інформаційні технології   |       3 |           4
 Математика                |       1 |           1
 Фізика                    |       2 |           1
 Гуманітарні науки         |       0 |           0
```

### 2.4. Пояснення ключових моментів

**Чому `LEFT JOIN`:**

- Хочемо побачити **всі кафедри**, включно з порожніми (HR не має курсів — все одно з'являється з 0 у звіті).
- Кожен курс може не мати реєстрацій — теж має бути в підрахунку з 0.

**Чому `COUNT(DISTINCT c.course_id)`:**

Коли на курс записані 2 студенти, JOIN створює **2 рядки** для цього курсу. Без `DISTINCT` `COUNT(c.course_id)` показав би `кількість_курсів × кількість_реєстрацій` — надуте число.

Приклад:
- Курс DB має 2 реєстрації → у джойні 2 рядки з `course_id = DB`.
- `COUNT(c.course_id)` → 2 (неправильно для «кількості курсів»).
- `COUNT(DISTINCT c.course_id)` → 1 (правильно).

**Чому `COUNT(e.student_id)` без DISTINCT:**

Кожна реєстрація — унікальний запис `(student_id, course_id)`. Нам потрібна саме кількість реєстрацій, тож дублікати тут неможливі й DISTINCT не потрібен. Якщо `e.student_id = NULL` (кафедра без курсів → всі колонки з e — NULL), COUNT автоматично це ігнорує.

## 3. Запит 2 — Середній бал студента (HAVING)

### 3.1. Мета

Розрахувати середню оцінку кожного студента з `INNER JOIN` (щоб не включати студентів без жодної реєстрації) та відсіяти тих, у кого **жодної виставленої оцінки**.

### 3.2. SQL

```sql
SELECT
    s.student_number                  AS номер,
    s.full_name                       AS студент,
    COUNT(e.grade)                    AS оцінок,
    ROUND(AVG(e.grade), 2)            AS середнє,
    MIN(e.grade)                      AS мін,
    MAX(e.grade)                      AS макс
FROM college.students    s
JOIN college.enrollments e ON e.student_id = s.student_id
GROUP BY s.student_id, s.student_number, s.full_name
HAVING COUNT(e.grade) >= 1
ORDER BY середнє DESC NULLS LAST;
```

### 3.3. Ключові деталі

**`COUNT(e.grade)` vs `COUNT(*)`:**

- `COUNT(*)` рахує усі реєстрації студента (включно з тими, де `grade = NULL`).
- `COUNT(e.grade)` рахує лише **виставлені оцінки**.
- Умова «хоча б одна оцінка» — це `COUNT(e.grade) >= 1`, не `COUNT(*) >= 1`.

**`HAVING` замість `WHERE`:**

Умова використовує агрегат `COUNT()` — у `WHERE` недопустимо (виконується до агрегації). `HAVING` фільтрує групи **після** `GROUP BY`.

**`NULLS LAST`:**

Якщо `AVG(e.grade) = NULL` (жодної виставленої оцінки), стандартне `ORDER BY ... DESC` ставить NULL на початок. `NULLS LAST` переносить їх у кінець.

## 4. Запити 3a і 3b — Курси без реєстрацій

### 4.1. Мета

Знайти курси, на які ніхто не записаний. Розглянемо дві реалізації й порівняємо.

### 4.2. Варіант A — LEFT JOIN + NULL (anti-join)

```sql
SELECT c.code, c.title
FROM college.courses       c
LEFT JOIN college.enrollments e ON e.course_id = c.course_id
WHERE e.student_id IS NULL
ORDER BY c.code;
```

**Семантика:** `LEFT JOIN` залишає ВСІ курси. Для курсів без реєстрацій колонки з `enrollments` стають NULL. Фільтр `WHERE e.student_id IS NULL` залишає саме ці.

### 4.3. Варіант B — NOT EXISTS

```sql
SELECT c.code, c.title
FROM college.courses c
WHERE NOT EXISTS (
    SELECT 1 FROM college.enrollments e
    WHERE e.course_id = c.course_id
)
ORDER BY c.code;
```

**Семантика:** для кожного курсу перевіряємо, чи **НЕ існує** жодного запису в enrollments на цей курс.

### 4.4. Порівняння

| Критерій | LEFT JOIN + NULL | NOT EXISTS |
|---|---|---|
| **Результат** | ідентичний | ідентичний |
| **Читабельність** | «джойну та відкидаю парні» | «залишаю без пари» — явніше |
| **Швидкість на великих даних** | потрібно сканувати всі збіги | short-circuit (stop на першому) |
| **Поведінка з NULL** | OK | OK |
| **План виконання** | може стати semi-join | зазвичай semi-join |
| **Небезпека помилки** | забути `IS NULL` → отримаємо всі рядки | явно виражає намір |

**Третій варіант — NOT IN** (не рекомендується):

```sql
SELECT c.code FROM college.courses c
WHERE c.course_id NOT IN (SELECT course_id FROM college.enrollments);
```

Якщо серед `enrollments.course_id` є хоч один NULL — результат порожній через тризначну логіку SQL. **Завжди використовуйте NOT EXISTS замість NOT IN** при запереченні.

**Висновок:** `NOT EXISTS` — переважний варіант. `LEFT JOIN + NULL` — коли потрібні колонки з іншої таблиці (у нас не потрібні).

## 5. Запит 4 — Викладачі з найбільшою кількістю курсів

### 5.1. Мета

Знайти **всіх** викладачів, у яких максимальна кількість курсів (якщо декілька мають однаковий максимум — показати всіх).

### 5.2. Варіант A — підзапит у HAVING

```sql
SELECT
    t.teacher_id,
    t.full_name,
    COUNT(c.course_id) AS courses_cnt
FROM college.teachers t
JOIN college.courses c ON c.teacher_id = t.teacher_id
GROUP BY t.teacher_id, t.full_name
HAVING COUNT(c.course_id) = (
    SELECT MAX(course_count) FROM (
        SELECT COUNT(*) AS course_count
        FROM college.courses WHERE teacher_id IS NOT NULL
        GROUP BY teacher_id
    ) t2
);
```

**Як працює:**
1. Внутрішній підзапит обчислює кількість курсів у кожного викладача.
2. `MAX()` знаходить найбільше значення.
3. Зовнішній HAVING залишає викладачів, у кого кількість точно дорівнює MAX.

### 5.3. Варіант B — віконна функція (альтернатива)

```sql
WITH ranked AS (
    SELECT t.teacher_id, t.full_name,
           COUNT(c.course_id) AS courses_cnt,
           RANK() OVER (ORDER BY COUNT(c.course_id) DESC) AS rnk
    FROM college.teachers t
    JOIN college.courses c ON c.teacher_id = t.teacher_id
    GROUP BY t.teacher_id, t.full_name
)
SELECT teacher_id, full_name, courses_cnt
FROM ranked WHERE rnk = 1;
```

**Переваги:** читається послідовно; `RANK()` автоматично дає всім «першим місцям» одну позначку.

**Чому не `ORDER BY ... LIMIT 1`:**

```sql
-- НЕ ПІДХОДИТЬ, якщо декілька з однаковим максимумом:
SELECT ... FROM teachers ... ORDER BY cnt DESC LIMIT 1;
```

LIMIT 1 візьме **одного випадкового** із групи максимуму. При нічиїй — не гарантовано, кого саме. Для «усіх з максимумом» потрібне порівняння з MAX або RANK.

## 6. Запит 5 — Студенти з оцінкою вище середньої по курсу

### 6.1. Мета

Для кожного курсу знайти студентів, чия оцінка перевищує середню **саме на цьому курсі**.

### 6.2. SQL

```sql
SELECT
    s.full_name AS студент,
    c.code      AS курс_код,
    e.grade     AS оцінка,
    ROUND((
        SELECT AVG(e2.grade) FROM college.enrollments e2
        WHERE e2.course_id = c.course_id AND e2.grade IS NOT NULL
    ), 2) AS середнє_по_курсу
FROM college.enrollments e
JOIN college.students s ON s.student_id = e.student_id
JOIN college.courses  c ON c.course_id  = e.course_id
WHERE e.grade IS NOT NULL
  AND e.grade > (
      SELECT AVG(e2.grade) FROM college.enrollments e2
      WHERE e2.course_id = e.course_id AND e2.grade IS NOT NULL
  )
ORDER BY c.code, e.grade DESC;
```

### 6.3. Як працює корельований підзапит

Для кожного рядка зовнішнього запиту підзапит обчислює **своє** середнє — за умовою `e2.course_id = e.course_id`.

- Для рядка «студент X, курс DB» підзапит → `AVG(grade)` по всіх реєстраціях курсу DB.
- Для рядка «студент Y, курс WEB» підзапит → `AVG(grade)` по WEB.
- Кожен рядок порівнюється зі **своєю середньою**, а не глобальною.

### 6.4. Альтернатива — віконна функція (ефективніше)

```sql
WITH enrolled AS (
    SELECT e.*,
           AVG(e.grade) OVER (PARTITION BY e.course_id) AS avg_by_course
    FROM college.enrollments e
    WHERE e.grade IS NOT NULL
)
SELECT s.full_name, c.code, e.grade, ROUND(e.avg_by_course, 2) AS avg_by_course
FROM enrolled e
JOIN college.students s ON s.student_id = e.student_id
JOIN college.courses  c ON c.course_id  = e.course_id
WHERE e.grade > e.avg_by_course;
```

Віконна функція обчислює середнє **один раз** (у одному проході) і дає його кожному рядку в партиції. На великих даних — помітно швидше за корельований підзапит.

## 7. Запит 6 — INTERSECT

### 7.1. Мета

Знайти **коди курсів**, які є одночасно в двох кафедрах.

### 7.2. Пряма реалізація

```sql
SELECT code FROM college.courses WHERE department_id = 1
INTERSECT
SELECT code FROM college.courses WHERE department_id = 2;
```

**У нашій моделі результат порожній**, бо `code` має `UNIQUE` обмеження на всю таблицю — один код не може з'явитися у двох кафедрах.

### 7.3. Практичніший варіант — спільні студенти двох курсів

```sql
SELECT e.student_id FROM college.enrollments e
JOIN college.courses c ON c.course_id = e.course_id
WHERE c.code = 'DB'
INTERSECT
SELECT e.student_id FROM college.enrollments e
JOIN college.courses c ON c.course_id = e.course_id
WHERE c.code = 'WEB';
```

Повертає ID студентів, що записані **одночасно на обидва курси**.

### 7.4. INTERSECT vs INNER JOIN

Той самий результат через JOIN:

```sql
SELECT e1.student_id
FROM college.enrollments e1
JOIN college.courses c1 ON c1.course_id = e1.course_id AND c1.code = 'DB'
JOIN college.enrollments e2 ON e2.student_id = e1.student_id
JOIN college.courses c2 ON c2.course_id = e2.course_id AND c2.code = 'WEB';
```

**Різниця:**

- `INTERSECT` автоматично прибирає дублікати, читається явніше для «спільної множини».
- JOIN дає більше гнучкості (можна додати додаткові колонки з обох боків).

## 8. Бонус — комплексний звіт

```sql
WITH student_stats AS (
    SELECT e.student_id,
           COUNT(e.course_id)     AS courses_cnt,
           ROUND(AVG(e.grade), 2) AS avg_grade,
           MAX(e.grade)           AS best_grade
    FROM college.enrollments e
    WHERE e.grade IS NOT NULL
    GROUP BY e.student_id
),
best_course AS (
    SELECT DISTINCT ON (e.student_id)
           e.student_id, c.code, c.title, d.name AS dept
    FROM college.enrollments e
    JOIN college.courses c USING (course_id)
    JOIN college.departments d USING (department_id)
    WHERE e.grade IS NOT NULL
    ORDER BY e.student_id, e.grade DESC
)
SELECT s.full_name, ss.courses_cnt, ss.avg_grade,
       bc.code AS best_course_code, bc.dept AS best_dept
FROM college.students s
LEFT JOIN student_stats ss USING (student_id)
LEFT JOIN best_course   bc USING (student_id)
ORDER BY ss.avg_grade DESC NULLS LAST;
```

**Техніка `DISTINCT ON`** — PostgreSQL-специфічна конструкція: повертає **перший** рядок з кожної групи за критерієм сортування. Тут — **кращий курс** кожного студента.

## 9. Відповіді на питання для захисту

### 9.1. Як вирішити, що використати: JOIN чи підзапит?

**Пряма відповідь:** залежить від того, чи потрібні колонки з іншої таблиці у вихідному результаті.

**JOIN — коли:**

- Потрібно **показати дані з двох таблиць поруч** (назва курсу та ім'я студента).
- Будуєте звіт з багатьох джерел.
- Треба групувати/агрегувати дані з однієї таблиці по атрибутах іншої.

**Підзапит / EXISTS — коли:**

- Треба **тільки перевірити умову**, без виведення колонок.
- Умова складна і краще виразити «перевіркою існування».
- Хочете уникнути DISTINCT (JOIN часто вимагає його через множення).

**Таблиця рішень:**

| Потрібно... | Варіант |
|---|---|
| Колонки з обох таблиць | JOIN |
| Тільки перевірка «є в списку» | IN або EXISTS |
| «НЕ є в списку» з можливими NULL | NOT EXISTS |
| Фільтр за агрегатом іншої таблиці | підзапит / CTE |
| Порівняння з іншим рядком тієї ж таблиці | self-JOIN або віконна функція |

**Практичне правило:** починайте з JOIN'ів, бо вони читаються послідовно. Переходьте до підзапитів/EXISTS, коли бачите проблеми з множенням рядків або коли «просто перевірити».

### 9.2. Чому `COUNT(DISTINCT ...)` потрібен після множення рядків через JOIN?

**Причина:** JOIN створює рядок для **кожної пари** збігів. Якщо одна сторона має багато пар, інша «розмножується».

**Приклад:**

Таблиці:
```
courses:      1 курс "DB"
enrollments:  2 реєстрації на курс DB (студенти A і B)
```

Запит:
```sql
SELECT c.course_id, COUNT(c.course_id) AS wrong_count
FROM courses c
LEFT JOIN enrollments e USING (course_id);
```

У результаті JOIN:
```
 course_id | student_id
-----------+------------
 1 (DB)    | A
 1 (DB)    | B
```

`COUNT(c.course_id)` поверне **2**, бо курс DB з'явився у двох рядках JOIN'у.

**Правильно:**
```sql
SELECT COUNT(DISTINCT c.course_id) AS correct_count;
```

`DISTINCT` каже «рахуй **унікальні** значення» — курс DB порахується лише раз, незалежно від кількості реєстрацій на нього.

**Загальне правило:** якщо агрегуєте колонку з «батьківської» таблиці після JOIN з «дочірньою» (один-до-багатьох), **завжди** додавайте DISTINCT, інакше результат буде помножений.

**Альтернатива:** агрегувати в підзапиті до JOIN (див. §9.4).

### 9.3. Як перевірити коректність складного запиту?

**Кроки верифікації:**

**1. Декомпозиція.** Розбити запит на частини, виконати кожну окремо:

```sql
-- Крок 1: перевірити внутрішній JOIN
SELECT COUNT(*) FROM courses JOIN enrollments USING (course_id);

-- Крок 2: додати GROUP BY, переглянути групи
SELECT course_id, COUNT(*) FROM ... GROUP BY course_id;

-- Крок 3: тільки після того додавати фільтри й HAVING
```

**2. Тестові дані з відомим результатом.** Вставте кілька рядків, для яких ви знаєте очікуваний вивід, і прожене запит:

```sql
-- Відомо: 2 студенти на DB, 1 на WEB
-- Очікуємо: DB=2, WEB=1
```

**3. Перевірка кардинальностей.** Порівняйте COUNT до і після JOIN:

```sql
SELECT COUNT(*) FROM enrollments;             -- 6
SELECT COUNT(*) FROM students JOIN enrollments USING (student_id);  -- має бути 6
```

Якщо після JOIN число зросло — є множення (один-до-багатьох).

**4. EXPLAIN ANALYZE.** Подивіться план виконання: правильний план (`Hash Semi Join`, `Index Scan`) vs підозрілий (`Nested Loop` на мільйонах рядків).

**5. Порівняння альтернатив.** Напишіть той самий запит іншою технологією (JOIN vs EXISTS, підзапит vs CTE) — результати мають збігатися.

**6. Перевірка країв.** Що буде на:
- Порожній таблиці?
- Рядках з NULL?
- Великих значеннях?

Багато запитів ламаються саме на граничних випадках.

**7. Логічні перевірки.** Чи сума частин збігається з загальною? Чи кількість рядків розумна для даних?

### 9.4. Що змінить LEFT JOIN на INNER JOIN у першому запиті?

**Запит:**

```sql
FROM departments d
LEFT JOIN courses c USING (department_id)
LEFT JOIN enrollments e USING (course_id)
```

**З INNER JOIN:**

```sql
FROM departments d
JOIN courses c USING (department_id)
JOIN enrollments e USING (course_id)
```

**Різниці:**

1. **Кафедра без курсів (HR)** зникне зі звіту. Її не видно взагалі.
2. **Курс без реєстрацій** (`EMPTY1` з демо-даних) зникне. Його не видно.
3. Усі агрегати (`COUNT`, `SUM`) рахуватимуться тільки по **реально задіяним** даним.

**На нашому прикладі:**

| Варіант | Рядків у звіті |
|---|---|
| `LEFT JOIN × 2` | 4 (включно з HR і порожніми курсами) |
| `INNER JOIN × 2` | 3 (без HR і без порожніх курсів) |

**Коли LEFT доцільний:**

- Dashboard-звіти — хочемо бачити всі об'єкти, навіть з 0.
- Виявлення «порожніх» записів — щоб їх видалити або заповнити.

**Коли INNER достатньо:**

- Звіти «активних» даних — цікавлять тільки реальні зв'язки.
- Звіти для аналізу використання (курси, які реально відвідувались).

**Небезпека INNER JOIN:** можна не помітити, що якісь дані «тихо зникли». Якщо звіт показує «5 кафедр», а в системі їх 7 — INNER JOIN усунув 2.

**Рекомендація:** для звітів з групуванням використовуйте LEFT JOIN за замовчуванням, щоб бачити повну картину, включно з нулями.

## 10. Типові підходи до складних звітів — підсумок

### 10.1. Патерн «одна таблиця → багато агрегатів»

```sql
WITH enriched AS (
    SELECT col, COUNT(*) OVER (PARTITION BY type) AS cnt
    FROM table
)
SELECT ...
```

Віконні функції замість корельованих підзапитів.

### 10.2. Патерн «дві таблиці з агрегатами з обох»

```sql
WITH left_agg AS (SELECT key, COUNT(*) FROM t1 GROUP BY key),
     right_agg AS (SELECT key, SUM(x) FROM t2 GROUP BY key)
SELECT * FROM left_agg FULL JOIN right_agg USING (key);
```

**Не агрегуйте одразу після JOIN** — отримаєте множення.

### 10.3. Патерн «anti-join»

```sql
-- "Що є у лівій, але немає у правій":
FROM left
WHERE NOT EXISTS (SELECT 1 FROM right WHERE right.fk = left.id)
```

### 10.4. Патерн «ranking»

```sql
SELECT *, RANK() OVER (PARTITION BY category ORDER BY score DESC) AS rnk
FROM items;
```

Для «топ-N на групу».

### 10.5. Патерн «найкращий у групі»

```sql
SELECT DISTINCT ON (group_col) *
FROM table
ORDER BY group_col, rank_col DESC;
```

PostgreSQL-специфічно, швидше за window + WHERE.

### 10.6. Правила побудови складних запитів

1. **Знайдіть «центральну» таблицю.** Зазвичай це найбільш деталізована (enrollments у нашій схемі) або та, що задає гранулярність звіту.
2. **Намалюйте граф залежностей.** Які JOIN'и потрібні, щоб отримати всі колонки з умов і SELECT-списку.
3. **Групуйте перед JOIN, якщо є агрегати з іншої таблиці.** Інакше отримаєте множення.
4. **Використовуйте CTE для читабельності.** Складний підзапит у FROM → винести у WITH.
5. **Тестуйте інкрементально.** Спочатку JOIN, потім GROUP BY, потім HAVING, потім ORDER.
6. **Пишіть коментарі** — для кожного блоку що він робить. Через місяць ви самі не згадаєте.

## Висновок

- **Складні звіти** будуються комбінацією JOIN, GROUP BY, HAVING, підзапитів і операцій над множинами.
- **LEFT JOIN** — за замовчуванням у звітах з групуванням, щоб бачити «нулі».
- **COUNT(DISTINCT)** — обов'язковий, коли JOIN множить рядки «батьківської» таблиці.
- **NOT EXISTS** — переважний варіант заперечення (безпечний з NULL, часто швидший).
- **Корельовані підзапити** читаються природно, але оптимізатор не завжди їх «випрямляє» — на великих даних краще віконні функції.
- **CTE (WITH)** — найкращий інструмент для декомпозиції складного запиту.
- **Верифікація** — через декомпозицію, порівняння альтернатив, перевірку кардинальностей.

Разом з віконними функціями і рекурсивними CTE ці патерни покривають майже всю аналітику в SQL. Наступний крок — **транзакції**, **індекси й EXPLAIN** або **віконні функції** для більш витонченої аналітики.
